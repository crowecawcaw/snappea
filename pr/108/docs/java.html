Languages

Java

Check P specs against the events your code emits during its JUnit tests.

Application code calls SnappeaEmit.emit("eReserved", ...) where a change becomes visible. After each test, the JUnit 5 extension checks that test's events against your P specs and fails the test if one was broken. You need only the specs (event declarations and spec machines), not a full P model.

It sees only the orderings your tests produce: it checks the implementation against the design, it does not explore other interleavings. For how this fits with model checking, see the overview.

Install

Java 17 or later. One artifact, io.github.crowecawcaw:snappea, holds both halves:

  • io.github.crowecawcaw.snappea.emit: SnappeaEmit.emit(...) and production sinks. JDK only; this is all production code uses.
  • io.github.crowecawcaw.snappea: recordings, checks and the JUnit 5 extension. JUnit and opentest4j are optional dependencies that your test framework brings.

The snappea checker comes in a classifier jar of the same artifact, natives-<os>-<arch> (linux-x86_64, linux-aarch64, macos-x86_64, macos-aarch64, windows-x86_64). Add it in test scope, with snappea.version set to a release:

Test setup

Every test: the JUnit 5 extension

Pick one registration:

Or every test class, with junit.jupiter.extensions.autodetection.enabled=true in junit-platform.properties. An autodetected extension steps aside in classes that register their own.

  • A recording starts before @BeforeEach and is checked after @AfterEach, so fixtures are checked too.
  • A test that already failed keeps its failure; the check's result is attached as suppressed.
  • Inject the recording as a Recording parameter when code needs it explicitly.
  • In marked mode only tests or classes annotated @Snappea are checked.
  • A recording with no events and strict off passes without running the checker.
  • Several extensions on one class need .name("billing") and @SnappeaRecording("billing") Recording parameters.

Per-test options:

Explicit checks

Closing checks once and throws SpecViolation or SetupError. The manual form is observer.start(label), then recording.stop() and recording.check(). recording.emit(...) and emitAt(...) write to that recording only, for code that takes an injected sink. Join worker threads and child processes before the check: an event emitted after the check throws.

Negative controls

Prove the spec catches the bug it is meant to catch:

It fails if the check passes or another spec is violated. Enclosing recordings, such as the extension's, ignore that spec for the rest of the test.

Property tests

Jupiter callbacks do not wrap jqwik tries: open observer.recording(...) inside each @Property method, with a CoverageCollector closed in @AfterContainer.

Emitting events

  • Payload: a Map or record for a P named tuple, a single value, or none. Enums go by name, collections and arrays as lists.
  • Key splits events into independent streams, such as one per product. Each stream gets its own instance of every spec.
  • Emit after the change commits, at the same place production code would publish it.
  • Each line records the call site, a per-process sequence number and a wall-clock time that never goes backwards.

Where an event goes, in order:

  1. A recording in this JVM: the one the current thread (or the thread that started it) opened.
  2. SNAPPEA_EVENTS_DIR, when a test started this process.
  3. The production sink, if set.
  4. Nowhere: two volatile reads. SnappeaEmit.enabled() skips building an expensive payload.

In production

A background thread writes the lines. emit never throws or waits: drops (full queue, I/O error, bad payload) are counted in SnappeaEmit.dropped(). SnappeaEmit.flush(timeout) waits for the queue.

Other processes

recording.eventsDir() is the folder itself, for containers or other services writing event lines. Events are ordered by timestamp per key; equal times keep this process's events first.

Failures

A failure shows the spec's assert message, the events of the key that broke it with where each was emitted, the assert in the P file, and the folder that keeps the events and the checker's output. SpecViolation is an AssertionFailedError, so JUnit and jqwik treat it as an ordinary failure. Its fields: spec(), key(), message(), location(), events() (each with event(), payload(), src()), liveness() and others(). Anything else is a SetupError whose kind() is:

KindCause
SetupError.BINARY_MISSINGNo snappea binary; the message says how to install one
SetupError.CONFIGBad options or config file, missing spec files, P compile errors, an unknown spec name
SetupError.PARSERA payload that does not match its P declaration, or an unreadable event line
SetupError.VALIDATIONstrict: a selected spec saw no relevant event
SetupError.UNKNOWN_EVENTAn event name no P file declares
SetupError.OUT_OF_ORDERLive input out of order
SetupError.TIMEOUTThe check took longer than the timeout

Both keep their artifacts folder (artifacts()) and the checker's report (report()). Assert on fields, not message text.

Reference

Settings

Set in snappea.properties (searched from the working directory upwards, then the classpath), or as snappea.* keys in junit-platform.properties. Paths resolve against the file's folder. The builders (SnappeaObserver.builder(), SnappeaExtension.builder()) have a method per key in camel case: .specFiles(...), .checkHot(...), and so on. Precedence: builder, environment variable, file, default. Unknown keys are an error.

SettingEffectDefault
spec_filesP files to load: paths, globs, or folders meaning every .p in themrequired
specsSpecs to checkevery spec in the files
excludeSpecs left out when every spec is checkednone
strictFail when a selected spec saw no event, which catches instrumentation that was removedtrue when specs are named, else false
check_hotAlso fail when a spec ends in a hot state (still waiting for something)false
unknown_eventsEvent names no P file declares (usually a typo): error, warn or ignoreerror
timeoutHow long one check may take30 s
artifactsWhere failed checks keep their events and outputa temp folder
coverageSuite coverage JSON: the spec handlers, statements and branches the tests reachedoff
modeWhich tests are checked: auto (every test), marked, or offauto

Environment variables

VariableEffect
SNAPPEA_SPEC_FILESSpec files, separated like PATH; overrides the configured ones
SNAPPEA_MODEauto, marked or off; overrides the configured mode
SNAPPEA_ARTIFACTSWhere failed checks keep their events and output
SNAPPEA_COVERAGESuite coverage JSON path; setting it turns coverage on
SNAPPEA_BINThe snappea binary to run, instead of the one the package finds
SNAPPEA_EVENTS_DIRSet by a recording for the processes a test starts: where they write events

Suite coverage

Set coverage (or SNAPPEA_COVERAGE): the extension writes the P spec handlers, statements and branches all checks reached once, when the run ends, and prints the summary. Outside JUnit, observer.coverage() gives a collector to pass to observer.recording(label, collector). Collectors merge into an existing file under a lock, so forks share one path; delete it before a run.
