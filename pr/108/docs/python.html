Languages

Python

Check P specs against the events your code emits during its pytest tests.

Application code calls emit("eReserved", ...) where a change becomes visible. After each test, the package checks that test's events against your P specs and fails the test if one was broken. You need only the specs (event declarations and spec machines), not a full P model.

It sees only the orderings your tests produce: it checks the implementation against the design, it does not explore other interleavings. For how this fits with model checking, see the overview.

Install

The package is imported as snappea. Its platform wheels bring the snappea checker, so no Rust or Java is needed. Python 3.9 or later. Set SNAPPEA_BIN to use another binary; pip install ./python in a checkout builds one with cargo.

Production code depends on the same package and imports only emit, which has no dependencies and does nothing unless a test is recording or a production sink is set.

Test setup

Every test: the pytest plugin

Installing the package adds the plugin. It does nothing until a [tool.snappea] table (or SNAPPEA_SPEC_FILES) exists:

  • Events emitted while fixtures are set up count. The check runs when the test body ends, so a broken spec is a test failure, not a teardown error.
  • A test that already failed is not checked. A test that emits nothing passes without running the checker.
  • pytest --snappea off (or marked, auto) overrides the mode for one run.

The snappea_events fixture is the test's recorder, for ordinary assertions: snappea_events.count("eEnter"), snappea_events.events_named("eEnter").

Explicit checks

Three functions make the check visible in the test. They work without the plugin.

  • check_spec(*specs, ...) checks the events emitted inside the block and raises SpecViolation at the end of it. Options left as None come from [tool.snappea], then the defaults.
  • check_events(events, *specs) checks a hand-written list of events, for testing a spec on its own.
  • Recorder(specs) is the manual form: start(), stop(), check().
  • Checks nest, and every active recorder gets every event, including events from threads the test starts.

Property tests

With Hypothesis, give each generated case its own recording: with check_spec(...) inside the @given body, or a Recorder per RuleBasedStateMachine.

Emitting events

  • Payload: keyword arguments, matched by name against the P event's payload type. A single positional value works for payloads that are not named tuples, or whose fields are called key or at. Enums are sent by name, sets and tuples as lists.
  • key splits events into independent streams, such as one per product. Each stream gets its own instance of every spec.
  • at sets the event time: a datetime, or an integer of epoch nanoseconds (a logical clock works). Default: now.
  • Emit when a change becomes visible (after the commit), not when it is attempted, or specs see states that never existed.
  • Each event records the file and line it was emitted from, for failure reports.

In production

The same calls can feed snappea observe on production logs. Set a sink once at start-up:

A background thread writes the lines. emit never raises or blocks: when the queue (10,000 lines) is full, a write fails or a payload cannot be encoded, the event is dropped and counted in sink.dropped. Queued lines are written at exit; sink.flush() waits for them earlier and snappea.set_sink(None) turns the sink off. In a test, the recording takes precedence over the sink.

Failures

A failure shows the spec's assert message, the events of the key that broke it (the last 20) with where each was emitted, the assert in the P file, and the folder that keeps the events and the checker's output. An event whose time was set with at= says so, which explains an order that differs from the emit order.

snappea.SpecViolation is an AssertionError, so pytest and Hypothesis treat it as an ordinary failure. Its fields: .spec, .message, .key, .events (each with .event, .payload, .src), .location, .liveness (a hot state at the end) and .others (further violations). Anything else is a snappea.SetupError with a .kind:

KindCause
"binary_missing"No snappea binary; the message says how to install one
"config"Bad options or config file, missing spec files, P compile errors, an unknown spec name
"parser"A payload that does not match its P declaration, or an unreadable event line
"validation"strict: a selected spec saw no relevant event
"unknown_event"An event name no P file declares
"out_of_order"Live input out of order
"timeout"The check took longer than the timeout

Strict checks

Strict means every selected spec checked at least one relevant event, which catches instrumentation that was removed or never ran. With named specs (check_spec("Name"), [tool.snappea] specs) it defaults to true; for this release such a check emits a snappea.StrictDefaultWarning where it would fail, and the next release fails it. Pass strict=False to keep the old behaviour. With every spec selected (the plugin's default) it defaults to false; turn it on with strict = true or pytest --snappea-strict, and mark uninstrumented tests skip=True.

Suite coverage

pytest --snappea-coverage=coverage/monitor.json (or SNAPPEA_COVERAGE) reports the P spec handlers, statements and branches the suite's checks reached, and writes them as JSON for CI. Runs merge into an existing file under a lock, so pytest-xdist workers can share one path; delete the file to start over.

How it works

Each check writes the test's events to a file and runs snappea observe on them with --json-report, then reads the report. A check costs about 5 ms; tests that emit nothing cost nothing.
