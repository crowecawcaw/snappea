Upstream parity

The same P model, schedules and observable results.

Parity means running the same project and test case with the same schedule count and seed, on one worker, then getting the same exit code, separate stdout and stderr, and the same output files after the fixed normalizations below. This measures snappea-compat; the native snappea CLI has its own presentation and defaults.

The committed check corpus contains 465 cases, of which 459 must match completely after normalization. The vendored observe corpus contains 96 runs, of which 94 must match completely after normalization. The remaining cases and runs are listed with reasons below.

The check corpus was recorded from upstream P at 260da928f67569ca7a8c0039a02d0bad7cde6096, pinned in UPSTREAM. CI runs Snap Pea against those frozen outputs; it does not need to run P.

In addition, both sides remove a leading UTF-8 byte order mark and replace the working directory with <dir>: encoding markers and temporary paths do not describe model behavior. The recorder moves compile warnings to the beginning of check output, because Snap Pea compiles when checking. No other check output is ignored.

PObserve normalization

  • Strip ANSI colors and replace the output directory with <out> to remove terminal styling and temporary paths.
  • Remove configuration lines for outputDir, supplierJars, pproj and pfiles, since the tools load specs differently.
  • Mask total runtime and per-event average and maximum times in metrics. Verified event counts remain exact.
  • Remove Java stack frames from parser and unknown-error files, since they describe generated Java rather than the P spec.
  • Sort console error blocks and mask their numbered filenames; sort error-file contents and renumber files. Upstream checks keys in parallel, so error order and numbering vary.

The executable definitions are in compat_observe_upstream.rs and compare-pobserve.py.

What this does not cover

Finite schedule counts and step bounds measure the recorded executions, not every possible execution of every model. Strategies are sampled by the option cases. PEx mode, the PVerifier tutorials, the PriorityQueue tutorial with C# foreign code, and Liveness/DynamicError/InfiniteLoopInAtomicBlock are not recorded; upstream hangs on the last one. Multiworker schedule ordering, generated code, C#/Java foreign code, and .NET/Java stack frames are outside this comparison. Timings and memory are not performance assertions.

See the compatibility reference for supported features and the validation guide for broader compiler, checker and tutorial tests.
