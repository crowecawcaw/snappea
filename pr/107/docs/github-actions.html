GitHub Actions

Check your P model on every pull request, so a design change can't quietly break it.

A model that is checked once and then forgotten drifts from the design. Run it in CI like any other test: a job installs snappea in about a second, runs the model's test cases, and fails the pull request when one finds a bug. This works the same for a change to the model made by a person or by an agent.

A workflow

Save this as .github/workflows/p-model.yml, with working-directory set to the folder that has your .pproj file (or your .p files):

  • Install. The install script downloads the release, checks its checksum, and adds snappea to the PATH of later steps. Pin a version so a new release can't change your results without a commit; leave out -s -- --version ... for the latest.
  • Check. snappea check with no arguments finds the sources and checks every test case. The job fails on exit status 1 (a bug) or 2 (an error, such as a type error).
  • Output. On a failure, the artifact has the failing schedule's log (bug.txt) and a bug.schedule file. Download it from the run page and run snappea replay bug.schedule locally to step through the same bug.

This repository runs the same workflow on its example model: check-model.yml, linked from examples/model/github-workflow.yml.

How long to explore

Search strategies are selected automatically. The default is ten seconds per test; choose a larger timeout for CI when needed. Exhaustive completion ends a check early:

--timeout 2mExplore for a fixed time per test case. The simplest choice for CI.

The checker uses every CPU core by default. A slower nightly job with a larger budget (on: schedule) is a good complement to a quick check on each pull request.

Specs in your language's tests

The language helpers check P specs inside your ordinary unit tests and bring the checker with them, so CI needs no install step: see Python, Rust, Go and Java. Run pytest, go test, cargo test or your Maven or Gradle build as usual.
