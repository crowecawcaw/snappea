Command line

Install the snappea checker and run it on P models and logs.

snappea is one binary with no runtime dependencies: no .NET, Java or Python. It type-checks P sources, explores the schedules of their test cases, and checks logs of a running system against P specs.

Install

On Linux or macOS:

On Windows, in PowerShell:

The script downloads the latest GitHub release for your machine, checks it against the release's SHA256SUMS, and puts snappea in ~/.local/bin (Windows: %LOCALAPPDATA%\snappea\bin, added to your user PATH). It supports Linux x86_64 and arm64 with glibc, macOS on Intel and Apple silicon, and Windows x86_64.

To pin a version or pick the folder:

The same settings work as environment variables, SNAPPEA_VERSION and SNAPPEA_INSTALL_DIR, which is how the PowerShell script takes them. Check the install with snappea version.

Sources

Commands that read P take .pproj or .p files as arguments. With none, they use the *.pproj file in the current folder, or else every *.p file in it and its immediate subfolders. So in a project folder, snappea check is usually enough. There is no separate compile step.

Exit status

0No bug found.
1A bug (or, for observe, a spec violation) was found.
2Any other error: a type error in the sources, a missing file, a bad option.

This makes every command usable as a CI step or a pre-commit hook as it is.

Text and JSON

Every command prints text for people on a terminal or in CI, and a JSON result for agents and scripts otherwise. SNAPPEA_FORMAT=text or json sets the default; these options choose per run:

--format text|jsonText or the JSON result. Default: text on a terminal or in CI (CI set), JSON otherwise.
--jsonThe same as --format json.
--json-report <FILE>Also write the JSON result to FILE.

Output options work before or after the command. Unknown options and missing values also produce a JSON error result and write --json-report when requested. JSON keys retain insertion order.

snappea check

Checks test cases by exploring schedules: orderings of messages between machines, and the choices the model leaves open. A TEST is a test case name or a glob (tc*); with none, every test case is checked. It prints one line per test case with its coverage and, for a bug, the failing assertion and a snappea replay command. Then it lists the code no test case ran: handlers never triggered, if conditions never true or never false, and statements never reached.

Coverage from a test case stopped at its first bug is marked partial in the console and withcoverage.partial: true in JSON, including the combined total. Scenario coverage appears as a console summary and as scenarios artifacts in suite and test case JSON results. The coverage guide explains condition outcomes, transition pairs, and components excluded from the selected tests.

Search is automatic: exhaustive, random, guided, and priority scheduling retain their state between executions. Recent behavioral novelty per controlled choice changes their work shares; every enabled strategy retains a minimum share. Small exhaustive searches end early. A timeout or coverage plateau does not establish that the model is correct. The default timeout is fixed at ten seconds per test. --time remains an alias for --timeout.

When every test case passes, check then runs them against mutants: copies of the model with one small change, such as a removed statement, an if forced one way, or < swapped for <=. A change no test case detects is listed with its line: the code ran, but no spec or assertion depends on what it does. Add a spec, an assertion or a test case that would fail with the change, or suppress it with // snappea-lint: allow mutation[:kind] -- reason on the line before. Specs and test drivers are not mutated, and undetected mutants do not change the exit status. JSON results list them under mutation.undetected. Changes share the time limit round robin, so a run cut short gives each about the same number of schedules.

snappea check lint [SOURCE...] runs only the model lints, without exploring schedules. snappea check mutation [SOURCE...] [TEST...] runs only mutation testing, with a 5 minute limit by default, and exits with 1 when a change goes undetected, so CI can require every change to be detected or suppressed.

How much to explore

--timeout <DURATION>Time limit per test case. Default 10s; accepts seconds or units (90s, 5m, 1h).
-j, --workers <N>Worker limit. Default: one per CPU core.
--seed <N>Seed for reproducible choices. Not needed to reproduce a bug: its .schedule replays exactly.

Mutation testing

--mutation-timeout <DURATION>Time limit for mutation testing. Default 30s.
--no-mutationSkip mutation testing.

Time and output

--latency <FILE>[:<PROFILE>]Latency profiles (TOML), and the profile to use.
--timedTime-aware scheduling: never run a step that is certainly later than another.
-o, --out <DIR>Output folder. Default PCheckerOutput.
-v, --verboseShow progress and statistics, and log every schedule.

Output files

A test case that finds a bug writes to <DIR>/<TEST>/, replacing the previous run's files: bug.txt (the log of the failing schedule), bug.schedule and bug.trace.json. Scenario monitors also write scenario_coverage.json there.

snappea replay

Runs a schedule written by snappea check again, so you can fix the model or the design and confirm the bug is gone. Exit status 1 means the bug was reproduced. If the schedule was found with step options (--max-steps and the others), pass the same ones; the replay line that check prints includes them.

snappea tests

Type-checks the sources and lists their test cases, one per line. A fast first step in CI.

snappea observe

Checks logs of a running system against P spec monitors. A LOG is a file, a folder of logs, or a quoted glob ("logs/**/*.jsonl"). By default each line is one JSON event. It prints one line per spec with its coverage (the spec's handlers, statements and branches the events ran), and lists the spec code no event ran. The observe guide covers log formats and live streams.

--spec <NAME>Spec monitor to check; repeat or separate with commas.
--all-specsCheck every spec monitor (--exclude-specs to leave some out).
--live <PATH>, --stdinRead a live stream of lines until it ends, stopping at the first error.
--p-traceThe logs are P JSON traces (bug.trace.json from snappea check).
--parser-config <JSON>Where the JsonLines parser finds its fields, e.g. {"event": "msg.type", "key": "msg.id"}.
--key <KEY>Check only this key; repeat for several.
--check-hotReport a key whose spec is still in a hot state after its last event.
--strictFail a spec that checked no relevant event.

snappea coverage

merge combines the scenario coverage reports under a folder (for example, from several CI jobs) into one. merge-observe merges the coverage of snappea observe JSON results, without the P sources.

More

Every command has --help. If you have scripts written for upstream P's p check, snappea-compat takes the same options and prints the same output; see Coming from P. To check P in CI, see GitHub Actions.
