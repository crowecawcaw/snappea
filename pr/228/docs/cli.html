Command line

Install the snappea checker and run it on P models and logs.

snappea is one binary with no runtime dependencies: no .NET, Java or Python. It type-checks P sources, explores the schedules of their test cases, and checks logs of a running system against P specs.

Install

On Windows, in PowerShell:

The script downloads the latest GitHub release for your machine, checks it against the release's SHA256SUMS, and puts snappea in ~/.local/bin (Windows: %LOCALAPPDATA%\snappea\bin, added to your user PATH). It supports Linux x86_64 and arm64 with glibc, macOS on Intel and Apple silicon, and Windows x86_64.

To pin a version or pick the folder:

The same settings work as environment variables, SNAPPEA_VERSION and SNAPPEA_INSTALL_DIR, which is how the PowerShell script takes them. Check the install with snappea version.

Sources

Commands that read P take .pproj or .p files as arguments. With none, they use the *.pproj file in the current folder, or else every *.p file in it and its immediate subfolders. So in a project folder, snappea check is usually enough. There is no separate compile step.

Exit status and output

Every command exits with 0 when nothing failed and non-zero otherwise, so it works as a CI step or a pre-commit hook as it is. What fails a check lists the exit statuses of check; the --help of check, check mutation, check lint, replay and observe states theirs.

Every command prints text by default, for people and agents alike. --json or SNAPPEA_FORMAT=json prints the JSON result instead, and --json-report FILE also writes it to a file.

snappea check

Checks test cases by exploring schedules: orderings of messages between machines, and the choices the model leaves open. A TEST is a test case name or a glob (tc*); with none, every test case is checked. It prints one line per test case with its coverage and, for a bug, the failing assertion and a snappea replay command. Then it lists the code no test case ran: handlers never triggered, if conditions never true or never false, and statements never reached.

Coverage from a test case stopped at its first bug is marked partial in the console and withcoverage.partial: true in JSON, including the combined total. Scenario coverage appears as a console summary and as scenarios artifacts in suite and test case JSON results. The coverage guide explains condition outcomes, transition pairs, and components excluded from the selected tests.

Search is automatic: small models are searched exhaustively and can be proved; larger ones are sampled with several schedulers. Each passing test case gets a verdict: proved, search settled, or still finding new behavior, which means it needs more time or a smaller test. Without --timeout the test cases share a short time budget; set --timeout before trusting a pass on a large model.

When every test case passes, check then runs them against mutants: copies of the model with one small change, such as a removed send or an if forced one way. A change no test case detects fails the check and is listed with its line: the code ran, but no spec or assertion depends on what it does. Add a spec, an assertion or a test case that would fail with the change, or suppress it with a reason. See mutation testing.

snappea check lint runs only the model lints, without exploring schedules. snappea check mutation runs only mutation testing, with more time, e.g. as a CI gate.

A failing test case writes its bug.txt (read this first), bug.schedule for snappea replay and bug.trace.json to PCheckerOutput/<TEST>/. snappea check --help lists every option and default; the checking reference states the exact behavior.

snappea replay

Runs a schedule written by snappea check again, so you can debug it (-v logs each step) and, after fixing the model or the design, confirm the bug is gone. Exit status 1 means the bug was reproduced. Copy the command from the Replay: line that check prints.

snappea tests

Type-checks the sources and lists their test cases, one per line. A fast first step in CI.

snappea observe

Checks logs of a running system against P spec monitors. A LOG is a file, a folder of logs, or a quoted glob ("logs/**/*.jsonl"). By default each line is one JSON event. It prints one line per spec with its coverage (the spec's handlers, statements and branches the events ran), and lists the spec code no event ran. The observe reference covers its options, log formats and live streams.

snappea coverage

merge combines the scenario coverage reports under a folder (for example, from several CI jobs) into one. merge-observe merges the coverage of snappea observe JSON results, without the P sources.

More

Every command has --help. If you have scripts written for upstream P's p check, snappea-compat takes the same options and prints the same output; see Coming from P. To check P in CI, see GitHub Actions.
