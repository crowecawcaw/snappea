## Shared public contract and implementation algorithms

PUBLIC/TASK.md:3-26 requires shared Store state, bounded FIFO, persistent accepted and rejected put results keyed by string ID with same-item retries, persistent take results including None, distinct put/take namespaces, positive general capacity, competing clients, the actual atomic Store operation, implementation-derived observations, and proper handling of concurrent ordering. PUBLIC/runtime.py:13-23 separates atomic versioned loads from atomic compare-swap and deep-copies both directions.

Both Python algorithms appear consistent with the core FIFO/CAS contract on the required valid input domain, based on inspection rather than execution. A/solution.py:11-17,22-39,44-57 initializes with CAS and reloads after failed CAS; B/solution.py:20-28,44-57,62-70 does likewise. Both commit queue mutation and memo atomically in one record, including rejected puts and empty takes. Duplicate results return from a load containing the memo; snapshots return load-derived copies (A:59-60; B:72-74). These read-only paths linearize at load, while new-operation paths linearize at successful CAS; the prose statement that every operation's successful CAS is its linearization point (B/DESIGN.md:4-7) is too broad for memo hits and snapshots.

Capacity behavior differs: A uses the Store's initialized capacity even when a later wrapper requests another value (A/solution.py:9-17; A/test_observation.py:15-16). B rejects a mismatch and rechecks it on loads (B/solution.py:23-25,37-38; B/test_observation.py:66-72). PUBLIC/TASK.md:12 says all instances sharing a Store use the same capacity, but does not explicitly prescribe conflicting-constructor behavior. Treat this as an interpretation difference, not an established core-contract failure. Both support positive capacities beyond 2 in code; B additionally saves a capacity-7 test (B/test_observation.py:42-64), whereas monitors/models intentionally encode capacity 2.

## A: broad abstract history, missing selected monitor and actual contention model

1. A/tests.p:1-2 is comments only. There is no explicit selection of QueueContract; A/monitor.p:1 explicitly suppresses an unselected-spec lint. Consequently the frozen source does not establish that the intended P history is checked by QueueContract. This is a selection/coverage finding, not a claimed solver outcome. The Store's only direct assertion checks same-ID item equality (A/model.p:30-31), not an independent FIFO/capacity invariant.

2. A/model.p:7-8 describes each whole request handler as a successful CAS transition. The handlers (28-63) directly compute and update queue and memo state together, then announce their chosen results. There is no version, separate load, stale proposed record, failed CAS, or retry transition. Two Client machines exist (70-77,86-88), but both send exactly the same ID `left` and value 11. This can represent two competing duplicate logical requests at an abstract serialized Store, not implementation-level read/CAS contention or distinct-operation lost-update schedules. The independent reference monitor is meaningful when fed implementation observations, but constructing the same abstract desired behavior in one atomic model handler does not establish refinement from the supplied Store interface.

3. A/DESIGN.md:16 explicitly says the P model should expose load/CAS contention; executable A/model.p does not do so. DESIGN.md:13 promises distinct-ID one-slot puts and take/put races; the P workload has neither. A/model.p:89-105 queues a serial request history then starts clients without responses or a barrier confirming Store completion, so the prose phase boundary that clients act "now" after the serial history is not an executable completion boundary across senders.

4. A's model includes takes and retry histories (A/model.p:91-101), but the rejected `full` put is never retried after capacity changes, and the `empty` take is retried only after the scripted refill has been drained. Thus those particular model cases do not witness the temporal distinction between retaining a memo and recomputing the same result. The successful take retry at 96-97 does occur while a second item remains, and the same-ID put repeat at 92-93 would expose duplication if an independent selected reference monitor were checking it.

5. Saved Python assertions supply stronger temporal witnesses than the P model: reject `put-c`, take an item, retry rejection, assert snapshot [20] (A/test_observation.py:28-48); empty take, enqueue 50, retry empty, assert [50] (58-79). Put/take same-ID namespaces are exercised (62-67). The successful take retry at 53-56 occurs after the other item was already removed at 49-52, so that particular Python assertion does not demonstrate preservation of a pending later item.

6. A/test_observation.py:20-81 derives serial events from public results and writes observation.jsonl, but does not invoke `snappea observe`. It appends the same ePut twice for one call (43,45) and the same eTake twice for one call (55,57). These redundant memo events can pass the monitor but are not one-event-per-actual-call observations. They do not by themselves demonstrate a queue defect. A's concurrent test uses separate wrappers and a start barrier with two distinct puts into capacity 1 (87-103), followed by concurrent retries of the already successful ID (105-116). Independent assertions check acceptance count, final length, and later exact winning item. This is genuine saved thread coverage, but does not force competing loads before CAS, test simultaneous first-time duplicates, or record a complete concurrent linearizability witness.

## B: selected independent monitor, explicit CAS interference, narrower model workload

1. B/tests.p:1 explicitly selects QueueContract against module model. B/monitor.p:20-55 independently reconstructs queue and memo state from observed results and asserts acceptance, found/item FIFO, stable retry results, and snapshots. This is stronger executable selection evidence than A's comments-only tests.p. Both monitors retain separate put and take maps and check item identity on put retries (A/monitor.p:21-54; B/monitor.p:20-55).

2. B/model.p:37-70 explicitly splits load/computation and proposed-record CAS into separate events, carries a version with the proposed queue state, commits only on version equality, and reloads on failure. This represents the relevant stale-read/lost-update boundary that A abstracts away. The accepted-result memo is committed in the same handler as the queue/version update (59-67). The additional local assertion `count <= 2` (64) is an invariant, but much of the useful checking remains the independently selected monitor.

3. The modeled workload is only three initial puts `a=10,b=20,c=30`, then one retry of `a` (B/model.p:9-11,72-78). There are no eTake or eSnapshot operations in the P model. Monitor lint suppressions explicitly delegate those coverage gaps to Python tests (B/monitor.p:35,51). DESIGN.md:20-21 should therefore not be read as P exploration of FIFO removal, take retry, or snapshot behavior. The load/CAS states model contention for tagged requests, but not three independently executing client machines: Main submits the requests in fixed order and Store sends its own CAS/reload events. FIFO delivery constraints can restrict successful order; the source does not establish exploration of all permutations of independently invoked puts merely by tagging requests with client integers. The client integer otherwise only propagates through retry payloads.

4. B's saved Python behavior and observed history retry a rejection while still full and retry an empty take while still empty (B/test_observation.py:21-34,98-109). They lack the decisive rejection-after-space-freed and None-after-refill witnesses that A saves. B's successful take retry is stronger in its Python serial history: it retries t1 while item 5 remains (28-30,104-105). B's namespace test retries a successful put after its original item has been removed (36-40), a useful changed-state success-memo witness. Neither saved suite directly exercises distinct request IDs with equal item values.

5. B/test_observation.py:80-96 emits one serial event immediately after each public result and 111-122 explicitly invokes strict `snappea observe` with QueueContract. This is an executable observation integration, unlike A's event-file-only test; no claim is made here that the command passes. Its concurrency test (42-64) uses one Queue wrapper, 25 barrier-started distinct puts at capacity 7, checks acceptance and final counts, and drains seven values. It does not retain request-to-result association or compare exact accepted values/FIFO order against final state, and does not exercise overlapping wrappers, concurrent take/put, or concurrent same-ID first calls. No completion-order stream is incorrectly presented as concurrent linearization order: both submissions keep monitor observations serial and make limited invariant assertions for thread tests.

## Interpretation limits

The monitors can meaningfully reject wrong externally observed serial behavior; they are not inherently vacuous specifications. A's P check selection and atomic abstraction limit what its saved model check could support. B has explicit selected-monitor checking and an actual stale-CAS transition, but only for a narrow put-only workload. Python coverage partially complements each model in different ways. None of these source observations establishes a test run result, private evaluator behavior, a numeric ranking, or a causal explanation of how either submission was produced. The two additional frozen sources were not sought or inspected.

It does not supply a valid empty-result-after-refill witness: the fresh take at 57 was never empty. The concurrent tests independently assert a distinct-ID one-slot winner and exact winning item (79-94), simultaneous first-time identical puts across wrappers (96-108), and simultaneous identical takes across wrappers plus later retry preservation (110-127). ### Added internal declarations: semantics versus packaging

PUBLIC/TASK.md:24-26 requires QueueContract to use the declarations in events.p and requires observation events to derive from implementation public results. It does not explicitly require events.p to remain byte-identical or forbid appending internal declarations. A02/events.p:1-3 preserves the public event names and exact payload types; monitor.p:1 still observes only those three public events. Its internal events do not alter public queue semantics. On the visible task alone, their placement in events.p is a source-organization choice, not an established contract-semantic violation.

There is nevertheless a concrete packaging dependency. PUBLIC/TASK.md:22-23 explicitly lists six required submission files and does not list events.p among authored deliverables, while A02/model.p uses the internal names without declaring them locally (e.g. 23-27,49,83-106). The instructed check command includes events.p (PUBLIC/TASK.md:33), so the frozen full directory supplies the declarations. Under the stated hypothetical of restoring original public events.p and checking the six authored files, eLoad/eLoaded/eCASPut/eCASTake/eDone/eRetry/eStartPut/eStartTake/eSnapshotReq/eStartFifo would have no declaration in these sources, preventing that model from being compiled as written. This is a source-deducible portability/harness-compatibility issue; no grader outcome has been inspected. Moving the same internal declarations into model.p would preserve model behavior and public schema. It would be inappropriate to equate this packaging issue with changing the public contract or use it as evidence of weaker queue semantics.

### Executable model and selected assertions

1. A02/tests.p:1-3 explicitly selects QueueContract for three workloads: competing puts, empty take, and mixed FIFO traffic. The independent monitor asserts current capacity/FIFO behavior and memo identities/results (A02/monitor.p:17-44). It reconstructs expected state rather than merely asserting values directly set by the Store model. In particular snapshots compare the entire sequence (43-44).

2. Unlike A01/B02, A02 models independently scheduled client load and CAS requests with a saved version and retry response (A02/model.p:23,27-47,49-71,98-110). The Store compares the loaded version before committing new logical requests, increments the version for rejected puts and empty takes too, and commits queue effects and memos in the same handler. Its announcements occur at the Store operation transition (25-26,30,38,44,51,61,68), so they carry an explicit modeled operation order rather than B02's client receipt order.

3. This is still an abstraction of runtime.py: the load response includes only the version (A02/events.p:5; model.p:23), and the Store computes the effect from its own current state after a successful version check instead of receiving a client-computed candidate record from a deep-copied load. Equal versions justify equivalence for a correctly computed transition, and the model does expose stale-version retries, but it cannot expose bugs in client-side record copying/proposal construction that are absent from its representation. B01 carries a concrete proposed queue state in eCASPut, so the two models expose different detail. Memo hits bypass version validation at the modeled Store handler (28-31,50-52), whereas Python memo hits return at load (solution.py:28-34,48-50); both are legal abstract linearization choices, not an exact instruction-by-instruction refinement proof.

4. The competing-put workload creates distinct clients for p1=10 (one retry), p2=20, and p3=30 (A02/model.p:165-180). EmptyMain repeats the same empty take without any refill (183-190), so it does not witness memo retention after a new item arrives. FifoMain races put fifo=7 followed by take fifo and its retry with a distinct put racer=8 and take racer (115-161). This supplies selected mixed-operation concurrency and namespace coverage. Concurrent interleaving can place a later item before a successful take retry, but no dedicated driver forces that changed-state scenario. There is no rejected-put retry after space is freed: Main has no takes, while FifoMain has at most two distinct puts at capacity 2. The P snapshot workload emits only an initial snapshot request (176), not snapshots throughout post-mutation states.
