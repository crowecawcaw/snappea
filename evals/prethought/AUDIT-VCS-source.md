# Initial SOURCE-ONLY audit: frozen VCS a01 and b01

Scope: read only the authorized public TASK.md, contract.py, runtime.py and the six files in the two frozen submission directories. No solver, implementation, or tests were executed. No prompts, metadata, grades, private fixtures, transcripts, or other submissions were inspected. No repository file was changed. SHA-256 hashes of all nine reviewed source files are in `/tmp/prethought-audit-vcs-hashes.json`. This is a qualitative exploratory comparison, not a numeric ranking or an inference about author intent/private reasoning.

Paths below abbreviate `/workspace/snappea-skill/evals/certified-bundles/` as BASE, with A=`BASE/runs/prethought-vcs-a01/submission/` and B=`BASE/runs/prethought-vcs-b01/submission/`.

## Contract and runtime boundary

The required concurrency is multiple independent Service instances, overlapping calls, durable writes with lost responses, and fresh instances after crash (BASE/public/TASK.md:7-11,60-76). All head changes, the published marker, and the publish-request outcome must become visible at one point, including durable memoization of rejected outcomes (TASK.md:36-47). Revision, approval, and CI invalidation matter independently (TASK.md:25-35). A snapshot reader must be consistent (TASK.md:48). The store actually yields before and after each read/CAS, deep-copies stored values, rejects values above 16,384 bytes, and can raise Crash after a successful write (BASE/public/runtime.py:29-48). Thus a model of an already atomic logical publish is a specification abstraction, not executable coverage of this storage protocol.

## A: abstract commit plus recoverable pending snapshots

**Executable P coverage is narrow and serial.** A/design.p:35-42 creates one AtomicPublish target and sends it two identical publish events from the same Main handler. There are no competing writer machines, read events, response values, request identifiers, failure events, or store/CAS primitives. The sole Publish handler sets both heads, published, outcomeRecorded, and current together before assertions (design.p:21-31). The head equality assertion is a legitimate safety expression, but the implementation protocol cannot interleave inside these assignments. The other assertion checks the variables just set together. The second event is a repeat of a guarded no-op (current already 1), not a modeled lost-response retry with an independently checked returned memo. There is no application count or varied next update to detect a second application. No revisions, authorization, CI, stale/not_ready/conflict outcomes, rejection memoization, competing parents, partial snapshot writes, helpers, or recovery are represented. The saved P test is AtomicCommitPoint (design.p:46-47).

**Prose accurately limits this abstraction, but execution claims are not independently established here.** A/DESIGN.md:44-56 calls this an abstract commit check and explicitly says pending recovery/chunk encoding are outside the P model. It reports five schedules and a check command allowing incomplete coverage; this source-only audit has not rerun or verified that report. Its statement about retry not applying twice is stronger than the model's observable request/response coverage. The submission directory contains no saved Python test file or runtime-check script; its three saved files are DESIGN.md, design.p, solution.py. The public interface-test coverage claim (DESIGN.md:55-56) cannot establish which crash schedules those tests exercise under this restricted audit.

**Python represents the missing protocol rather than implementing the small P machine literally.** A/solution.py:95-114 reads an immutable generation, claims a pending root by CAS, then helps finish that operation. `_finish_pending` applies the op to the prior snapshot, uses the pending root's version as generation identity, writes immutable chunks/manifest, and CASes root to expose the generation (solution.py:78-85). Concurrent helpers must reproduce identical data, with collision checks (39-53). Readers help pending work before reading one selected immutable snapshot (87-93). Submit/publish retries return stored outcomes before another pending write (103-106); semantic checks, revision resets, set-like approvals, CI replacement, ordered publish checks, and publishing memo plus heads are present in `_apply` (150-208). This is meaningful storage coordination absent from the P model. The source supports the stated root-switch linearization architecture; it is not a proof that all interleavings work.

**Concrete representation limitation:** an operation, including its complete update map, is placed directly in the single pending-root record (solution.py:107-108; submit/revise copy the full map at 116-124). Chunking the later snapshot does not bound that root write. Also `_chunks` splits only between rows and never splits/rejects one oversized row (16-31), and a bundle's complete update map is one row (18-20,157-158). Valid strings have no stated length cap (TASK.md:15-19), so sufficiently large legal updates can exceed the store limit, irrespective of total-history chunking. A/DESIGN.md:63-64 acknowledges a one-row fit assumption using “ordinary commit IDs,” an assumption absent from the contract. This is a static input-size concern, not an observed test result. A failure after a pending root has been installed can cause later helpers to encounter the same unwritable snapshot.

## B: two-client event-order abstraction plus immutable event log

**The P model adds a real producer race, but the publication protocol is still assumed atomic.** B/model.p:20-33 creates two client machines, each sending a distinct publish followed by a read to one Commit machine. Different clients can race in event delivery. Each central handler checks both parent heads and assigns both new heads and its winner flag in one handler (11-16). Read handling independently asserts paired-head equality and mutual exclusion of winners (17). This covers event ordering of two shared-parent contenders at an abstract serialized commit point. It does not represent separate repository writes, snapshot staging, a CAS loser/reload loop, or a reader that itself performs multiple store reads. The “reader” is eRead handled by the central Commit machine, not a third independent reader client. The test is tcConcurrentAtomicHeads (36-37).

**Coverage is broader than A's producer sequence but still a small specification fragment.** B's P model has no explicit publish outcomes or request IDs, durable response memo, repeated publish, revisions, approvals, CI, rejections, initialization race, failures, crashes, restart, blob/event preparation, root pointer or recovery. The model's failed parent guard simply does nothing: it does not assert a conflict return or durable conflict memo. B/DESIGN.md:5 describes the shared-parent race and reports 144 schedules. DESIGN.md:7-9 lists useful exposing scenarios beyond that model. DESIGN.md:29-31 reports solver/public/additional runtime checks, but no saved Python test file/script or output is present in the frozen submission directory. Those are prose reports, not independently inspectable executable coverage in this source set.

**Python uses a different, explicit optimistic protocol.** B/solution.py:90-107 reads one root and reconstructs its immutable predecessor chain. `_commit` persists any blob chunks and an immutable event before its root CAS (109-124); callers loop and reevaluate after a failed root CAS (e.g. publish 193-225). A losing/crashed precommit attempt leaves unreachable immutable data rather than a globally pending operation requiring help. A successful publish event holds result memo, all new heads, and published state together on replay (33-55,219-223), and request memo is checked before the remaining publish conditions (195-218). Revise clears approvals/CI (38-44), reviewers are restricted (167-179), CI replaces prior results after revision/digest checks (181-191), and submit saves its original response (126-147). The source aligns with the design's root-pointer visibility argument (DESIGN.md:15-23), while the P model does not validate this algorithm.

**Sizing and progress limits:** B chunks canonical ASCII event payload text into 6,000-character pieces once delta encoding exceeds 8,000 bytes (76-88,109-124), rather than assuming a whole update row fits. This addresses the specific A pending-map/whole-row limitation structurally. However every snapshot reads the entire event chain plus referenced blobs, and every attempt rebuilds state (90-107). Thus quiescent store calls grow with total committed events, with a lower bound of one root read plus one read per event before the operation's own writes. More than 4,999 prior events necessarily exhaust a 5,000-call limit even without blobs. TASK.md:78-80 states a 5,000-call quiescent bound and hundreds of bundles but does not bound the number of revisions/CI updates per bundle. B/DESIGN.md:25 acknowledges growing replay cost but its assertion that ordinary hundreds-of-bundle histories stay within budget is not an encoded bound or source-only test evidence.

## Comparative conclusion

Both submissions implement substantive synchronization and durability logic that their P models omit. A models one atomic successful publish plus a same-sender repeated event; B models two competing publish event producers and read checks at the atomic abstract service. B therefore adds a shared-parent contention scenario, while neither provides implementation-level independent checking of CAS interleavings, failure recovery, durable response identities, rejected outcomes, or revision/certification races. Both construct a coherent new logical state atomically in their P handlers, so passing assertions at that boundary do not establish that the Python storage protocol implements that atomic boundary. A explicitly disclaims modeling recovery; B's wider failure-mode prose remains mostly outside its saved model. Python source includes many of those semantics; the absence from a model must not be confused with their absence from implementation. All execution counts and runtime checks mentioned above remain unverified author reports in this initial source-only phase.

## Third frozen source: prethought-vcs-b02 (SOURCE-ONLY addendum)

C abbreviates `BASE/runs/prethought-vcs-b02/submission/`. Only C/DESIGN.md, C/model.p, and C/solution.py were added to the reviewed sources; their hashes are appended to the existing JSON manifest. No tests/solvers were executed and no other files were read. These are the only files present in the frozen submission directory, including hidden-file enumeration: no standalone saved Python tests or runtime-check artifacts are available there.

**Actual modeled concurrency is one serialized API-event stream.** C/model.p:41-64 creates one Ledger and one Main sender that queues a fixed ordered sequence of approve/CI/failing-CI/revise/publish events. There are no two competing clients, read events, store operations, or CAS comparisons. Ledger handles each entire logical mutation as one handler (21-38). This differs from B01's two competing producers: B02 expands logical rule scenarios but does not preserve its competing-publisher scenario. Its self-sent eApplied event (35) is consumed by a no-op handler (29), and the separate Safety observer sees eApplied (68-76). Any scheduling of that notification is not competing storage-step coverage.

**Exactly represented rules:** approval count starts at zero and saturates at two; publication blocks further approval, CI, and revision changes; passing/failing CI sets/clears one boolean; revise clears approvals and CI; publish requires unpublished plus count two plus CI; a successful publish increments both heads and marks published (C/model.p:14-38). A single fixed driver sends an initial unready publish, a third approval, success then failing CI and another publish, revise and publish, fresh evidence then publish, and post-publication evidence/revise/repeated publishes (46-64). There is no reviewer identity/set or authorization, revision number or stale revision, candidate digest/expected-base binding, branch-parent conflict, second bundle, submit, response value, request ID, memoized rejection, lost reply, blob/event preparation, allocator race, root CAS loss/retry, crash, restart, recovery, snapshot-reader interleaving, or progress property.

**Independent assertions are narrower than the represented rules.** Ledger asserts paired-head equality only after ePublish (37), after it has advanced both heads together within that handler (32-33). The independent Safety monitor asserts at most one eApplied notification for the single modeled bundle (68-73). This is more explicit once-only observation than A's current/published boolean relation, and would detect two emitted successful-application notifications. However the monitor does not assert that any publication occurs, that publication happens only after the correct evidence, that failed CI/revise cleared evidence, or that post-publication state is unchanged. Those rules are largely constructed by handler guards/assignments. For example, an erroneous early publication followed by suppression of all later publications can still satisfy both equality and at-most-once. No returned not_ready result is asserted after the failure/reset scenarios. DESIGN.md:53-61 explicitly calls the model an atomic-ledger abstraction and separates the Python storage refinement, which matches its granularity. Its broader wording that the model “checks” the guard/reset/failing-CI/post-publication rules should be read as rules encoded and exercised, not all independently asserted properties. Its full coverage/check-success report (57-59) was not rerun or independently verified here; coverage of branches would not by itself close these assertion gaps.

**Python implements an optimistic immutable event chain with a durable allocator.** C/solution.py:21-26 allocates unique event numbers using a CAS counter. `_snapshot` pins one root version, follows predecessor links (not numerical allocation order), reads any blobs, and replays the selected immutable chain (28-53). `_commit` allocates, durably writes bounded event/blob records, then CASes the root from the observed version (93-106). All mutating API methods retry from a snapshot if that CAS loses (108-174). Thus abandoned allocated numbers and orphan records need not be recovered/helped. With a unique allocation, each blob/event key has a single owner; a crash after allocation or data writes abandons it, while a crash after root CAS leaves its full event reachable. This is substantial storage concurrency logic entirely outside the P model.

**Semantic alignment and remaining limits:** the Python approve path checks authorized reviewer and current revision, and replay uses a set (81-84,133-142); revise increments revision and clears certification (74-80,120-131); CI checks revision/digest/publication then replaces its boolean (144-152). Publish checks its durable request memo before ordered stale/published/not_ready/conflict checks, and stores every outcome (154-174). Replay combines the memo, successful head changes, and publication marker (85-91). Submit replay preserves its original response separately (59-73,108-118). These executable semantics are much broader than the saved P model. Large event maps are split into 7,000-character canonical ASCII JSON chunks (11,17-19,93-103), avoiding A's complete-update-map pending record. Source inspection supports the root-CAS visibility architecture without proving its refinement.

The unbounded replay concern from B01 remains: every snapshot does at least one root read plus one read per committed event (28-53), and the design explicitly has no compaction (C/DESIGN.md:45-49). In B02 even duplicate authorized approvals append events (133-142), so arbitrarily many valid repeated approvals of one unpublished bundle can grow the chain without growing the bundle count. A history beyond 4,999 events forces more than 5,000 snapshot reads before any mutation's allocation/writes; chunked events increase this cost further. Consequently “hundreds of bundles” alone does not establish the stated quiescent call budget. This is a static bound observation, not an executed failure.

**Three-source comparison:** A is an atomic successful publish plus repeat; B01 adds competing same-parent producers and abstract reads; B02 adds a sequential logical-rule scenario and an independent once-only application monitor. None breaks the implementation's root-CAS protocol into interleavable storage steps. B02 changes the modeled dimensions rather than being a strict coverage superset of B01. All three Python implementations contain materially more concurrency/durability behavior than their saved models validate.

## Fourth frozen source: prethought-vcs-a02 (SOURCE-ONLY addendum)

D abbreviates `BASE/runs/prethought-vcs-a02/submission/`. Reviewed D/DESIGN.md, D/model.p, D/revision_model.p, and D/solution.py, and appended all four SHA-256 hashes to the existing JSON manifest. These four files are the complete submission directory inventory including hidden files; no standalone saved Python tests or runtime-test artifacts are available. No solver, service, or tests were executed. All four source-only reviews are now saved, without reading prompts, assignments, metadata, grades, transcripts, or private fixtures.

**This model separates competing initial reads from attempted commits.** D/model.p:20-53 creates two independent writer machines and a reader. Writers register, send read events, and await try notifications before sending their CAS events. Ledger will issue try notifications only after both reads have occurred (84-95). The initial rootVersion is zero and each CAS handler checks `rootVersion == 0` before incrementing it (75-82,105-123). This is a small but real abstraction of two stale-read contenders with only one allowed CAS success, unlike A01/B01/B02's complete publish API-event abstractions. No read event actually returns or records a version; zero is an implicit fixed expected version. Both writers are deliberately held at a read barrier before either attempt. Different CAS orderings can be explored, but a loser does nothing: it does not reread, recompute, record a conflict, or make progress on disjoint work.

**Independent observers improve the properties, with explicit abstraction limits.** Reader forwards one paired-head observation request and asserts on a torn reply (56-61); Ledger compares both heads in a single read handler (96-99). A separate Safety monitor counts commit notifications from either writer and rejects more than one, and also rejects torn replies (133-145). Both success handlers still set both heads and publication atomically inside one handler (105-123), with no immutable-event write, multi-read snapshot traversal, blob preparation, or partial persistence steps. The reader can observe before/after this atomic handler, never between the head assignments. Thus it tests an abstract root-version exclusion protocol and observer interface, not the Python storage refinement.

**Retry and durability properties are asymmetric and simplified.** If A wins, its handler sets replyMemoized=true and self-sends a retry event; the retry asserts memo, publication, both heads, and rootVersion==1 (105-114,125-130). This gives an explicit post-commit retry-state check beyond A01's repeated guarded publish event. There is no request identity, returned cached outcome, response-loss event, service restart, or independently executing retry client; the retry handler itself only asserts and does not attempt a second publish. B's success handler does not set replyMemoized and has no retry counterpart (116-123), so a B-winning run is not checked for durable outcome memoization. No rejection memo, submit retry, authorization, CI/digest guard, expected branch-parent comparison, or second evaluation after lost CAS is modeled. Since both writers advance the same boolean heads, they do not distinguish two bundles' update contents. At-most-one initial root-CAS winner must not be equated with the full same-parent rule that the other request eventually returns a durable conflict.

**The separate revision scenario independently checks reset and stale evidence, but is sequential.** D/revision_model.p initializes revision 1 with two approvals and passing CI (25-28). One sender queues revise, old approval, old CI, and check in that order (7-15). Revise increments revision and clears both pieces of evidence; old handlers only accept when revision==1 (36-45). The final explicit assertions require revision 2, zero approvals, and failing CI (47-51). These assertions independently expose retained evidence or acceptance of the simulated stale events, unlike merely executing the guarded assignment/reset. The external RevisionSafety monitor only checks that the final eChecked event occurs no more than once (55-61); the substantive evidence assertions are inside RevisionLedger. There are no concurrent stale/current calls, event payload revision numbers, current-revision evidence acceptance, digest matching, expected_revision stale revise, failing-CI-after-pass, publication interaction, or rejection outcomes. The fixed ordering ensures its old-evidence acceptance branches are unreachable, as the design acknowledges (DESIGN.md:35).

**Design claims and Python implementation:** D/DESIGN.md:31-35 describes the same-root race, reader, A-side retry and revision scenario, reports successful checks with incomplete coverage allowed, and explicitly excludes encoding/size from P. These reported runs were not independently verified. Its statement about store byte limits being verified by the Python runtime (35) means oversized values are rejected by the store, not that valid oversized input is accommodated. Python persists content-addressed immutable events with deterministic collision suffix probing (D/solution.py:23-36). Snapshot initialization installs a genesis event using a root CAS, and every read pins a root then replays only the immutable chain (38-103). `_transact` computes on a snapshot, writes an immutable event, CASes root, and reevaluates after a loss (105-116). Its loser retry/recomputation is more complete than the model's dropped losing attempt. Semantic paths implement original submit response caching (118-129), revision resets on replay (77-83), authorized distinct approvals (145-157,84-87), revision/digest checked CI replacement (159-170,88-89), and ordered publish memo/checks (172-198). Successful publish replay applies its memo, heads and publication together (90-100). Duplicate approvals and unchanged accepted CI can return without another event (153-154,166-167). As with the other implementations, meaningful executable protocol and rules exist beyond their model coverage.

**Static limitations:** every immutable event must fit one store record; `_put_immutable` writes the entire JSON object directly (23-30). Genesis includes all initial heads (43-45); submit/revise events include the complete update map (127,141). There is no chunking. DESIGN.md:39 acknowledges the individual-event limit and assumes test-scale updates fit. The public contract bounds neither string lengths nor total encoded update-map size, so valid large heads/updates can be rejected by the runtime rather than supported. This is a source-level limitation, not an observed executed failure. Full-chain replay also gives at least a root read plus one read per event, including genesis (41-60), so quiescent call cost eventually exceeds the stated 5,000-call budget; no compaction bounds it. Unlike B02, duplicate approvals/unchanged CI are suppressed, but sufficiently many real revisions or changes still grow the chain without increasing bundle count.

## Final four-source SOURCE-ONLY comparison

A01 represents one atomic publish and a repeat, B01 adds two competing API-event producers and read assertions, B02 expands sequential certification/reset scenarios and an independent at-most-once observer, and A02 adds separated initial-read/CAS attempts plus explicit post-revision stale-evidence assertions. A02 therefore has the clearest modeled stale-read exclusion protocol of these four, while still treating successful state/memo/head installation as one atomic handler and omitting the implementation's full persistence/refinement steps. Its losing CAS is not retried in the model; its retry check covers only A and does not execute the API retry logic. These are qualitative differences in modeled dimensions and assertion strength, not a numerical quality ordering. No source set supplies a saved standalone runtime test suite; each contains P test declarations, and prose execution reports remain unverified in this phase. The hash manifest now covers the three public sources plus all thirteen frozen submission sources (16 files total).
