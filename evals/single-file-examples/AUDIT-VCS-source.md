# Blinded VCS source audit

Scope: neutral frozen submissions V1 and V6 only so far; read Bundle.p, solution.py, DESIGN.md and V6/test_extra.py, plus shared public contract. No assignment map, prompts, transcripts, grades, report JSON or observation output was read. This is static source assessment; DESIGN execution claims are unverified until transcript review. Further cases will be appended before unblinding.

## V1

- Selected AtomicBundle monitor, independent head/version and committed-client set, hot completion after two clients with exactly one head advance (Bundle.p:7-39). Stronger than a bare trace, but eMemo overwrites expected result without checking prior equality (:25); it does not independently derive rejection outcomes. Actual eReply is observed, checked against the memo and requires a recorded effect for success (:26-32).
- Store atomically combines version/parent validation, update and memo (:49-65); clients start with fixed version/parent zero and never read a snapshot (:76-82). This is NOT a concrete read/candidate/CAS-loser/reload model. A failed version/parent guard is durably memoized rejection; a client's second attempt changes parent but reuses its machine identity and receives the same memo. It models business conflict replay, not the Python retry protocol.
- No revisions, evidence lifecycle, multiple branches, crash/restart or store record limits in P. DESIGN openly omits preparation/crash injection, but 'bounded branch maps and normal bundle payloads' is not the contract's full value-size obligation.
- Python stages immutable event then CASes one root (solution.py:55-60), rebuilds all state on CAS loss, retains original submit digest and all publish outcomes. Already-published fresh requests create an outcome-only event (:134-137,152-157), preserving newer heads; no obvious reapplication bug. Reads pin root and replay immutable history. Each whole event and initial-head map remains one record; valid large maps/strings can exceed 16KiB. Cold operations read all historical events (:29-46), with no bounded reconstruction/compaction. No saved custom tests or implementation-to-P capture source in submission.

## V6

- Concrete split snapshot / client candidate / versioned CAS / loser reload model for two competitors (Bundle.p:86-145), plus stable delayed retries only after both first calls finish (:164-165). Generated revisions, approval counts, CI, published flags and independent parent conflicts (:158-162); fixed ready, isolated second-parent conflict and rejected-then-certified retry scenarios (:170-237).
- Independent monitor computes outcomes from command/config history and checks actual state, memo and returned replies (:35-81). Four actual observations and replies/two distinct saved IDs required before cold completion. Ready config plus those independently checked outcomes forces useful success. Full Observed checks memo; alternative PublicObserved omits internal memo comparison for public capture, clearly a narrower observation interface. One request ID is conflated with one bundle ID in this bounded abstraction; no fresh publish ID against the same already-published bundle after a later head advance. No explicit crash/recovery action or evidence-revision protocol, disclosed as omissions in DESIGN.
- Python uses immutable, chunked, copy-on-write AVL tree exposed by a single versioned root (:119-128). CAS loss recomputes all guards. Chunking considers second JSON escaping, keeps original values for collision checking, and snapshots use immutable root paths. Already-published request only records memo (:193-195,211), so no reapplication defect visible. Tree/chunk mechanics are outside P and merit ordinary tests; no obvious API semantic defect from this review.
- Seven saved Python tests cover isolated authorization/stale/digest/evidence guards, guard priority and aliasing, concurrent publishers/evidence, publish crash at each actual write, growth/large escaped Unicode, and two real serial public-result replay histories (test_extra.py:20-146). Uses check_events with selected Contract, strict and hot completion. Sequential capture explicitly avoids response-order linearization claims; separate concurrency tests do not invent P commit order. Rejected trace asserts actual result before encoding constant2, so the P adapter is narrow but ordinary test still catches a wrong result. Ready/conflict and rejected-after-certification replay are genuine temporal cases. No execution outcomes assumed from static source.

## Provisional distinction

V6 contains materially more discriminating generated/concurrent and delayed-retry modeling, independent actual-state/reply checks, useful completion and saved actual-capture tests than V1. This is an artifact distinction, not an attribution to a condition or model. Both Python designs use joint root publication; only V6 source includes bounded record chunking and indexed lookup.

## V2

- Selected independent BundleContract, hot completion, counts five observations/four IDs, exactly one publication, retains original not_ready rejection after readiness, and fresh published-request success (bundle_model.p:10-52). Expectations partly derive from returned result, but the fixed scenario's aggregate constraints force one useful success and one conflict. Driver selects one of two send orders from a single machine (:106-113), rather than independent clients exploring read/CAS interleavings. Service whole-operation handlers are atomic (:67-88), so no load/candidate/CAS loser/reload. This omission is explicitly disclosed in DESIGN.
- Monitor observes eObserved audit, not actual eReply; Driver checks some reply values and IDs but not all (:104,114-135). A corrupted losing competitor's result can evade the independent monitor if the winner's response still selects the correct fresh-request target. It covers readiness-change rejection replay, not a published bundle retried after another bundle subsequently advances the head. No explicit crash, evidence revision/digest or multi-branch protocol in P.
- Python prepares chunked JSON values plus compressed immutable radix-trie paths and publishes all logical changes through one root CAS (solution.py:26-134). Losers reload/recompute, snapshots pin root, original submit memo is separate, already-published fresh request records outcome only (:218-220), no reapplication visible. 6000 ASCII-character chunks leave room for second JSON escaping. SHA content and logical-key collision resistance assumed, documented, rather than checking full keys/content. No saved custom Python tests or actual Python-to-P capture source. DESIGN's stress/runtime-test claims need transcript confirmation; no execution assumed here.

## V3

- Three clients generate seven operation kinds over seven rounds each; separate root reads, candidate construction and version-CAS loser reload (model.p:75-127). Includes revision/evidence clearing, independent approval bits, CI true/false, publish guards, conflicting head movement and successful-call repetition as response-loss abstraction. Actual restart/volatile-state loss is not modeled. Per-client publish request ID is reused across rounds while targetRevision is resampled (:79-80), broader than the contract's same-arguments retry domain.
- Assertions live inside Root (:19-50), not a selected spec. They independently compare old/new version, head equality, prerequisite evidence/parents on first publication, evidence clearing, retained memo entries and joint publication memo. These are meaningful transition invariants, but no independent full public-result oracle, no checked public replies, no actual progress/completion or useful-success obligation. With random operations, permitted safety coverage need not imply a publication or each lifecycle witness. No model assertion that a memo's fresh result is the correct stale/not_ready/conflict outcome.
- Python exact-key prefix-free Patricia trie with chunked key/value blob trees, staged reachable writes, unique IDs allocated in one CAS range, one root CAS for joint visibility (solution.py:16-185). Unreachable preparation is invisible; CAS losers recompute. No digest-collision assumption for lookup. Pages use base64 of <=9000rawbytes, fitting actual JSON record limits. Already-published fresh requests memoize only (:257-258,275), retaining newer heads. No obvious required API bug statically; path shape/payload affects costs, disclosed.
- Four saved test methods cover 12 competing publishers, crash each successful publish write, growth/64branches/largeUnicode, several lifecycle/evidence/alias guards (test_additional.py:9-104). Tests inspect/copy private Store records only for fixture setup, not application synchronization. No Python-to-P capture/replay source. DESIGN self-reveals chosen compatibility CLI in its command; assignment map and all external results remain withheld, so this audit is source-first rather than guaranteed condition-blind.

## V4

- Three clients, split snapshots/candidate/CAS-loser reread, eight operation rounds with directed approval/CI/publish prefix then random revisions/reviewers/CI/digest-validity/parents/IDs (BundleModel.p:91-151). Preparation aborts and repeated successful commands abstract crashes/lost replies, but no actual restart-state machine. Preparation may abort all directed operations, so prefix alone does not require useful success. No hot/count completion or public-result observations.
- Root asserts candidate equals Apply(current,command) (:64-66), but the SAME Apply function constructs candidate (:130); it is not an independent sequential oracle. Additional separately written transition invariants are meaningful: same old snapshot, untorn heads, preserved memos, publication evidence/parents/memo, evidence clearing (:64-82). Shared Apply defects can survive the equality check. No selected spec; assertions live in implementation Root. One-bundle model cannot exercise old published bundle after another bundle advances heads.
- Python immutable heads blob plus compressed hash-trie directories, exact key buckets, bounded-size chunk/join storage and durable unique writer tickets; one root CAS exposes heads/bundle/memo together (solution.py:23-52,78-124,126-206). CAS losers rebuild from fresh snapshot. All API guards and memo ordering visible, already-published creates no head write. No obvious required API violation statically; paging and trie are outside P.
- Four saved ordinary Python tests: crash every publication write, 12 conflicting publishers/ID namespaces, growth/restart/Unicode chunking, and evidence/revision/guard/alias semantics (test_extra.py:17-94). No real Python-to-P observation path. DESIGN explicitly reveals compat command, so source-first/no hidden results, not full condition blinding.

## V5

- Selected independent Contract derives result/state from initialized bundle definitions + command history; checks actual heads/flags and actual returned response by saved request ID, hot completion requires four observations/four replies/two IDs (Commit.p:19-48). Concrete separate load/client candidate/CAS loss/reload (:51-103), replay reads actual current memo/state. Test-only three-attempt bound disclosed separately from implementation retry policy.
- Generated b0 revision/readiness/published/parent classes with a guaranteed ready b1, two independent clients, delayed replay barrier (:105-122); isolated second-parent conflict (:125-142); rejected publish before another bundle makes its parent current followed by old-request replay (:145-162). These are meaningful competing/temporal witnesses, not just immediate duplicate calls. Whole evidence lifecycle/crash recovery and fresh request against an old published bundle after later head advancement remain outside P. Model uses one publish ID per bundle; two-target heads are abstract integers.
- Python stages chunked, base64-encoded values and compressed immutable hash-trie paths, single root CAS with guard recomputation, snapshot reads, separate namespaces/original submit digest, correct already-published no-head-write branch (solution.py:120-233). SHA content/index collision resistance explicitly assumed; no obvious required semantic API violation statically. Payload chunking and indexed access avoid the V1 single-value/history-scan limits.
- Six saved Python tests: isolated guards/lifecycle/original submit/aliasing, eight publisher-contention schedules with concurrent untorn readers, crash offsets1..34 (not dynamically derived exhaustive write count), growth/64branches/large escaped payload, rejected-conflict retry after parents become current then fresh-ID success, and actual public-call check_spec/emit with strict and hot completion (test_additional.py:17-138). Real serial snapshots/results drive the same P monitor; no invented internal commits or concurrent append-order linearization claim. DESIGN honestly distinguishes incomplete broad search and bounded mutation evidence, but execution claims await transcript/grade review.
