## b01

**Concrete empty-take memo defect.** `solution.py:43-45` uses `previous = record["takes"].get(request_id)` and treats only non-None as a memo hit. Fresh empty takes store None (`46-48`). Consequently an empty take followed by a successful fresh put and then retry of the original take takes the later item, violating `public/TASK.md:16-17`. This is a direct source deduction; no probe was run. DESIGN.md:3 claims that retries inspect None-containing tables before changing the queue, but the implementation cannot distinguish that stored result from absence. Constructor and put otherwise use load/CAS loops, Store-owned capacity/memos, and distinct namespaces (`solution.py:5-36`). The found integer case, including zero, is handled by `is not None`; only the empty memo case is lost. Snapshot returns the list from the Store's deep-copy load (`51-52`), so it does not expose the live stored list.

**P model and oracle.** `AtomicStore` explicitly supplies separate load and version-conditional replacement handlers (`model.p:12-16`). Each client carries version and candidate fields and, on failed CAS, reloads and rebuilds (`30-39`). Two distinct clients/IDs/items race one put each (`44-46`). This is a real bounded stale-read/CAS conflict model. However the record has only count/first/second, no result tables, and the workload has no retry by request identity, takes, snapshots, or full rejection: two puts into capacity two both fit. Thus it cannot expose the Python empty-take defect or check memo atomicity. The selected QueueContract (`tests.p:1`) has an independent expected capacity/FIFO/memo/snapshot state (`monitor.p:7-16`). Its checks for takes/retries/snapshots are not exercised by P clients, which emit only ePut (`model.p:38`). Announcements occur at client receipt of successful CAS reply, not in Store's commit handler (`15-16`, `38`); the two clients can announce in a different order from commits. For this put-only workload with no snapshot/take, either order yields two accepted puts, so the monitor cannot compare its FIFO order with actual Store contents. A later FIFO observation would need commit-order instrumentation or a linearization argument.

**Capture and witnesses.** Python explicitly selects QueueContract via check_spec and emits values obtained from actual serial public calls (`test_observation.py:9-25`), then checks counts (`38-39`). Accepted-put, found-take, and empty-take retries are immediate (`27-36`). The rejected put is never retried, and the empty retry occurs while still empty; this leaves the source defect unwitnessed. The second test checks shared instances/capacity one (`41-49`). No Python contention test is submitted. DESIGN.md:5 accurately limits P to two puts, but its broader mention of monitor coverage describes handlers rather than exercised P paths. Client Done states are cold, and no global completion/useful-success assertion ensures all work finished.

## Cross-source distinctions

All Python implementations place state in the supplied Store and use CAS loops, but b01's empty memo lookup is a concrete semantic exception. a01/c01/c02 distinguish empty memo membership from absent entry. All use stable operation identity within the required string-ID/same-argument domain; their changed-argument handling differs without changing that required domain.

The P artifacts exercise different evidence: a01 has a whole-operation assertion machine with an unselected/unreplayed separate monitor; b01 has split load/candidate/CAS retry but only fresh puts and potentially reordered client-side announcements; c01 has full-record load/CAS types but no failed-CAS retry or public announcements; c02 has a selected active public oracle and commit-handler ordering but abstracts away split load/CAS. None supplies an explicit global useful-success/completion property. None's P scope establishes arbitrary capacity or unbounded correctness. Actual serial Python result capture exists in all four, with direct selected monitor invocation only in b01/c02. Meaningful explicit delayed retries differ by outcome: a01 covers empty take after later put; c01 covers rejected put after removal and found take after later put; b01/c02's saved Python retries are immediate. These are concrete source differences, not a quality ordering.

## a02 (fifth authorized frozen source)

**Python source.** Initialization uses CAS and every load checks the configured capacity against Store record (`solution.py:17-33`). Put and take use load/private-copy transformation/CAS loops (`38-51`, `56-65`). Store.load already deep-copies candidates. Put tuple memos retain item and Boolean; take membership plus `(found,item)` retains empty results (`40-49`, `58-63`). Same-string-ID retries return memoized outcomes, separate namespaces remain Store-owned, and changed put arguments raise (`35-45`). Snapshot is a load and copied FIFO (`67-69`). The constructor checks integer/positive capacity (`8`); unlike b01/c01 it does not explicitly exclude bool, an input-validation distinction outside normal positive integer capacities.

**P model and selected oracle.** The model gives the Store a version and whole queue/memo record, separate load handler, and version-conditional publication handler (`model.p:6-40`). Clients receive copied record fields, build private candidates, send CAS, and keep loading/recomputing until CAS succeeds or a stable identity memo is found (`87-119`). Two clients use one shared Store (`126-133`). Memo and FIFO changes publish together (`26-38`). Stable string request IDs persist across phases, including accepted-put replay after a take and take replay after another operation (`76-84`). The selected QueueContract (`tests.p:1`) independently derives expected capacity, FIFO and retry outcomes from its own sequence/memos (`monitor.p:8-37`). Public observations occur at successful Store publication or Store load of an existing memo (`model.p:15-20`, `34-37`), so they have a justified single-Store order rather than client reply arrival order. The public result fields for fresh calls are read from the submitted candidate's memos, allowing the separate monitor to challenge candidate behavior.

This is a split load/candidate/CAS retry model for both operations, not merely an atomic queue service. Its fixed phases do include delayed identity replays (`71-84`); for example client 1's p1 can be rejected when client 0 fills the queue, client 1's t1 then removes an item, and p1 is replayed at phase 2, so a rejected-put-after-removal path is present. This is a source-feasible path, not an executed witness. There is no explicit coverage assertion showing it was reached, no success-count assertion, no completion event/hot-state property, and snapshot is omitted from the monitor/workload. Bounds are accurately stated in DESIGN.md:9-11; capacity is implicitly fixed at two (`model.p:104`), rather than a modeled record field despite DESIGN.md:9's wording. Fresh initialization and mismatched capacities are not P-modeled. No fairness result is established by the cold-state safety monitor.

**Actual capture and witnesses.** Wrappers append actual serial public results (`test_observation.py:15-33`) and explicitly call check_events for QueueContract (`57-64`). Events use flattened event dictionaries, unlike the nested payload representation of b01/c02; checker-format acceptance was not inspected or executed. Only put/take observations are sent, matching the monitor's observes set; snapshots are actual public calls asserted separately throughout (`35-55`). Two instances share the Store. The test explicitly retries an empty take after a later successful put and verifies `[40]` remains (`50-55`). Rejected-put and found-take retries in this Python history are immediate relative to queue mutation (`39-47`); no accepted-put retry is in the Python history. Capacity three, zero rejection, and mismatched instance capacity are tested separately (`66-79`). No Python contention test is present. DESIGN.md:11 clearly distinguishes P put/take checks from Python snapshot assertions, although its phrase “after each serial call” is broader than the actual assertions around the final group (`52-55`).

## b02 (sixth authorized frozen source)

**Python source.** Unlike the other constructors, this constructor only saves Store/capacity and validates positivity; initialization is lazy (`solution.py:7-23`). First fresh put/take/snapshot constructs an initial record and publishes through CAS (`33-38`, `46-55`). Contending callers reload and recompute. Empty-take memoization uses membership (`43-44`) and preserves None. Put tuple memo lookup preserves false results (`28-31`). IDs/memos are in separate Store maps; the required same-string-ID/same-item case is supported, although changed arguments and non-string IDs are not rejected. Capacity belongs to the first published record; subsequent instances use that record's capacity in puts (`33`) without checking their configured capacity. DESIGN.md:3-7 describes Store-owned capacity, but this source does not enforce the same configured capacity across instances. The contract assumes all instances sharing a Store use the same capacity, so this mismatch behavior is distinguished from the required same-capacity domain, rather than labeled a definite contract failure. Snapshot CAS-publishes an unchanged record and increments Store version (`51-55`), so it has a successful CAS linearization point but also causes contention. DESIGN.md:12-13's “atomic read pattern” understates that write/CAS behavior.

**P model and monitor selection.** QueueStore contains whole queue-operation handlers, no version/load/candidate/CAS failure (`model.p:17-35`); two clients send bounded request sequences to it (`39-55`). Both submit accepted-put/found-take immediate retries, two fresh put IDs each, and one extra A take (`44-49`). The name A-empty does not guarantee an empty outcome because other client order affects contents. There is no explicit retry of that extra take, no delayed rejected-put retry, no snapshot, no reply protocol, and no useful-success/completion assertion. Public-result-shaped events are raised locally and explicitly ignored by QueueStore (`14-15`, `23`, `35`), rather than announced as in a02/c02. Regardless of any tool-specific raised-event observation rules, `tests.p:1-2` selects no QueueContract. There are no assertions in the queue/client machines. Thus this submitted P test has no FIFO/capacity/memo oracle selected; it principally exercises event handling/interleavings. The standalone QueueContract independently derives acceptance/FIFO/memo/snapshot expectations (`monitor.p:17-46`) but closely shares the model's slot-map representation. DESIGN.md:17-20 describes the coarse serialization abstraction; it omits failed-CAS/stale-candidate limitations and does not distinguish the monitor's external selection from the P test.

**Actual capture and witnesses.** Actual serial public results are encoded as nested payload events (`test_observation.py:17-45`), written to a temporary JSONL log, and passed to `snappea observe ... --spec QueueContract --strict` with the process return code asserted (`58-70`). This is a concrete selected observation replay path, and explains `monitor.p:1`'s external-observation comment; it is not a P-test selection. Serial capture covers immediate accepted-put and found-take retries, one rejected put, empty take, and snapshots (`47-56`). A separate direct-Python test retries an empty take after a later successful put and checks the item remains (`90-100`); its other retry is immediate. Rejected put is not retried after space opens and accepted put is not retried after intervening removal. Separate tests cover shared state/capacity three and ID namespaces (`72-88`). ThreadPoolExecutor cases assert exactly capacity five accepted fresh puts, same-ID concurrent put results with one effect, and distinct takes returning all three seeded items exactly once (`102-124`). They do not force a stale-read/CAS collision or capture concurrent events for monitor replay, and therefore make no append-order linearization error. No output/result was executed during this audit.
