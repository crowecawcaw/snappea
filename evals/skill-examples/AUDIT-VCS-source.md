## a01

### Python storage, temporal behavior, and limits

solution.py:18-60 implements content-addressed 16-nibble tries, keeping full logical keys in collision buckets; :62-81 lazily initializes heads and commits all modified map roots by one root CAS. :83-96 stores original submit responses separately. :98-137 implements revision, approval, CI lifecycle and avoids committing unchanged accepted evidence (although it still stages trie nodes before deciding changed=False). :139-170 checks durable publish memo first and stores all rejection outcomes; only the fresh successful branch at :162-167 changes heads/published flag. An already-published fresh request records only an outcome, so does not reapply old heads. :172-184 pin snapshot and normalize reads.

The root CAS is a concrete joint boundary for all head paths, bundle status, and memo, and unsuccessful CAS attempts loop through a new snapshot. Read-only/no-change operations can linearize at the captured root read. Preparation crashes leave unreachable trie paths; post-root crashes leave durable original responses/outcomes. Fixed trie depth avoids replaying historical operations. For ordinary bounded records and 64 target branches, the path count is compatible with 5,000 calls in quiescence (each fully populated path is 17 reads plus 17 immutable CAS preparations; successful publish includes 64 head lookups and replacements, bundle and outcome paths). This is a source-level bound, not a measured test.

Record-size qualification: each leaf embeds the complete logical value (:51-53), so an individual bundle/update map, ID, head string, or collision bucket can exceed 16,384 bytes even without large history. Full keys prevent semantic hash-prefix aliasing but do not bound bucket size. DESIGN.md:43-49 acknowledges pathological buckets and model/layout omissions, but not all oversized individual-value cases. No explicit chunking exists.

### Actual P model and independent oracle

design.p:6-24 has a separate monitor with head and seen-request state. It independently checks effect request uniqueness, predecessor consistency, unit head advancement, and repeated result agreement for requests already seen. Store :31-42 serializes eTry and updates abstract head/memo together; Main :54-65 starts three single-shot clients, including a duplicate request. This permits competing event ordering but does not separate a client read from a CAS, and no client retries a CAS rejection. eRestart is declared (:4) but unused; there are no crashes/lost replies, initialization, storage bounds, multi-branch reads, bundle lifecycle/evidence, or rejection memo replay. A failed expected-head attempt returns 0 without memoizing (:40-42), so the abstract rejected operation is not the actual durable publish rejection protocol. The monitor's seen state only contains successful effects and has no independent rejection-history oracle.

DESIGN.md:5-12 accurately limits scope to abstract publication/outcome boundary, but 'two publishers reading' overstates the actual model: clients receive fixed expected values, not snapshots. :9-10 claims 595 schedules and coverage, and :52-55 claims public tests plus 64-branch and crash checks; none has saved supporting capture/test source in this submission. The source's independent monitor is useful for its narrow abstract transition but does not establish concrete trie/CAS retry correctness or full API semantics.

## b01

### Concrete lifecycle defect derived from source

solution.py:158-175 returns outcome='published' for a fresh request against an already-published bundle (:165-166) and appends the same publish event shape used for first success. During replay, _apply at :75-81 applies every event whose outcome is 'published', unconditionally rewriting all of that bundle's heads. There is no 'apply' distinction or already-published guard in replay. Static witness: publish A from h0 to h1; publish B from h1 to h2; publish A again with a fresh request ID and current revision. The last call must return published without effects under TASK.md:39, but its event replays A's updates and rewinds the head to h1. Reusing A's original request ID avoids the defect because memo lookup returns without a new event (:160-161). This is a temporal already-published lifecycle omission, separate from atomicity of the pointer swap. It also undermines DESIGN.md:9 and :13-15's implication that publish replay preserves the specified lifecycle: joint visibility is present, but the replayed effect is wrong.

### Other Python boundaries and progress

solution.py:26-46 reads one root and replays the immutable chain; :83-98 stages an event then CASes root and recomputes on loss. Genesis is staged before root installation. All other API guards and original submit digest storage (:100-156) match their stated order/lifecycle. Root CAS atomically exposes event/memo/effects, including rejected outcomes. Lost post-CAS responses are recoverable via the chain.

Each entire event is stored as one value (:85-87), and genesis embeds all initial heads (:31-33); no splitting exists. History is not one growing record, but an oversized individual update map or strings can still fail CAS size checking. Every operation rereads every committed event (:37-45); with N events, an initialized read requires N+2 reads, and mutation adds two CAS calls. There is no compaction or hard bounded-history argument, so sufficiently long valid history violates the 5,000-call bound. DESIGN.md:31 acknowledges growth/no compaction but asserts the stated hundreds-of-bundles workload stays within budget without a bound on revisions, evidence toggles, and fresh publish requests per bundle.

### Actual P model and oracle

Bundle.p:33-61 models separate snapshot read and conditional version commit, and Publisher :79-102 recomputes after stale-version feedback. Two independent publishers target two jointly assigned heads from base zero. AtomicBundleContract :9-31 observes replies and checks non-torn x/y and success-head identity; a hot state transitions cold after both IDs reply. It does not track memo consistency independently: replies is overwritten without equality comparison (:24), published set is never used for an assertion (:19), and Complete ignores later replies (:28-30). There is no caller replay request, lost-response/restart path, lifecycle, approvals, CI, revision, storage layer, or a third operation that could expose the Python reapplication defect. Store memo checking occurs only after expected-version equality (:44-46), unlike the Python public memo-first protocol, though stale retries can eventually reach memo. Progress is only the bounded two-reply hot-state condition, not Python history recovery.

DESIGN.md:19 describes the narrow snapshot/CAS abstraction accurately. :21-27 claims 129 schedules and openly reports uncovered replay and stale-retry branches; no captured output is saved. The code contains a retry branch, but the claim itself says the cited check did not cover it. No saved Python checks accompany this source.

## a02

### Python storage-size defect derived from source

solution.py:80-85 splits the already JSON-encoded event into 12,000-character pieces and stores each piece as {'data': piece}. The actual store value JSON-encodes that string again (runtime.py:35-37). An event text rich in escaped backslashes or quotes can expand toward twice its character count at this second encoding, so a 12,000-character chunk can exceed 16,384 encoded bytes. For example, an otherwise valid long commit string containing many backslashes causes the inner JSON text to contain repeated backslashes and the outer {'data': ...} encoding escapes them again. There is no validation/adaptive resplitting. Therefore DESIGN.md:7-10's unconditional 'below its 16 KiB limit, including ... large ... maps' claim is not established and is contradicted by the encoding path. This is a static size argument; no test was run.

### Other Python boundaries and progress

_snapshot :22-74 pins one root, reads immutable links plus body chunks, and replays state from supplied initial heads. _commit :76-96 prepares all body chunks, then link, then root CAS. Existing immutable content is checked for exact equality (:86-95). Root CAS exposes complete staged payload plus memo/effects jointly, and every API retries against a new snapshot after CAS loss. :152-178 preserves memo-first, priority checks, and explicit applied/head fields; replay :68-73 avoids old-bundle reapplication. Revision/evidence semantics, submit original-response map, separate ID namespaces, and output copies are visible in :43-67,:98-150,:184-194.

Progress cost is at least two reads per historical one-chunk event (one link plus one blob, :26-32), plus the root read; a one-chunk mutation adds chunk/link/root CAS. Therefore 2,500 ordinary one-chunk committed events imply at least 5,001 snapshot calls before any mutation work. 'Hundreds of bundles' does not bound events per bundle: a sequential workload with 500 bundles and submit+two approvals+CI+publish yields 2,500 events. The next read/operation already crosses the stated budget, with no contention or failures; no compaction exists. This directly qualifies DESIGN.md:50-53's assertion that stated workloads fit the per-operation budget. Large event chunks add still more reads. This is derived operation counting, not an executed workload.

### Actual P model and oracle

bundle_model.p:4-24 stores one abstract head and a count. Two fixed drivers send 1 then 2, or 2 then 1 (:26-51); each driver sends to one StoreModel, whose handler atomically permits a change only at head==0 and then asserts published<=1. There is no independent monitor/oracle: the implementation under test maintains both the gating head and the assertion count in one handler. The two tests explore both chosen delivery orders, but no separately captured reads, stale versions, CAS failure/recomputation, crash/lost response, durable memo/rejection, revision/evidence, multi-branch atomicity, chunk encoding, or progress. The source models a serialized single-head gate, not the multi-record preparation or temporal API contract.

DESIGN.md:46-49 clearly calls the CAS serialization step an abstraction and disclaims JSON/all response rules. Claimed check success has no saved output. The claim does not validate the chunk-byte assumption or replay-call budget. No implementation-test source/capture is submitted.

## b02

### Concrete quiescent-progress defect

solution.py:135-149 reads a payload chunk into stored_chunk (:139). If absent, it CASes the chunk. On successful CAS (:141), it does not assign stored_chunk=chunk_value or reread the new value. The old stored_chunk therefore remains None. The following comparison (:143) fails, sets chunks_ready=False, and CASes the root to skip this slot while preserving the committed tail (:147-149). A new uncontended operation starts with absent slot/chunk records, stages its first chunk, skips its own slot, and repeats at the next fresh slot forever. Even the first submit cannot finish in quiescence. The write is durable, but the local variable is stale. This conclusion follows directly from the local dataflow and store absent-read semantics (TASK.md:60); no behavioral probe was run. A concurrent/restarting caller that encounters an already-staged matching chunk can potentially avoid that exact absent-chunk branch, but that does not satisfy the required failure-free uncontended progress. DESIGN.md:19-25,:36-40,:61-67 describes eventual retry/progress without acknowledging this path, so its completed-operation claims exceed the actual source.

### Additional storage and algorithm boundaries

solution.py:110-130 reserves numeric immutable slots and uses separate root slot counter and committed tail to skip abandoned reservations. Matching records can be reused; different records cause a root update that preserves logical state. Payload chunks are installed after reservation; only a root CAS moving the committed tail exposes the event (:151-155). _snapshot :35-61 follows only the tail chain, checks payload checksums, and ignores skipped slots. The root captures a consistent logical snapshot; losing root writers recompute. The staged slot record contains prior tail, chunk count and checksum (:114-115), rather than the entire operation.

Chunks split canonical ASCII JSON into 12,000-character pieces (:112-113), then store them as {'data': piece} (:138). As with a02, outer JSON escaping can expand these strings beyond 16,384 encoded bytes; no byte-aware/adaptive split is implemented. This is an additional independent static concern even if the stored_chunk progress bug were corrected. DESIGN.md:64-65 says each slot stores an event directly and limits individual event size, but the actual source is a slot header plus separately chunked event payload (:114-115,:136-142). Thus this prose is stale with respect to concrete representation.

If an event commits, _apply :88-94 uses explicit apply to avoid repeated published-bundle effects; publish :216-239 implements correct memo/check precedence and apply=False on already-published responses. Submit retains original digest (:158-172), revisions/evidence lifecycle is explicit (:174-214), and reads/status are copied and normalized (:243-257). These semantic paths do not remedy the inability to reach committed events in ordinary quiescent startup. Whole-chain replay requires at least one slot and one blob read per committed one-chunk event (:43-56), so its recovery budget also grows as 2N+1; 2,500 such committed events exceed 5,000 calls, apart from the immediate progress defect. No compaction exists.
