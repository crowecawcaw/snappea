# Baseline artifact audit: skill-base-01..03

Scope: frozen `submission/`, `tool-transcript.jsonl`, and run `metadata.json`/`prompt.txt` only. This is an artifact and process audit, not an implementation-grade report. The common prompt is the baseline prompt (“Use P/Snappea to model the design, then implement it in Python”; deliver `solution.py` and `DESIGN.md`). Metadata records all three as baseline, with common public input hashes and `public_files_unchanged: true`. No transcript records reading `/opt/p-modeling/SKILL.md` or a skill guide/example; these are baseline runs without a skill snapshot. None of the submissions contains a retained runnable custom Python test or observation helper.

## skill-base-01

**Artifacts and access.** The frozen deliverables are `model.p`, `solution.py`, and `DESIGN.md`. The transcript shows reading the task, contract, runtime, and public tests (calls 1 and 3), then authoring/checking a model (calls 9–17); it records no skill entry-point, guide, or example reads. The saved model is an executable state-owning P machine: `State` tracks `head`, `published`, and `memo`, and `Main` sends `Publish` twice (`model.p:3-36`). The final check searched five schedules; it reported 13/13 statements, 2/2 branches, and 2/2 conditions covered, but explicitly skipped mutation and bypassed the coverage gate (`tool-transcript.jsonl`, calls 17 and 23). This is substantive bounded checking of a tiny abstract transition, though not of the implementation protocol.

**Model fidelity and independence.** The model captures the desired all-at-once publish tuple and a repeated request (`model.p:17-25, 32-36`). It omits actual reads/CAS, concurrent writers, expected-head conflicts, revision/approval/CI changes, rejection-order outcomes, initialization, crash positions, and persistent representation. The two publishes are sequential events; there is no dropped response, intervening operation, or independently scheduled observer. Assertions are made by the state-owning machine itself, not by an independent history-derived oracle. Thus the model demonstrates only that this one transition updates its own three scalar variables together. `DESIGN.md:53-59` correctly calls it an abstract publish transition, but its “retry after a lost response” characterization is stronger than the model’s scenario.

**Implementation and source correspondence.** The implementation uses an immutable radix trie behind one root key; each update reads a root snapshot and CASes it (`solution.py:40-112`). Publish checks a request memo, verifies readiness and all expected heads against that snapshot, then installs heads, bundle state, and memo through one root CAS (`194-238`). Those source boundaries correspond to the atomicity story at `DESIGN.md:21-34`; the P model does not exercise them. It models no record-level storage calls or interleaving. The Python implementation has substantive expected-head conflict handling and durable result memoization, but no saved test in the submission distinguishes its behavior from a defective implementation.

**Observed checks and limits.** Public tests passed in the transcript (`tool-transcript.jsonl`, calls 20 and 23: four tests). An inline helper asserted 64 initial heads and published a 64-branch bundle, then reported 6,658 store events for the initial read and 9,814 for the publish (`call 21`). These exceed the design’s stated 5,000-call bound (`DESIGN.md:44-48`); no retained test covers this, and the helper only prints counts. Another inline helper exercised crashes at configured write positions around submit and publish and printed “crash recovery passed” (`call 22`). The publish crash is injected at the next write, before evidence of the root CAS; it does not establish recovery from a committed CAS with a lost response. These are useful actual-source probes, but they are ephemeral and check only the printed/asserted outcomes. No observation helper captures emitted storage events or compares them against an independent monitor.

## skill-base-02

**Artifacts and access.** The frozen deliverables are `certified_bundles.p`, `solution.py`, and `DESIGN.md`. The transcript records task/runtime/public-test reads (calls 1–3), but no skill entry-point, guide, or example reads. The saved P file contains an executable state-owning `BundleModel` and a spec called `BundleSafety` (`certified_bundles.p:1-31`). The final attempted check without the coverage bypass runs one schedule, covers 11/11 statements, only 1/2 branches and 5/10 conditions, reports an unhandled monitor event, skips mutation, and exits 1 on the coverage gate (call 22). The next check passes only with `--allow-incomplete-coverage` (call 23). The monitor’s permissive behavior and the no-model-machine finding were explicitly suppressed during iteration (transcript calls 20–22).

**Model fidelity and independence.** Initial state hard-codes ready-to-publish conditions (`approvals=2`, `ci=true`, `head=0`), and one `EPublish` transition atomically sets head, published, and memo (`certified_bundles.p:8-19`). The final assertion `!(published && head == 0)` is within that same transition. `BundleSafety` has an empty event handler (`23-28`) and its permissive-monitor lint is suppressed; the test binds the spec to the implementation machine (`30-31`), not to a separate oracle/history. The single explored schedule cannot cover rejection paths, conflicts, retry after response loss, revision evidence invalidation, crashes, or contention. No independent monitor derives expected results from a contract/history. The source design itself acknowledges it models only successful publish and not the treap/API outcomes (`DESIGN.md:17-25`).

**Implementation and source correspondence.** The implementation uses a deterministic content-addressed treap and one root CAS (`solution.py:26-87`). Submit commits bundle plus submit memo together (`89-108`); revision resets approvals and CI (`110-129`); publish checks memo and rejection order, tests expected heads, and commits all heads plus published bundle and memo atomically (`159-195`). These real boundaries broadly match `DESIGN.md:5-15`, but no model action represents individual reads/writes or CAS retries, so the model cannot expose an incorrect primitive boundary. The transcript has four passing public tests (`call 24` output), but no retained custom tests, source-event observation, crash injection, or concurrency probe in the frozen submission.

**Feedback.** The saved check command disables mutation. During model authoring, lint failures (tautological assertion, missing implementation machine, permissive monitor) led to suppressions rather than to a scenario/monitor that observes implementation-like transitions (transcript calls 20–22). The final accepted run bypassed incomplete coverage; the specific missing false branch/condition and never-handled monitor event are listed in its output. This is useful syntax/lint feedback, but not substantive feedback on API behavior or the implementation.

## skill-base-03

**Artifacts and access.** The frozen deliverables are only `solution.py` and `DESIGN.md`; there is no P source in the submission. The transcript reads the task/contract/runtime/public tests (calls 1–3) but records no skill entry-point, guide, or example reads. The transcript does show a temporary `BundleModel.p` being authored and linted, then changed to add `EObserve` and an assertion over allowed scalar tuples (calls 11 and 13). `snappea tests BundleModel.p` returned an empty test-case list and `snappea check lint` returned no lint findings (call 13); no `snappea check` model execution is recorded, and the model was not retained. Consequently there is no reproducible frozen model result or schedule/coverage evidence.

**Model fidelity and independence.** The final transcript model contains one `ECommit` transition that sets `heads`, `published`, and `memo` together, plus an `EObserve` handler asserting the tuple is either all old or all new (call 13 command). However, with a single atomic model transition and no test case, the assertion does not exercise partial visibility or interleavings. The monitor is in the same machine as the state it inspects, and no independent scenario schedules observations around actual storage operations. No crash, lost-response, conflict, version, or competing-writer scenarios are modeled. `DESIGN.md:12-16, 56-95` describes the root-pointer abstraction and mentions the observer, while correctly noting the CAS protocol remains implemented in Python; the frozen artifact omits the actual P file and any check command result.

**Implementation and source correspondence.** The implementation keeps one versioned root pointing to four immutable tries and uses content-addressed nodes (`solution.py:8-42, 138-162`). It has expected-value checked head updates for publish (`81-120, 234-271`), and commits all changed trie roots at one root CAS; reads capture one root before following immutable nodes (`273-290`). Submit memo, revision evidence reset, memo-first publish validation, and atomic publish writes are implemented in source (`164-271`). The design’s intended model/implementation boundary is plausible, but the absent frozen P artifact and absence of P execution mean correspondence is asserted, not demonstrated.

**Observed checks and limits.** Public tests passed during implementation (the command transcript records these at calls 4–6). An inline actual-source 64-branch publish helper reported `published` and 4,861 store calls (`tool-transcript.jsonl`, call 15), an improvement over base-01’s measured operation but with no retained regression check. There is no saved Python test or observation helper in the submission. The temporary P source was only linted; no model check, mutation run, coverage report, or run-level event observation exists.

## Cross-run assessment

All three implementations describe single-root CAS visibility and immutable records, and the source generally makes state changes at that root boundary. The meaningful gap is validation: the retained models are tiny scalar abstractions, not models of individual storage calls or their interleavings. The strongest existing run is base-01’s five-schedule retry-state model plus inline real-source probes; it still has no independent monitor, saved tests, lost-response-after-commit scenario, or verified 5,000-call bound (its measured wide publish is 9,814 events). Base-02’s model has only one fully ready publish path and its saved monitor accepts every event; coverage and mutation were bypassed. Base-03 has the strongest implementation-side root/trie optimization probe, but no frozen model or model-check result. None records emitted implementation events and checks them against an independent monitor, and none supplies mutation feedback or retained custom regression tests. All three report unchanged public inputs in metadata; this audit did not inspect hidden grading artifacts.
