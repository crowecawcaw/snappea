# Stream model v2 audit

- **State computation and monitor independence:** Both submissions implement a stateful service rather than replaying precomputed output announcements. Skill v2 computes admission, sums, corrections, and output records from request events in `evals/modeling-skill/phases/runs/stream-model-v2-skill-01/submission/model.p:15-33,35-111`; its `Caller` sends requests at `:116-132`. The baseline computes those values in `evals/modeling-skill/phases/runs/stream-model-v2-base-01/submission/model.p:62-83,85-117`, with its actor requests at `:15-28`. Both monitors derive expected acceptance, sums, revisions, and outputs from public events and compare output fields; skill v2 uses `monitor.p:18-39,42-134,136-153`, baseline uses `monitor.p:49-74,76-112,114-131`. The required separation is stated in the shared public task at `public/TASK.md:20-25`.

- **Late first arrival:** The skill service has the correct code path: an accepted add at/after `end` emits immediately, retaining revision 0 when the window had not emitted (`submission/model.p:23-30`). Its fixed actor history does not exercise that path: window 0 already emitted at watermark 10 before its late add (`model.p:121-125`), while the first add to window 10 occurs at watermark 25, exactly its rejection threshold (`:122,125-126`). Baseline also exercises only a correction to an already-emitted window (`base-01/submission/model.p:20-25`). So late-first-arrival behavior is implemented in skill v2 but lacks actor-history coverage in both runs.

- **Finalization, values, and output completeness:** Skill v2 handles direct-to-final jumps and a final revision after a prior nonfinal output in its advance branches (`model.p:41-109`); its actor advances to 25 and then 75 (`:125,132`), covering both kinds. Its 75 advance emits the already-created windows 20 through 60 in increasing start order, and the monitor enforces increasing starts plus exact per-call outputs at `eEndCall` (`monitor.p:136-153`). Negative input values are present (`model.p:127,130`), but there is no zero-valued input or zero aggregate in the actor history (`:121-132`). All seven windows are populated, so this history does not check omission of empty windows. Baseline's actor covers two windows and a negative input (`base-01/submission/model.p:20-27`); its implementation loops in ascending start order (`:94-115`), but its fixed calls do not exercise a multiwindow output on one advance.

- **Bounds and history breadth:** The skill monitor rejects timestamps outside `[0,70)` (`submission/monitor.p:26`), and the service explicitly repeats cases for starts 0 through 60 (`model.p:41-109`). The fixed caller exercises those starts once each, with a single predetermined request sequence (`model.p:121-132`); it does not explore alternative add/watermark histories. The baseline uses a bounded loop for the same seven starts (`base-01/submission/model.p:45-52,94-115`) and explicitly documents its finite actor-sequence limit (`submission/DESIGN.md:5-7`).
