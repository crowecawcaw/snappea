# Blind open audit: shared FIFO flow

Scope: only the three named frozen runs' `submission/`, `public/`, and `tool-transcript.jsonl`; no private material or prior results. This is a source/transcript audit, not a fresh execution. Paths below are absolute under `/workspace/snappea-skill/evals/modeling-skill/phases/runs/`. Public `TASK.md`, `events.p`, `runtime.py` have identical SHA-256 across runs: `de11ce859ce78c23d2a6ff4b9ab36cc31f5a8873fbcbd4bc31315fcbb138a3af`, `b6878ba28a85162675e6dfe5278386df0612fde125a2750d8cb879ffb1ba984b`, `03075a108b773ace32698eade86ffad44d3a49affcc171733f7665a0a17bcf44`, respectively.

All three Python implementations use one shared record, atomic versioned load and compare-swap, fresh recomputation after a losing swap, separate put/take memo tables, and memoized replay. Skill-01 and base return replays at load; skill-02 commits replays through CAS. They initialize with CAS and reject incompatible capacities. The monitor separately reconstructs a capacity-two FIFO and checks outcomes, retries and snapshots; ignored empty-take item placeholders are handled correctly. The serial observation wrappers record actual submitted Queue calls and public returns, with shared instances and retries after intervening work; they do not claim thread completion order establishes linearization. The monitors are contract oracles, though they only see emitted events and cannot independently detect an unannounced implementation effect without a subsequent discriminating observation. All models are finite fixed scenarios, not bounded generated histories over a domain of input sequences.

- **skill-01:** `model.p` separates store loads and CAS, retries failures, and runs two clients on the same store. The concurrent clients use distinct IDs and repeat each operation; the sequential boundary history replays a full rejection after a take and an empty result after inserts. Unlike Python, modeled replays perform successful CAS of an unchanged record, introducing version increments and extra interference; DESIGN discloses this. Its store emits snapshots after commits, giving a useful state check, but the model abstracts initialization and capacity. Python forces stale-read collision and checks an actual CAS failure; its serial capture covers cross-instance old replays. Transcript calls 5–7 build/check the model before call 8 writes Python; syntax failure is corrected. Final call 13 reports both searches complete (30,808 and 4 schedules), required coverage complete, mutation time limit reached (37/74 detected); call 10 reports four Python tests passing. These are bounded evidence, not proof or complete mutation evidence.
- **skill-02:** the shared storage model has distinct read/write messages and retry on failed version match; it likewise CASes unchanged replay records, matching its Python replay-CAS algorithm. Its concurrent model has two distinct puts and one take, without duplicate IDs or concurrent snapshots; its sequential scenario exercises old full/empty/success replays after changes and obtains snapshots from Storage. Python actually forces a stale collision, and separate concurrent same-ID tests check a single effect across instances; these schedules are not modeled by the concurrent scenario. Serial observations check real cross-instance behavior. Calls 4–5 create and check model before Python call 7; missing coverage drove the added sequential scenario. Final call 13 reports two passed, complete searches and full required coverage, mutation timeout (18 of 43 detected, 22 untested); call 14 reports five Python tests passing. No generated input history is present.
- **base-01:** the model represents shared versioned load/CAS, conflicts and reload, including concurrent duplicate put/take IDs and an empty-duplicate scenario. Its direct `ContractExamples` is an explicitly trace-only oracle test: old full and empty outcomes are replayed after changes, but this is not model execution against the store. Python's serial captured history does execute old full/empty/success replays after later work on the same store; threaded tests check same IDs and capacity but do not force a CAS failure. Model replay announces from the client after receiving an earlier store load, whereas Python returns from that load: concurrent intervening commits can precede the announcement, so the event order may not reflect the claimed load linearization point. Model snapshots are initial/trace-only, not snapshots read from the store after modeled work. Call 5 writes Python before the model and monitor in the same shell call, contrary to the requested design-first chronology. Call 12 reports no bugs found but `tcQueue` search incomplete at 99,645 schedules/10 seconds; the two smaller searches complete and mutation times out. Exit zero is not a complete search. Call 11 reports four Python tests passing.

The skill runs visibly consulted the skill and examples; the baseline did not. Skill-01 also opened the bounded-history example, but did not implement a generated history. These three runs do not isolate the effect of one sentence: fixed scenarios, different concurrency bounds, model fidelity differences, and incomplete mutation/search make schedule counts or native pass insufficient to establish a causal benefit.
