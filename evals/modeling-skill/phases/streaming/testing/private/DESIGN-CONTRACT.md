# Streaming contract and fault map

The service uses event timestamps to assign half-open width-10 windows. Its explicit watermark starts at zero and is monotonic. An accepted add contributes its signed integer value while `watermark < window_end + 5`. Existing un-emitted windows emit revision 0 when their end is reached. An add after that first output and before finalization emits an immediate correction at the next revision. Advancing past the final threshold emits a final record; if one call jumps across both thresholds before the window emitted anything, the single result is final revision 0. Finalization advances the revision when there was an earlier output, even if the total is unchanged. Empty windows do not exist. Outputs from one advance are ordered by window start.

Every public operation is followed in the observation log by all records returned by that operation and an `eEndCall` marker. The saved wrapper is responsible for this well-formedness rule because a monitor cannot infer that a final marker was omitted after the event stream ends. The marker lets the monitor reject missing records within a call and catches a missing final output at the end of a well-formed log.

`model/private/cases.py` has six valid traces and nine invalid traces, all within the model task's timestamp bound. The negative histories isolate boundary bucket assignment, inclusive final-threshold acceptance, signed sums, missing initial/correction/final output, revision gaps, backward watermarks, and output order. The model-only P monitor is bounded to starts through 60; the testing monitor scans every width-10 start through the actual watermark, so its monitor work is O(watermark/10) and very large watermarks are expensive. The fixed-window implementation and written public contract apply to any nonnegative timestamp.

The implementation mutants separately change the bucket boundary, final acceptance threshold, signed aggregation, late correction, correction revision, late-first emission, final output, and multi-window ordering. The reference Python suite captures actual calls and results and invokes `snappea observe` with the independent P monitor.
