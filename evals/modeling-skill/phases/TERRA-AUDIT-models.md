# Terra stream-model audit

Scope: frozen `runs/terra-stream-model-{skill-01,skill-02,base-01}/{submission,public,tool-transcript.jsonl}` only; no private or older reports. References below use each run's `submission/` unless stated. These are source and trace observations, not scores or causal comparisons with Luna.

The public contract (`TASK.md:7-16,20-25`) requires bounded timestamps, computed calls, ordered complete returns, cutoff rejection, and revisions/finalization. All three tests select `WindowContract` and both actors (`tests.p:1`). All three implement actual stateful algorithms: sums and revisions per window; acceptance at `wm < start+15`; immediate output for accepted post-end adds; ascending scans that emit initial or final records, including direct final revision 0. Under nonnegative, monotonic inputs, source inspection found no contract mismatch. Skill-01 uses a negative revision as finalized marker (`model.p:14-54`); skill-02 tracks a closed bit and next revision (`model.p:12-54`); base uses map membership to track emitted and closed (`model.p:42-78`). The monitor's timestamp bound means this is not a general unbounded service implementation. Skill-01 assumes monotonic input rather than asserting it in the service; its monitor asserts it (`monitor.p:33-39`).

All monitors reconstruct state from announcements and compare an expected ordered list with every output and at `eEndCall` (skill-01 `monitor.p:14-72`, skill-02 `monitor.p:11-69`, base `monitor.p:10-62`). They check acceptance, totals, revisions, flags, extra and missing output, and window ordering. They do not detect a trace ending permanently with a call open: completeness is enforced only if an end marker arrives, as base `DESIGN.md:7` acknowledges. Their state is independent of service memory, but the acceptance, scan, threshold, and output rules closely mirror the service, especially skill-02 and base, leaving correlated specification errors possible. A pass is not independent proof of those shared rules.

Workloads are mostly fixed. Skill-01 `model.p:58-105` and skill-02 `model.p:58-92` choose only the first value from -1, 0, 1; base `model.p:4-32` chooses initial 3 or -2 using `$`. The remainder is a predetermined sequence, not generated arbitrary calls or interleavings of clients. Skill drivers wait for replies; base sends FIFO requests to a single actor. Useful exercised cases include corrections, negative/zero values, exact-cutoff rejection, direct final output, multi-window ordered outputs, and a first accepted add after end; repeated advances appear in all, including advances after some windows finalize. Empty windows are skipped. These examples do not cover all legal sequences or values.

After the submissions were frozen, the auditor independently authored and ran monitor probes on copies with `snappea check`; these are auditor validation, not evidence that the solvers used this practice. The solver transcripts show model checks and mutation testing, but no separately authored manual valid/invalid monitor probes. The auditor used using a manually calculated history: add (2,3), advance 10 => (0,10,3,0,false), add (4,1) => (0,10,4,1,false), advance 15 => (0,10,4,2,true), then rejected add (1,9), with an end marker after each call. All three reported the valid test case as `ok`; each overall command exited 1 because the deliberately narrow probe missed required coverage, not because of an assertion. Changing only the correction total from 4 to 5 caused all three to fail at their output assertion (skill-01 line 63, skill-02 line 62, base line 55). The exact inputs, copied sources and hashes, commands, exit codes, and raw output are preserved under [terra-monitor-audit](runs/terra-monitor-audit/); rerun `bash runs/terra-monitor-audit/run-probes.sh` from this report’s directory. This demonstrates one valid and one invalid total case, not a comprehensive negative suite; the probe did not test missing end markers, all ordering and boundary errors, or mutations of both model and monitor.

Recorded final checks: skill-01 transcript line 5 reports six schedules, full required coverage, 67/69 mutants detected; skill-02 line 5 reports six schedules, 99/99 statements, 32/32 branches, 58/60 mutants detected. Their remaining mutations remove default-zero initialization and scan the unreachable start 70. Base transcript line 9 reports 802 schedules, 93/93 statements, 34/34 branches, 46/46 condition outcomes, and 53/57 mutants. One survivor changes `closed[s] = true` to false, but the service tests map membership, not the stored Boolean, so either value marks it closed; the other survivors concern default-zero initialization and the bounded scan. The fixed workload remains a meaningful history-coverage limit despite these survivors. Schedule counts and coverage refer to the chosen finite model, not all histories. Skill-01 transcript line 3 first failed a required coverage gate; its later checks pass. Base transcript line 5 records test declaration syntax failure, repaired in line 6.

Transcript reads: both skill runs explicitly read `/opt/p-modeling/SKILL.md`, `/opt/p-modeling/reference/p-patterns.md`, and `/opt/p-modeling/examples/bounded-history/README.md` (transcript lines 1-2); base read task/events and `snappea --help` (lines 1-3), with no skill/reference/example read shown. Both skill traces initially revealed a surviving removed watermark-state assignment because public watermark announcements echoed internal state; changing announcements to the requested watermark exposed the mutation (skill-01 lines 4-5, skill-02 lines 4-5). This illustrates a concrete risk in observation design, not a measured skill effect.
