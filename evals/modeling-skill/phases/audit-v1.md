# Frozen phase-v1 source audit

Scope: source-first review of the frozen `phase-model-v1-01`, `phase-test-v1-01`, and `phase-test-v1-02` submissions and their tool transcripts only. No grading artifacts were read.

## Modeling phase: phase-model-v1-01

This submission models the CAS design substantively. `Store` owns a single record plus version; each `Client` reads a `(version, record)` snapshot, decides locally, and sends a CAS request. A stale version returns the current record and version, after which the client re-enters `Decide` and recomputes (`model.p:19-45,50-118`). The contention scenario launches independent clients against the same store (`model.p:121-132`), so two acquisitions can read one version, race at CAS, and force the loser to retry against the winner’s record. This is genuine competing work, unlike a fixed queue processed by one public-operation handler.

Event placement mostly matches the intended linearization boundaries. Reads and peeks, plus rejections decided from a snapshot, are announced in the store’s atomic read handler (`model.p:19-32`). Accepted acquire/write/release and advance events are announced only after version comparison and record replacement in the CAS handler (`model.p:34-45`). This ordering gives the monitor a coherent linearization history for the modeled operations. The design note explains these choices clearly (`DESIGN.md:3-7`).

Coverage is narrower than the design’s general CAS protocol: the concurrent scenarios focus on acquire/acquire and same-owner reacquisition. Expiry, stale write/release, successful write, and value retention are exercised sequentially. The transcript’s final check reports that the required coverage gate remained incomplete by 11 points, chiefly around retry branches for write/release/advance CAS contention (`DESIGN.md:9`; transcript calls 27, 32-33). The accurate claim is a checked CAS model with meaningful competing acquisition schedules, not broad validation of all CAS operation types. Mutation exploration and a passing model assertion alone do not close that scenario gap.

The monitor reconstructs state from public outcomes rather than inspecting the `Store`, and checks successful/rejected operations plus subsequent read/peek observations (`monitor.p:8-41`). However, it requires the exact token sequence 1, 2, 3, ... (`monitor.p:9,16-18`). The contract only requires positive tokens strictly greater than all previously issued tokens. Exact incrementing is a valid implementation choice for `model.p`, but it makes the standalone monitor reject valid gapped token histories. The monitor should retain the last token and assert `p.token > last_token` on success.

## Testing phase: phase-test-v1-01 and phase-test-v1-02

Both tests use a wrapper that invokes the real public `Service` method and appends that call’s actual arguments and returned result to an event list (`test_lease.py`). They include actual public `read`/`peek` observations, then pass the recorded trace to `check_events` with strict checking and unknown-event errors. They do not hand-author the implementation trace or read private service fields. This is a sound, repeatable implementation-to-monitor bridge. Both initially omitted `events.p` from `spec_files`, causing setup errors; each author noticed the missing declaration and fixed the file list before freezing (v1-01 transcript calls 8-9; v1-02 calls 7-8).

The scenarios cover the core lifecycle well: initial state, ownership and wrong-token rejection, successful writes, release, expiry at the exact boundary, reacquisition after expiry, and persistence of the integer across release. They are serial public API histories, which matches the deterministic single-threaded service supplied for this phase; they do not provide concurrency evidence.

Both submissions over-specify token allocation in their Python assertions. They assert exact values 1, 2, and 3 instead of only positivity and strict increase (`phase-test-v1-01/test_lease.py:75,93,102,115,120`; `phase-test-v1-02/test_lease.py:82-83,103-4,111-12,119-27`). The service supplied in these runs allocates consecutive tokens, so these assertions pass, but a valid implementation may skip values. This is stricter than each phase task’s monotonically increasing token contract and could cause false failures against a valid alternate implementation. Their P contract monitors correctly use `token > last_token` (`lease_contract.p:21-31` in each submission).

A more consequential blind spot is silent side effects from rejected writes. In both tests, wrong-owner/wrong-token writes are followed by a successful write before the next `read`; an expired rejected write is also followed by a later successful write before state is read (`test_lease.py` v1-01 lines 82-85, 110-22; v1-02 lines 88-91, 99-107). An implementation that returns `False` but changes the stored value can therefore have that evidence overwritten before observation. Add an immediate public `read()` after each rejected write and assert the value is unchanged. Public reads only after successful writes do not establish the rejection side-effect guarantee.

## General guidance implication

The useful distinction is between a model of an operation’s contract and a model of its storage protocol. For a claimed CAS design, represent the snapshot, conditional commit, failed compare, and retry as separate scheduled steps; let independent clients share the same record; announce successful results at the commit point and read-based results at the read point. Then name which operation types actually race in the scenarios. For implementation tests, record actual public outcomes and observe state immediately after rejected operations so a later success cannot hide an earlier side effect. Keep contract requirements such as monotonic token allocation distinct from one implementation’s consecutive-token strategy.
