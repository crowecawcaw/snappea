## sol-flow-skill-01

**Assessment:** substantive bounded modeling and implementation correspondence, with independent checking of actual observations. The principal gaps are short generated histories, narrowly scripted concurrent model inputs, and a safety-only announcement oracle that cannot establish completion or detect all missing observations. This one run supplies no estimate of skill effects.

- **Store and atomicity:** `model.p` separates AtomicStore Read and version-tested Cas handlers; QueueClient computes a detached candidate and reloads after failed CAS. Thus competing clients can read one version and interfere. Python `solution.py` uses the same load/propose/CAS loop and commits item effects and receipts together, including rejected puts and empty takes. Cached retries/snapshots correspond to atomic loads. Initialization and capacity other than two are explicitly abstracted out of P and separately tested in Python; this is a real correspondence limit, not a hidden model of constructor races.
- **Independent contract:** `monitor.p:QueueContract` derives acceptance, FIFO heads, snapshots, and per-namespace retry results from its own FIFO and receipt maps. It does not inspect Store state or accept any well-typed result. It distinguishes zero from missing through `found`. The identical monitor file is supplied to P tests and Python `check_events` with strict/unknown-event errors. Ten hand-authored invalid oracle traces are separated from implementation observations. Their blanket `assertRaises(Exception)` checks rejection but does not verify that a particular contract assertion caused it.
- **Meaningful history content:** the 18-operation serial script retains an empty take across insertion, rejected put across removal, successful put/take receipts across newer state, namespace reuse, and FIFO snapshots on the same Store. P generated histories genuinely choose operation kind and ID/value pair on every step (three steps plus snapshot); they are not merely random values in one fixed script. However values are fixed to IDs x→−1/y→0, and all 125 distinct Python three-operation histories cannot include a capacity-two rejection followed by retry after removal. Those deeper cases depend on the fixed serial script. Concurrent P operations are fixed four/three-operation scripts with one same-ID/distinct-ID choice, not generated concurrent histories. They cannot fill beyond capacity two, so concurrent over-capacity competition appears only in Python.
- **Implementation observations and ordering:** `test_observation.py:History` records actual methods, IDs, integer arguments, public results, and invocation/response clocks. Serial observations preserve invocation order and reject overlap. Concurrent validation searches an independent FIFO/receipt oracle over orders respecting response-before-invocation edges; it then submits a valid witness to the same P monitor. It never assumes append/completion order equals linearization order, and it preserves actual ID/value/result associations. Python boundary values differ from the P fixed script (−7/91 versus −1/5), so this is corresponding scenario replay, not byte-identical replay of an extracted P history. No raw execution histories/witnesses are persisted for later inspection.
- **Actual interference checks:** CollisionStore barriers force separate threads to attempt CAS from the same version and assert failures occurred. Tests cover three distinct puts against capacity two, duplicate put IDs, duplicate take IDs after filling, empty take racing put, and constructor races. These exercise real submitted Queue calls rather than synthetic observation-only tests. Each concurrent scenario samples one forced execution; it does not enumerate Python schedules or guarantee both outcomes of empty-take/put races. Capacity 1/3/7 and snapshot-copy tests use direct assertions rather than the capacity-two monitor.
- **Feedback and limits:** transcript call 5 writes/checks model and monitor before solution creation at call 7; call 6 completes the reduced generated bound first. The initial four-step search was incomplete under 20 seconds, then deliberately reduced to three. Call 8 performs mutation checking; call 9 adds the same-ID competing put alternative and reruns. No algorithm or monitor repair is visible, and the record does not establish that mutation feedback specifically motivated that scenario addition. Final JSON records complete base searches (4/8,927/864 schedules), 114/114 statements, 32/32 branches, 5/5 handlers, no exclusions/gate bypass, and 48/68 detected mutants with zero suppressions. All 20 survivors report incomplete mutation searches; they include removed audit announcements, unconditional CAS failure, skipped work, and acknowledgement changes as well as plausible redundancies. These cannot be dismissed as equivalent. The monitor has no expected-operation count or completion/liveness obligation, and announcements occur inside Store rather than from a modeled client response; bugs in delivery, skipped requests, or return acknowledgement can evade it. Python observations partly address public-return correspondence, but do not close the bounded model's progress gap. `model-check.json` predates the final concurrency enhancement; `full-model-check.json` is the final evidence.

## sol-flow-skill-02

**Assessment:** real concurrent load/CAS modeling, independent oracle, and strong public-return observation checks; smaller operation-generation domain and incomplete mutation feedback limit the claim.

- StoreModel separates loads and conditional writes, clients recompute after conflicts, and successful CAS co-commits FIFO plus receipts. Python follows that algorithm; memo hits/snapshots use loads. P memo hits announce after the load reply in Client rather than inside Store, but immutable, effect-free receipts make the result valid despite intervening commits. P uses bool-only put memos because each generated ID has one fixed value; Python stores original item too. Constructor races and arbitrary capacity remain Python-only. P automatically audits the internal record after each commit with snapshots; Python events instead come from actual public snapshot calls, so those model audit points are stronger than the Python recording frequency.
- QueueContract independently derives exact capacity acceptance, FIFO presence/value, memo invariance, and snapshots; the identical monitor is used by P and Python strict checks. Nine invalid synthetic oracle probes remain separate from actual recordings. Invocation/response clocks feed an independent interval-constrained witness search preserving actual IDs, items, and results. No reliance on append/completion ordering. Serial calls are actually sequential, though serial_events does not explicitly assert non-overlap. No saved raw histories or witness files exist.
- Concurrent operation histories are genuinely generated: each of two clients independently chooses put/take on each of two steps. However each client always reuses its identity and item; distinct-ID and shared-ID mains are separate. No generated snapshots, arbitrary ID reassociation, or depth beyond two per client. Thus retry diversity and capacity-boundary rejection depend substantially on the 13-operation fixed serial script. Python has fixed serial/concurrent scripts, twelve repeated scheduler runs, and forced conflict cases, not a generated-input campaign. Forced races include full put/take and empty take/put as well as duplicate requests, plus initialization; failure counts establish real interference. Additional ordinary tests check equal values, capacities, and receipt retention after 200 later generations.
- Chronology: call 3 writes/checks P before solution call 6; the three-step-per-client initial search times out, call 5 reduces to two but still has a large domain. Call 8 replaces per-step ID choice with per-client identity and adds a shared-ID main, completing smaller base searches. This is an explicit domain restriction, not evidence of a repaired algorithm. Call 9 adds actual forced stale-load tests; call 11 adds equal-value/long-history tests. Model/monitor and solution exhibit no correctness repair. Mutation reports are inspected, not suppressed. Final model-check.json has complete base cases (16,249/4/5,906 schedules), full required 92 statements/28 branches/5 handlers, 40/92 mutants detected, zero suppressed, mutation time limit reached. The separate bounded no-mutation file reports 16,887/4/6,369; DESIGN quotes those counts rather than the final default run. Survivors include scenario changes, removed observations and progress/acknowledgement defects. As in skill-01, safety-only monitoring and Store-side announcements leave operation omission/response completion gaps; no progress monitor closes them.

## sol-flow-base-01

**Assessment:** actual Store contention modeling and the same independent observation contract, with a useful added progress check and preserved public history artifacts. P input diversity is narrower and its longer contention search remains incomplete.

- P and Python both CAS every operation, including unchanged memo hits and snapshots. This extra version increment is a valid implementation choice and is modeled faithfully. Effect and memo changes share the same whole-record CAS. Loads/CAS are separate atomic handlers; conflicts trigger reload/recompute. Initialization is abstracted out of P and raced four ways against the actual runtime in Python. Unlike skill runs, constructors use the existing Store capacity even when passed another positive capacity; the public task does not specify behavior for conflicting constructor capacities, so this audit does not classify the policy difference as a defect.
- QueueContract owns an independent FIFO and two memo tables and checks the same semantic properties as the skill monitors. Exact same monitor source is supplied to P and strict CLI observation checks. Public method calls populate actual result/argument records; Python's independent transition oracle additionally checks exact result types. Concurrent witness search respects response-before-invocation edges, and a dedicated probe verifies a legal overlapping completion-order inversion and an illegal real-time order. This is stronger direct testing of the linearizer than in the skill runs; there are no saved negative P-monitor oracle probes.
- Final P mains contain only fixed operation scripts (long concurrent 14+4, serial 14, and small shared-ID put/take 2+2); schedule exploration does not generate operation histories. Initial optional second-client choice becomes separate serial/concurrent mains. Values and IDs are fixed, and zero/negative item behavior is exercised in Python rather than P. Python genuinely generates five seeded 100-operation serial histories, with operation kind, ID, and object choice randomized; items remain fixed by ID. Meaningful rejection/empty/successful retry-after-state-change cases exist in the fixed serial script and Python tests. Eight three-client forced races establish at least two CAS conflicts each, plus duplicate IDs, namespace reuse, empty take, snapshots, and capacity competition. They are repeated fixed plans, not generated concurrent programs.
- Saved observations preserve serial traces, five generated traces, and eight concurrent witnesses with raw intervals. Read-only comparison confirms every concurrent witness has exactly the same multiset of public operation events as its ten raw calls, including IDs/values/results. Source performs real-time-constrained ordering before replay. Serial values deliberately differ from P; no extracted P history is replayed byte-for-byte. Other capacities use direct assertions outside the capacity-two monitor.
- Chronology/feedback: call 5 creates P (initial test syntax fails); call 6 corrects syntax and runs an incomplete, coverage-bypassed exploratory check before solution creation at call 7. Coverage feedback is followed by a separate serial main and removal of the optional-client branch; final required coverage is complete with no bypass. Call 9 changes equal positive values to distinct values for FIFO sensitivity and inspects mutation output. Call 11 adds hot QueueProgress after that output; the observer double-counts Done because sends are already observed, and call 12 inspects the counterexample. Call 13 removes redundant announce Done, a concrete model-check-driven repair to instrumentation, not a queue implementation fix. Call 14 adds an exhaustible small contention case. Final tcQueue remains incomplete at 41,365 schedules/10 seconds; tcSerial and tcSmall finish at 4 and 1,538. Required coverage is 112/112 statements, 34/34 branches, 12/12 handlers; one optional transition-pair gap remains. Final mutations detect 57/70 with no suppressions or mutation timeout. QueueProgress catches missing client completion but three complete-search survivors skip operation lists or finish immediately: it counts completed clients rather than required operations. Removed snapshot announcements and false-success acknowledgements also survive incomplete mutation searches. Its progress evidence should therefore not be read as per-operation observation completeness.
