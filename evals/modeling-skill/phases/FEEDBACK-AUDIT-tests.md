# Feedback test-run audit

Scope: six frozen `feedback-*-test-*` submissions and their public task text and tool transcripts. The original audit was blind to grading and mutant outcomes. This revision adds the findings disclosed for follow-up and checks relevant mutant definitions where noted; it still does not report hidden scores.

## Event-time windows

All three stream wrappers call the real `Service` first, then record call inputs, actual acceptance/output values, every returned record, and `eEndCall` in public call order: [skill-01 test_window.py](runs/feedback-stream-test-skill-01/submission/test_window.py:25), [skill-02 test_window.py](runs/feedback-stream-test-skill-02/submission/test_window.py:30), [base test_window.py](runs/feedback-stream-test-base-01/submission/test_window.py:14). The P checks use `events.p` plus `contract.p`; the skill versions also set strict mode, hot-state checking, and unknown-event errors (skill-01 lines 49–57; skill-02 lines 62–71). Expected-result assertions provide a second oracle, but scenario choice determines which boundary defects they can expose.

Skill-01 covers signed and zero values, including a zero-valued late correction; the late-first add after advancing to the window end; corrections and final revisions; the lateness deadline and rejection; backward event-time arrival; sorted outputs; and empty windows ([test lines 61–144](runs/feedback-stream-test-skill-01/submission/test_window.py:61)). Its bucket samples include 0, 9, and later-window timestamps, but no exact nonzero bucket boundary such as 10, so it cannot distinguish a partitioning fault that affects nonzero multiples of the width. Skill-02 tests the 9/10 bucket boundary, signed and zero values, emitted-window corrections/final revision, direct-to-deadline finalization, rejection, backward event-time arrival, sorted outputs, and empty windows ([test lines 73–145](runs/feedback-stream-test-skill-02/submission/test_window.py:73)). It does not exercise the first add to a window after its end has passed while that window has no aggregate yet.

The base tests cover exact nonzero bucket boundaries, corrections/finalization, deadline rejection, sorted outputs, and empty windows ([test lines 40–131](runs/feedback-stream-test-base-01/submission/test_window.py:40)). They use positive values only; unlike both skill submissions, they do not exercise negative or zero values. They also do not have a first late add to a window with no prior aggregate. The backward-watermark assertion in skill-02 is outside the listed public contract and is not an important coverage gap.

The monitor is independent of implementation outputs in all three runs: wrappers capture returned values, while `check_events`/`check_spec` checks them against the separately supplied P contract. The public task asks for full returned outputs and call boundaries so omissions remain visible ([TASK.md](runs/feedback-stream-test-skill-01/public/TASK.md:7), [TASK.md](runs/feedback-stream-test-base-01/public/TASK.md:7)). After the disclosed follow-up, the concrete stream gaps are the missing nonzero exact bucket boundary in skill-01, and the missing late-first-arrival case in skill-02 and base. The base run also misses negative and zero values.

## Stable priority queue

All three queue wrappers observe real `submit`, `pop`, `reprioritize`, and `cancel` results, encode empty pop as `"-"`, preserve history order, and check the P contract with both event declarations and the contract spec. Examples: [skill-01 test_queue.py](runs/feedback-priority-test-skill-01/submission/test_queue.py:8), [skill-02 test_queue.py](runs/feedback-priority-test-skill-02/submission/test_queue.py:10), and [base test_queue.py](runs/feedback-priority-test-base-01/submission/test_queue.py:10). This matches the public capture instructions at [priority TASK.md lines 18–24](runs/feedback-priority-test-skill-01/public/TASK.md:18).

Skill-01 checks empty pop, signed/zero priorities, stable ties, a duplicate whose proposed priority would change pop order, reprioritization across priority levels, missing IDs, cancel/resubmit order, and resubmitting a popped ID ([test lines 65–131](runs/feedback-priority-test-skill-01/submission/test_queue.py:65)). Its same-priority reprioritization assertion at lines 89–97 does not by itself demonstrate preservation after a changed priority creates a tie; a direct move into a peer's priority would be more discriminating. Skill-02 checks signed priorities, empty pop, duplicate mutation, reprioritization, and missing operations ([test lines 68–119](runs/feedback-priority-test-skill-02/submission/test_queue.py:68)). Its cancel/resubmit history does not distinguish fresh from retained admission order: `cycled` is admitted after `kept`, then canceled and resubmitted, so either order still yields `kept` first (lines 105–119). Base covers ties, reprioritization, and cancel/resubmit ([test lines 67–112](runs/feedback-priority-test-base-01/submission/test_queue.py:67)), but its duplicate no-effect case is not discriminating: `kept` already ties at the head before the duplicate proposes priority -100, so changing its priority still leaves the asserted pop order unchanged (lines 81–88). Invalid ID inputs are documented as preconditions; probing them is not recommended as an audit gap.

## Skill use and tool friction

The stream skill-01 transcript shows reading `/opt/p-modeling/SKILL.md`, the implementation guide, and the reservation `test_storage.py` example (transcript calls 1–4). Stream skill-02 reads the skill, implementation guide, reservation README, and `test_storage.py` (calls 1–5). Priority skill-01 reads the skill and implementation guide (calls 1–4); priority skill-02 also reads `test_storage.py` after an attempted read of a nonexistent `test_reservation.py` (calls 1–6). The base runs do not show reading the modeling skill or its reference/example files. The skill runs use the same core observation pattern and P API as the reference, and the saved tests are readable without unnecessary framework code.

The recurring setup friction was selecting only `contract.p`: the contract references events declared in `events.p`, so initial checks failed to type-check until both files were passed. This appears in both skill stream transcripts and the base stream transcript, and each was corrected by adding `events.p` (stream skill-01 calls 6–7; stream skill-02 calls 6–7; stream base calls 8–10). Stream skill-01 also had one unsuccessful `inspect.getsource` attempt on the `Event` class (call 5), which did not block completion. In priority skill-01, the first run exposed an omitted `pop()` expectation for the zero-priority item; the assertion was added and the recorded `python -m unittest -v` run then succeeded (calls 6–7). Priority skill-02 similarly refined its reprioritization/tie assertion and ran the saved tests successfully (calls 9–10). The base priority transcript shows exploratory lookup for `pysnappea`, then successful discovery/use of `snappea`; its test-creation command records a passing unittest run (calls 7–12). These are recoverable tool/API discovery costs, not shortcomings in final observation provenance.

## Post-disclosure supplemental findings

The follow-up disclosed that skill-01 misses the nonzero `boundarybucket` case, while skill-02 and base miss `latefirstarrival`. Direct reads of the exact frozen submissions confirm both findings: skill-01's timestamps include 0 but no nonzero exact multiple of 10; skill-02 and base never add to a new window after advancing past its end. Skill-01 does include `advance(10)` followed by `add(5, 0)` ([test lines 113–123](runs/feedback-stream-test-skill-01/submission/test_window.py:113)). The relevant `fault_late_first_arrival_silent` mutant replaces the add-path branch for an un-emitted window whose end has passed with a branch that never fires ([mutant definition](runs/feedback-stream-test-skill-01/private/mutants.py:26)).

For the disclosed queue examples, skill-02's cancel/resubmit scenario cannot discriminate retained admission order, while base's duplicate test cannot discriminate a duplicate that mutates the queued priority. The scenario changes above target those specific risks: resubmit an item that originally preceded its peer, and duplicate a later item with a priority that would move it ahead if applied. No hidden fault score is stated here.
