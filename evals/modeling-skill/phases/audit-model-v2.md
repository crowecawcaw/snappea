# Frozen modeling-phase v2 source audit

Scope: source-first review of frozen `phase-model-v2-01` and `phase-model-v2-02` submissions and transcripts only. No grader files or v2-01 work directory were read.

## v2-01

- **Actual CAS model:** Separate `Client` and `Store` machines read a versioned snapshot, send a conditional CAS, receive a conflict, reread, and recompute (`model.p:31-73,96-237`). `RaceMain` starts two clients against one store (`249-258`), so competing acquisitions can share a snapshot and force a real CAS retry. This is not an atomic-API toy.
- **Event linearization:** Accepted mutations announce in the successful CAS handler after the record fields update (`model.p:50-69`). Rejected acquire/write/release decisions announce in the atomic read handler that established their result (`31-47`). `advance`, `read`, and `peek` announce in the store’s single control handler (`75-90`). Those points match the v2 task’s declared linearization-order trace.
- **Clock:** `advance` is one atomic store control operation and bumps the version so an older snapshot cannot commit afterward (`model.p:75-80; DESIGN.md:5`). The lifecycle scenario uses it between completed public operations, matching the task’s test-control assumption.
- **Monitor:** The monitor derives owner/token/value/expiry from public events, permits strictly increasing token gaps, and checks read/peek outcomes (`monitor.p:10-79`). It is independent of the client/store state. No coverage suppression or bypass appears in the frozen source.
- **Scenario limits:** There is an acquisition race and a separate Alice-acquires/Mallory-write-release race. The lifecycle covers expiry and rejection, but it releases/reacquires under the same client; neither script applies the old owner’s stale release while a successor’s lease remains live. The lifecycle’s rejected writes are followed by later successful writes before `eRead`; the wrong-credential run has no `eRead`. Thus the scripts do not make rejected-write value preservation publicly observable, even though the monitor’s state rule leaves value unchanged on a rejected-write event. CAS contention is focused on acquire; write/release/advance retry conflicts are not represented by competing scenarios.
- **Assessment:** A genuine read/CAS/retry model with truthful event placement and a sound independent external monitor. Good enough for a combined-flow pilot as a meaningful design artifact, with the stated concurrency and side-effect scenario gaps kept visible.

## v2-02

- **Actual CAS model:** Independent `Operation` machines read the shared `Storage` record, calculate a candidate, CAS on its snapshot version, and reread/recompute after conflict (`model.p:15-60,64-116`). `Scenario` starts two simultaneous acquirers (`118-136`); a CAS conflict can make the loser re-read and reject after the winner commits. Lifecycle operations are modeled separately from storage steps. This is a genuine protocol model.
- **Event linearization:** Successful mutations and rejected mutations both announce only in the successful CAS handler, after the state replacement or version-only no-op commit (`model.p:35-52`). `read` and `peek` announce in the atomic `eGet` handler (`54-60`). Event order therefore reflects the modeled CAS/read linearization points as the task requires. Rejected writes preserve the modeled value (`proposed` starts as the snapshot; only a valid write replaces `proposed.value`).
- **Clock mismatch:** The task specifies `advance` as an atomic test-control operation serialized between public calls (`TASK.md:12`), but `Operation` routes advance through the same read/decide/CAS loop as a mutation (`model.p:93-106` in the operation logic; its scenario uses that path at `161-163`). No scenario races advance, so this does not invalidate the checked scripts, but the model permits advance to land between another call’s read and CAS. If serialization means advance cannot overlap an in-flight call, model it as the same atomic control transition used in v2-01, or state the intended weaker meaning.
- **Monitor:** It derives expected effects from public events and accepts any positive token at least the next permitted value, then raises the lower bound (`monitor.p:14-52`). It checks reads and peeks independently. No suppression or coverage bypass appears in the frozen source. The transcript records complete bounded searches; mutation exploration hit its time budget and left mutants unsearched, which the design note reports.
- **Scenario limits:** The competing-acquire test is substantive. The lifecycle tests same-owner reacquisition, a successful write, expiry, an expired write rejection, a new acquisition, release, and reads/peeks. It does not read immediately after the rejected expired write, but its later `eRead` occurs before any successful write, so the value-preservation effect remains observable. The stale release occurs after the successor is released (`model.p:167-175`); it does not test whether old credentials can disturb a successor that is still live. As in v2-01, CAS retry contention is only directly exercised by competing acquisition.
- **Assessment:** Also a meaningful CAS/read/retry model with correctly placed events and an independent contract monitor. Suitable for the combined-flow pilot with the clock-serialization mismatch and lack of stale-against-live-successor scenario explicitly noted. The finite scripts are not evidence for unbounded concurrency or every mutating operation’s retry path.

## Pilot decision

Both frozen artifacts pass the key source-audit gate: shared state, independent actors, distinct atomic read/CAS transitions, retry after version conflict, and event emission at the declared linearization points. V2-01 matches the atomic clock-control assumption more closely. V2-02 models advance as a CAS protocol, which the current scripts do not race. Both are reasonable phase-model examples for a combined-flow pilot, not proofs of correctness; the narrow retry and stale-successor scenarios should remain visible in any conclusions.
