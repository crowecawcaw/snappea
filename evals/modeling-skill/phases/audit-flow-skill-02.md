- **P model versus Store boundary:** The submitted runtime has separate locked `load` and versioned `compare_swap` primitives (`phase-flow-skill-02/submission/runtime.py:13-23`). The P model instead performs each request's decision and state mutation directly in one `Store` handler (`phase-flow-skill-02/submission/model.p:27-43,44-62`); it has no version, separate snapshot, failed CAS, or retry path. The Python implementation does use that protocol: `put`/`take` load a record, compute a copied candidate, and repeat after CAS failure (`phase-flow-skill-02/submission/solution.py:37-57,58-77`). Thus the submitted P model describes atomic queue operations, not the submitted CAS algorithm, despite the task asking for the actual atomic Store operation (`phase-flow-skill-02/public/TASK.md:22-28`).
- **Independent monitor and model concurrency:** `QueueContract` observes public `ePut`/`eTake` events and maintains its own FIFO slots and request-result maps (`phase-flow-skill-02/submission/monitor.p:1-9,31-64`). The saved Python test also creates four Queue objects on one Store, synchronizes four distinct puts with a barrier, and checks exactly two succeed and the shared snapshot has capacity two (`phase-flow-skill-02/submission/test_observation.py:60-80`).
