# Feedback audit: event-time model submissions

The original blind audit uses only the three runs' `public/`, frozen `submission/`, and `tool-transcript.jsonl`, plus the installed modeling skill, its reference, and bounded-history example. It does not use grading or private materials. A clearly labeled supplemental section below records scores supplied after that audit.

## What was built

All three submissions implement a real stateful aggregation algorithm rather than replaying a precomputed output transcript. Each service derives acceptance, per-window sums, revisions, and output records from received add and watermark calls (`feedback-stream-model-base-01/submission/model.p:32-109`; `feedback-stream-model-skill-01/submission/model.p:7-85`; `feedback-stream-model-skill-02/submission/model.p:9-77`). Each includes a separate monitor that derives expected results from public events rather than reading service state (`base-01/submission/monitor.p:38-123`; `skill-01/submission/monitor.p:27-118`; `skill-02/submission/monitor.p:28-90`). However, baseline's `tests.p` selects only `Main`, `Aggregator`, and `Caller` and never asserts `WindowContract` (`feedback-stream-model-base-01/submission/tests.p:1-3`); its monitor also suppresses the unselected-spec lint at line 1. Therefore the baseline native check does not run that monitor. The skill runs do select `WindowContract` in their tests (`skill-01/submission/tests.p:1`; `skill-02/submission/tests.p:1`).

Where selected by the test, the monitors are structurally separate, but their transition logic closely mirrors the service algorithms: each independently maintains watermark, totals, emission/finalization state, and revision counters, then computes the same expected-output sequence. This gives useful event-level checking for the skill runs, but the oracle is co-designed with the implementation and does not use a distinct hand-calculated source of truth. In particular, none of the transcripts records a `snappea observe` run over manually authored valid and invalid histories.

## Per-run evidence and gaps

- **Base 01:** The `Caller` sequence is fixed (`model.p:17-29`); the service algorithm is stateful. It reaches an initial output for window 0, a late correction, a too-late rejected add, and finalization (`model.p:20-27`). It uses a negative value, but no zero value. It does not test a first add to a previously absent window after that window's end. Although the submitted monitor contains acceptance/output checks (`monitor.p:38-120`), the native test does not select it, so those checks are not exercised by that test. The monitor also does not check the input timestamp bound or watermark monotonicity. The design documents the fixed sequence and omissions (`DESIGN.md:3-9`). The transcript ends with an allowed-incomplete-coverage check; the checker reports a completed search of 73 schedules, while the command explicitly permits incomplete coverage (`tool-transcript.jsonl:38`).
- **Skill 01:** `Calls` is also one fixed sequence, with each call waiting for its result (`model.p:88-119`); it is not a generated input-history tree. This sequence does cover a valid first late arrival: after watermark 30, timestamp 22 creates window 20 and emits its first nonfinal record (`model.p:103-110`, and service branch `model.p:32-49`). It also covers negative and zero values (`model.p:91-113`), accepted lateness below the cutoff, rejection at the cutoff (window 0 at watermark 15; `model.p:99-103`), direct finalization, and a timestamp near the upper bound. It does not test a timestamp exactly at a window start/end boundary such as 10. The monitor checks the `[0,70)` timestamp bound and the output list at every call end (`monitor.p:37-40`, `99-118`), but does not assert that observed watermark inputs are monotonic. The caller sends 65 after 70; the service clamps internal state but announces the regressive input, while the monitor silently clamps its own state (`model.p:55-60, 113-118`; `monitor.p:64-74`). Thus that out-of-contract call does not demonstrate enforcement of the forward-only watermark property. Design notes the fixed finite history and omissions (`DESIGN.md:10-26`). The final transcript check completed four schedules and passed with its default mutation phase (`tool-transcript.jsonl:14`).
- **Skill 02:** `Calls` is a fixed serialized sequence (`model.p:79-104`), not generated input histories. It covers negative, zero, and positive values, and timestamp 20 exactly at a window start (`model.p:82-100`). It has a late correction to an already-emitted window (`model.p:84-90`), but not a first late arrival into an absent window after its end, nor a rejected add: all its adds occur before their respective lateness cutoffs. A first late add to a previously absent window after `end` but before `end+5` would also expose a source-level gap: the model emits an output only when `emitted[ws]` is already true on add (`model.p:33-41`), and the monitor likewise queues no expected initial output in that case (`monitor.p:35-44`). The monitor asserts timestamps are in `[0,70)` and watermark updates are nondecreasing (`monitor.p:28-34, 46-49`), then checks output contents and per-call completeness (`monitor.p:71-90`). The design explicitly says fixed sequence and finite bounds (`DESIGN.md:3-9`). The final transcript command allows incomplete coverage and reports six uncovered points despite a completed four-schedule search (`tool-transcript.jsonl:21`).

## Skill use, bounds, and syntax friction

The transcript for **base 01** shows the task and event schema plus `snappea --help`, but no skill or reference reads (`tool-transcript.jsonl:1-3`). **Skill 01** read `/opt/p-modeling/SKILL.md`, `guides/modeling.md`, `reference/p-patterns.md`, and the bounded-history `.p` example; it did not read `guides/scenarios-and-oracles.md` or the bounded-history README (`tool-transcript.jsonl:1,3-4`). **Skill 02** read the skill, modeling guide, P patterns, and bounded-history `.p` example, but likewise not the scenarios/oracles guide or example README (`tool-transcript.jsonl:2,4-5`). The skill and README specifically call for generated input histories and independent hand-calculated monitor probes (`skills/p-modeling/SKILL.md:16,21`; `skills/p-modeling/examples/bounded-history/README.md:5-9,27-36`). Neither skill run adopted those two practices: inputs stayed fixed, and only model checking appears in the transcripts.

Bounds are generally disclosed rather than presented as production-wide proof: the public task limits timestamps to `[0,70)` (`public/TASK.md:16,25`); the skill submissions state that the checked trace is fixed and omit arbitrary histories or runtime behavior (`skill-01/submission/DESIGN.md:14-26`; `skill-02/submission/DESIGN.md:5-9`). The public task itself asks for a stateful service and bounded model, so the fixed histories meet that construction shape while leaving history diversity untested.

P syntax caused visible iteration in all runs. Base 01 encountered unsupported array declarations, tuple/event payload shape errors, reserved `start`/`end` identifiers, and repeated test syntax errors before reaching a check (`tool-transcript.jsonl:5-19,24-34`). Skill 01 and 02 still hit reserved-name and tuple trailing-comma/type errors despite reading `p-patterns.md` (`skill-01/tool-transcript.jsonl:6-10`; `skill-02/tool-transcript.jsonl:7-14,18-20`). The reference does document reserved names, named tuples, and trailing commas (`skills/p-modeling/reference/p-patterns.md:21-25,57-60`), so syntax friction persisted after that reference was consulted.

## Strengths and unresolved gaps

The skill runs show clearer finite-scope disclosure, richer signed/zero-value coverage, and event-driven monitors that compare every output field and require complete per-call output lists. Skill 01 has the strongest fixed-sequence semantic probes, including the first late arrival at the window-end boundary and rejection exactly at the lateness cutoff. Skill 02 explicitly checks monotonic watermarks and a window-start timestamp.

The target improvement—generated input histories plus manual monitor probes—was not adopted in either skill run. All runs use a single fixed caller history; the monitor duplicates much of the service's transition structure; and there are no hand-calculated `observe` probes. Remaining semantic gaps are exact half-open timestamp boundary coverage, rejection at the threshold in skill 02, and an unambiguous forward-watermark contract check in skill 01. Skill 02's final check also explicitly suppresses incomplete-coverage failure, so its passing status should be read with the six uncovered points noted above.

## Supplemental findings after the blind audit

The following scores were supplied after the original source-only audit and are kept separate from its findings: skill 01 accepts 6/6 valid and rejects 8/9 invalid cases; the missed invalid case is the regressive watermark, consistent with the source behavior described above. Skill 02 accepts 5/6 valid and 9/9 invalid cases; the missed valid case is the first late arrival into an absent window, consistent with the model and monitor paths identified above. These results reinforce the source review: the skill 02 monitor is selected, but it mirrors the model's missing initial-output expectation for that case. No motive is inferred from either result.
