# Blind frozen-source audit: SOL certified bundles

The initial blind audit reads only the frozen `submission/`, `public/`, and `tool-transcript.jsonl` for the three runs named below. Skill runs were declared frozen before inspection; baseline inspection began only after parent freeze confirmation. No private source, grading artifacts, grader logs, or prior reports were read. Filenames outside the permitted scope appeared in directory listings; their contents were not read. Submitted checks/results are evidence of what the solver ran, not independent verification. The separately labeled growth experiment below is auditor postfreeze exploration. No causal effect can be established from two skill runs and one baseline.

## Judgment about models

The skill runs show useful qualitative modeling practices: models precede implementation, each has a separately maintained contract monitor, separate storage read and CAS events expose stale decisions, actual competing identities and memo values are represented, checker feedback changes the workload or assertions, and saved real Python observations run through the same design monitor. They adapt examples to bundles rather than merely rename an inventory example. These are substantive improvements in modeling discipline compared with this baseline's code-first, shared-evaluator checks.

That does **not** mean uniformly richer task modeling. Baseline models revision changes, reviewer sets, CI overwrite, candidate evidence, and guard interactions. Skill-01 omits those entirely; skill-02 replaces them with initial `ready` and `stale` sets. Neither skill model tests evidence invalidation by a concurrent revision. Skill-01 is strongest on preparation and the important A-publish/B-advance/A-retry scenario. Skill-02 models four actual outcomes and nondeterministic guard combinations, but cannot distinguish a new publish request for an already published bundle. Baseline's broader generated lifecycle exploration has weaker oracle independence and remains search-incomplete. All three have substantial abstraction gaps between the storage graph and their models.

## Run-specific evidence

### sol-vcs-skill-01

`submission/protocol.p` has independent Client and Store machines. `eRead`, `ePrepare`, and `eCas` are distinct messages. Store checks the root version and that a complete candidate image was prepared; one handler atomically changes both heads and both memo slots. Client loses a response by rereading after CAS and can abandon preparation once. A and B are real competing identities; result 1 means published and 2 conflict, and memos retain those values rather than a generic seen bit. B's base is chosen between 0 and 1, and Main retries A after both finish. Thus the bounded model includes both shared-base conflict and successful later advancement before an original retry. `AtomicBundles` maintains old image, expected bases and returned results, derives expected head changes, checks memo persistence and actual returned outcome equality. Its contract state is separate from candidate construction, although expected-parent comparisons naturally resemble the implementation guard.

Limits: both heads always start and advance together, so independent second-target mismatch is unreachable (final condition coverage 41/44). No revision number, approval identity, digest or CI transitions, bundle publication flag, or fresh request for the same published bundle exists. Prepared state is a set of whole images, not a chunk chain; there is no partial durable node failure, restart machine reconstruction, reader client, or liveness property. Rereading after CAS and a bounded abandonment represent selected crash effects, not every store boundary.

Transcript calls 4–6 (79.317–98.130 seconds) create/check the model before call 7 writes Python at 130.554 seconds. Initial coverage explicitly reported that `saved` retry comparison never ran; call 5 adds retries and expected-base checks. Early 20/40-second searches remain incomplete. Call 11 replaces redundant retry interleavings with a completion controller and the saved result reports completion of 30,304 schedules, 82/82 statements, 32/32 branches, 11/11 handlers. This is a real workload change that reaches retry assertions, with a deliberate reduction of retry scheduling scope. Call 12 removes version validation in a separate negative control: 161 schedules find `forgot A outcome`. No automatic mutation suite was run; final report says `--no-mutation`.


**Postfreeze reproducibility note (added after the blind audit):** Parent-supplied fresh-container rechecks of frozen `protocol.p` did not reproduce its saved 30,304-schedule/1.965-second search completion. The matching 40-second `--no-mutation` recheck explored 422,795 schedules and remained incomplete; five-second seed 0, 1, and 0 checks also remained incomplete. All these checks reached required coverage and reported no assertion failures. Their model hash is `83a9119c634eaac03a1fcbcfb8f15cb245d140da2116e4d5931ea7a26aae076d`; recheck records identify binary hash `2ea61378c21ff899f3977eaefc505753b566f2fa3a114d5288c4a8a60d864194`. I independently reconstructed the final model from transcript call 4's literal file plus replacements in calls 5, 6, 8 and 11, without executing transcript code or running another checker: the bytes exactly match the frozen source and that hash. Thus an unrecorded final-source edit does not explain the discrepancy. Cause remains unknown; this audit does not infer fabrication or attribute it to seed behavior. Treat original completion as a saved solver report whose completion was not reproduced, while coverage/no-observed-assertion evidence is reproduced. Evidence: `model-recheck.json`, `model-agent-budget-recheck.json`, and `model-seeded-rechecks.json` in the skill-01 run root; literal reconstruction script, output and resulting model in ignored `sol-open-audit-vcs/`.

Python uses complete logical-state JSON in a 6,000-character immutable linked chunk chain, with equality-checked hash addresses and collision suffixes, then root CAS. All guards are recomputed after CAS failure. Reads retain an immutable root snapshot; successful publication co-locates head effects, flag, and rejection/success memo at root CAS. This corresponds to the modeled atomic primitive without assuming an entire API call atomic. The chunk-size argument is reasonable for ordinary references; the model does not validate encoding, graph closure, or growth. Full-state copying creates the concrete budget failure below.

`test_validation.py` is hand-authored: eight scheduling seeds for competing publications and snapshot readers; explicit lifecycle/CI/reviewer checks; second-branch conflict; a lost root rejection response followed by readiness change and retry; 64-branch crash-after-every-publish-write sweep; a small 230-bundle growth case. Transcript call 12 records ten tests passing including public tests. The crash sweep checks durable successful writes, not every read/CAS-before boundary or every API operation.

Saved `observed-history.json` records A published at heads (1,1), B published at (2,2), then A retry returns its original result. Head values and publication results come from actual Python calls; memo fields are reconstructed by the adapter from those results, not directly read from durable memo storage. The final retry reads/asserts current heads but its event reuses the prior image variable. Calls are deliberately sequential, so operation order supports the abstract commit sequence; no concurrent reply ordering is treated as a linearization proof. The same `AtomicBundles` monitor checks it strictly. A deliberately torn event must fail. This is real implementation observation with a limited adapter, not a distinct scenario oracle or generated implementation workload.

### sol-vcs-skill-02

`submission/model.p` models two Publisher identities, competing snapshots, versioned root CAS, retry recomputation, and two attempts per identity. Store initializes readiness and staleness nondeterministically and separately. Memo values distinguish published/stale/not-ready/conflict (1/2/3/4). `Certified` independently maintains heads, version, memo map, ready/stale sets; its Expected function derives outcome from its state. `eReturned` compares actual client return values with durable memo state, and `eObserved` checks memo retries and current heads. This is materially stronger than an assertion that a client-supplied valid bit is true.

Limits: immutable preparation is entirely abstracted away. Retry-after-completion represents lost response effects but no explicit crash/restart or durable partial graph exists. One ID serves as bundle, target commit and publish request, so already-published lifecycle behavior under a fresh request cannot be exercised. The `published` set is written but unused in Expected and Publisher decisions. Initial stale/ready bits cover guard ordering, not evidence provenance, authorization, duplicate reviewers, CI failing after success, revision reset, or approval/CI/revision races. Heads remain equal and the independent second-head conflict condition is not reached (34/36 conditions). Model result logic and monitor Expected duplicate guard structure, though they use separate states.

Transcript call 4 creates/checks model at 92.068 seconds; call 6 writes code at 161.262. Call 4 reports coverage gaps for memo retry, unused published branch and unhandled eObserved. Call 5 makes reads announce actual memo observations and removes the unreachable published branch from both sides. This both improves retry coverage and narrows lifecycle scope. The model was not simply made adequate by hitting a percentage. Call 7 runs automatic mutation: 27/57 detected, 30 undetected with incomplete search, aggregate 30-second limit. One listed undetected mutation removes `result = s.memo[input.id]`. Call 9 adds actual eReturned assertions and reruns the base model, 6,304 complete schedules, 71/71 statements, 26/26 branches, 6/6 handlers. There is no saved rerun establishing that the previously undetected mutant is now killed. Final base-model completion is stronger evidence than the incomplete mutation run, and neither proves unbounded correctness.

Python uses a chunked immutable AVL tree, storing keys and payloads in 2,048-character blobs; path copying updates only changed entries and branches, then root CAS selects the complete graph. A per-invocation cache holds only immutable objects. Failed root CAS reruns evaluation at a new root. Equality checks and collision suffixes were added in final call 10; tests rerun successfully afterward. Code review found no concrete ordinary-operation atomicity defect. Record size, AVL rotations and immutable graph construction are outside P.

Submitted Python tests are hand-written, with 12 scheduling seeds and repeated snapshot reads, a two-head 18-write publish crash sweep, lifecycle/guard cases, output alias checks, and 220 large 64-branch Unicode bundles. Final transcript records nine tests passing and a 939-store-call 64-head publish. The saved history uses actual sequential return and head values: A succeeds, B conflicts, A retry returns success. Its `old` version is an adapter sequence index, not measured root version; sequential isolated calls make an abstract order appropriate. Same `Certified` design monitor is reused with strict validation; torn-head and changed-retry corruptions must fail. There is no separate scenario oracle, no saved concurrent linearization history, no generated Python action workload, and no claim supported that all storage schedules were observed.

### sol-vcs-base-01

Transcript writes Python at call 5, 123.470 seconds; model follows at call 8, 200.278. Baseline reads the installed inventory example rather than a modeling skill. `model.p` has two optimistic clients taking three generated actions each, finite revision/candidate tokens, reviewer choices including unauthorized, success/failure CI, fresh request IDs, a synthetic competing head advance, bounded abandoned attempts and lost-response retries. This is genuinely generated bounded action exploration rather than only a fixed script. One main bundle and an unconstrained synthetic competitor do not model two certified bundle lifecycles with separate memo identities. The candidate token does not fully represent digest of expected parents plus updates, and revise selects its expected parent from the current head rather than arbitrary supplied update maps.

DurableRoot and Client both call global `Evaluate`. Recomputing Evaluate at current root is useful to detect stale decisions, but equality of outputs is not an independent specification of Evaluate's semantics. Additional assertions check torn heads, publication monotonicity, revision resets and readiness at transition; `SemanticChecks` supplies literal expected outcomes and checks memo precedence with revision 99. Thus baseline has some independent contract checks, but no independent monitor machine and no real-Python-to-P observation path. The semantic checks do not make the shared evaluator an independent oracle for every generated action.

The final report has 217,364 concurrent schedules and a 30-second incomplete search; deterministic semantics complete in one schedule. Union required coverage is 155/155 statements, 46/46 branches and 4/4 handlers; concurrent-only is 103/104 and 45/46. `--allow-incomplete-coverage` remains enabled (`gate_bypassed: true`) despite no final required gaps. Final call 14 makes real coverage-directed changes: one initial action revises while another publishes, memo retries are checked on read-only evaluation, and an impossible memo-existing commit branch becomes an assertion. This feedback discipline is present in baseline too. No mutations or saved implementation observations are submitted. No unbounded liveness property is checked; retries can stop after a bound even when CAS loses.

The implementation uses persistent AVL maps, a chunked head object, fanout-64 blob index records, and one mutable root. An allocator CAS grants unique immutable arenas, not ownership, so abandoned allocation does not block recovery. Root selection and guard reevaluation match the model abstraction; storage allocation/preparation remains outside it. The eight saved Python tests include concurrent same-ID submissions/approvals and six distinct publish IDs on one bundle, small publish-write crash sweep, lifecycle checks, and 220 large 64-branch Unicode bundles. There is no competing distinct-bundle publication/snapshot reader loop in added tests and no generated Python sequence or saved observation monitor. Code review found no concrete correctness defect within the exercised ordinary-size regime.

## Exploratory auditor postfreeze growth witness

This is a source-informed, posthoc check, **not primary scoring or solver validation evidence**. Exact script and commands/output are under `/workspace/snappea-skill/evals/certified-bundles/runs/sol-open-audit-vcs/`. The same input protocol is applied to all three frozen implementations using their own unchanged public runtime. It submits 176 fresh IDs `bundle0` … `bundle175`, sequentially with no contention or failures, 64 heads initially `0`, and 85,293-byte compact-ASCII update maps. Each new head is `('\\\"雪' * 130) + branch`, copied from skill-02's submitted growth test. Each store operation has two runtime steps, so measured call count is delta steps / 2.

At the 176th submit, skill-01 uses **5,008 store calls**, exceeding the explicit 5,000-call quiescent budget. Baseline uses **48**, skill-02 **121** for that same submit. This is a concrete valid 64-branch/hundreds-of-bundles workload, not an arbitrary infinite-input impossibility argument. Individual store writes remain within the runtime's cap; the failure is cumulative full-state work. Skill-01's original growth test uses only one branch with short commits and misses this joint dimension. Its design document acknowledges proportional-to-history cost, but that limitation occurs inside this concrete workload. Persistent layouts in baseline and skill-02 avoid that particular witness; these results do not establish a universal call bound for arbitrary string sizes or prove all their operations correct.
