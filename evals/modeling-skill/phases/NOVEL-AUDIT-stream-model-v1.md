# Stream model v1 source audit

- **Skill run 01: stateful service and useful semantics, with one material implementation hole.** The service owns watermark, per-window sums, phase, and revision, then computes outputs in `Aggregator` handlers ([submission/model.p:5](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/submission/model.p:5), [submission/model.p:22](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/submission/model.p:22), [submission/model.p:50](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/submission/model.p:50)). It handles multiple windows, late corrections, a direct-to-final record, and a rejected boundary add in the actor sequence ([submission/model.p:90](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/submission/model.p:90)). But `eAddCall` emits only when phase is already 2; it misses the required initial output when a window is first created by an accepted late add after its end but before its lateness cutoff. The task explicitly requires this case ([public/TASK.md:11](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/public/TASK.md:11)). Its fixed sequence never creates a new window after its end, so the gap is unexercised.

- **Skill run 02: strongest service/monitor pairing, but its design report overstates coverage.** The service computes accepted adds, totals, revisions, and watermark outputs from state ([submission/model.p:22](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/model.p:22), [submission/model.p:55](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/model.p:55)). Its fixed driver covers multiple windows, a late first emission, a correction, and finalization ([submission/model.p:94](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/model.p:94)). The monitor derives expected outputs from public calls and checks all fields, ordering, extras, and omissions at `eEndCall` ([submission/monitor.p:26](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/monitor.p:26), [submission/monitor.p:55](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/monitor.p:55), [submission/monitor.p:87](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/monitor.p:87)). However, the actor never takes a window directly from unseen to final: window 0 emits before finalization, and window 20 emits at watermark 20 before finalization at 35. Window 30 is created but its end is not reached. `DESIGN.md:5` claims a direct-final output, which the submitted call sequence does not produce ([submission/DESIGN.md:5](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/DESIGN.md:5), [submission/model.p:119](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/submission/model.p:119)).

- **Baseline run: stateful computation and independent trace oracle, but fixed input script.** `WindowService` stores per-window state and computes outputs from calls ([submission/model.p:5](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/model.p:5), [submission/model.p:31](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/model.p:31), [submission/model.p:55](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/model.p:55)). The monitor independently derives expected outputs, checks each record, and verifies completeness per call ([submission/monitor.p:56](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/monitor.p:56), [submission/monitor.p:81](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/monitor.p:81), [submission/monitor.p:115](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/monitor.p:115)). The sequence includes multi-window activity, correction, direct-to-final output for the window created at timestamp 25 then advanced to 35, and a previously emitted window finalized ([submission/model.p:91](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/model.p:91)).

- **Exploration and completeness across all three runs.** Each actor supplies one predetermined operation sequence; skill run 01 and 02 wait for a service reply before the next call, while baseline enqueues one sequence from a single actor. The checker can explore delivery/scheduling details, but no run explores alternative add/watermark input orders or values. The fixed traces do cover several distinct threshold cases, but they cannot establish behavior for unchosen histories. All three monitors bound themselves to seven starts and reject timestamps outside `[0,70)`, matching the v1 task's explicit model and monitor bound ([skill public/TASK.md:16,25](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/public/TASK.md:16), [baseline submission/monitor.p:63](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/submission/monitor.p:63)).

- **Tool discovery is separate from model quality.** Skill run 01 inspected the skill/examples, attempted an unavailable `rg`, then called `snappea --help`, used `snappea check`, and replayed a counterexample; the transcript records early P syntax failures and an unexpected-output monitor failure followed by edits and a passing check ([tool-transcript.jsonl:5](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/tool-transcript.jsonl:5), [tool-transcript.jsonl:6](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/tool-transcript.jsonl:6), [tool-transcript.jsonl:8](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/tool-transcript.jsonl:8), [tool-transcript.jsonl:11](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/tool-transcript.jsonl:11), [tool-transcript.jsonl:19](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-01/tool-transcript.jsonl:19)). Baseline checked for `p`, `PChecker`, `dotnet`, and related binaries, found none, and stopped after writing model files without invoking a checker ([tool-transcript.jsonl:4](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/tool-transcript.jsonl:4), [tool-transcript.jsonl:6](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/tool-transcript.jsonl:6), [tool-transcript.jsonl:9](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-base-01/tool-transcript.jsonl:9)). The record supports “PChecker unavailable,” but does not establish whether Snappea was available from the container preflight; its command was neither discovered nor tried. The task did not initially name the installed Snappea command, so this tool-name/discovery ambiguity should be tracked independently from design quality. Skill run 02 discovers and uses `snappea check` after an initial unsupported `exists` syntax and identifier/parser repairs ([tool-transcript.jsonl:4](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/tool-transcript.jsonl:4), [tool-transcript.jsonl:9](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/tool-transcript.jsonl:9), [tool-transcript.jsonl:15](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/tool-transcript.jsonl:15), [tool-transcript.jsonl:17](/workspace/snappea-skill/evals/modeling-skill/phases/runs/stream-model-skill-02/tool-transcript.jsonl:17)).
