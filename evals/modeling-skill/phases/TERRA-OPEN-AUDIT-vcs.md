## Implementation evidence

All three use a versioned root read, prepare immutable content-addressed records, and CAS the root; failed root CAS loops back to reread and reevaluate. Successful publication places all heads, the published flag, and the request memo behind one root CAS; rejected publication also commits its memo. A lost root response is recoverable by reading that memo, and partial preparation is unreachable garbage. This is a credible mapping to the supplied single-key CAS primitive, conditional on collision resistance and eventual completion after contention/failures stop. All preserve the original submit digest and implement the stated guard order, approval and CI invalidation. Snapshot reads traverse immutable records from one root. The code supports the design argument; finite passing tests do not prove linearizability or crash safety.

`skill-01` and `base-01` use persistent hashed radix maps, namespacing heads, bundles and request IDs, with linked value chunks (1,500 ASCII characters versus 6,000 bytes base64). Their bounded-size nodes and path updates avoid rewriting all historical state, although storage accumulates unreachable records and calls scale with value size, target count and trie paths. `skill-02` instead serializes the entire state into 6,000-byte base64 leaves and 100-way internal nodes and rewrites/reads the whole tree on each mutation. Individual values fit the 16,384-byte bound, but history growth increases quiescent call cost for every operation. All three allow arbitrarily large valid strings, so a universal 5,000-call bound is not established; the fixed bound is infeasible for sufficiently large inputs under any bounded-record layout. `skill-02` explicitly acknowledges its whole-state scaling limit. Its history-dependent cost is a source-level risk, not a demonstrated violation in the stated hundreds-of-bundles and 64-branch setting; the audit did not independently measure such a violation.

## Models and observed evidence

- `skill-01` transcript calls 1–4 read the skill, implementation guide, examples and P references, then **copy** the versioned-publication `Revalidated.p` example and check it before writing Python at call 5. Its two competing publishers do model separate reads, conditional root commits and loser revalidation with an independent version/record monitor. The submitted model is the generic copied example, not a bundle-specific model: no heads, memo, durable preparation, crash, CI or approval. Its two-client fixed retry is bounded, not a general progress proof. The native check reports 137 schedules and 24/30 mutations detected; six mutants had incomplete searches, not confirmed survivors. Calls 9 and 11 show actual Python outcomes and heads sent to a strict monitor for a sequential rejection/success/replay history, plus racing publishers and root-response loss; the final seven tests passed. Call 10 records an actual 300-bundle, 64-branch, 20,000-character-head publish in 3,227 calls. Those observations cover those histories only, not arbitrary interleavings.
- `skill-02` read the skill, modeling guide, P reference, durable-retry and reservation examples (calls 1–5), authored and checked its own P before Python (calls 6–7), then consulted the implementation guide and observation examples. Its model separately schedules root reads and CAS, two competing requests and a duplicate ID, with independent monitor assertions; the CAS atomically updates head and memo, mirroring the proposed root abstraction. It models neither the actual immutable-tree preparation nor revisions/approval/CI, multiple heads, or crash transitions. A duplicate concurrent client approximates replay but is not an explicit lost-response crash; the monitor's memo is an ID marker rather than actual distinct outcome values. The native 5,413-schedule check skipped mutations. Calls 11–12 actually ran four custom Python tests and four public tests successfully: a strict observed sequential success/conflict/replay history, a race, crash offsets 1–4, and 120-bundle growth. The crash loop does not assert that each offset actually triggered a crash, and this growth test does not measure the 5,000-call bound or exercise a single large logical record.
- `base-01` wrote and tested Python first (call 7), then authored its P model (calls 8–9). It checked a versioned read/CAS race and a nondeterministic post-success retry; heads and memo are co-updated in one Store handler, representing the claimed atomic root rather than modeling immutable preparation or independently checking Python. Both clients share one boolean memo and same target values, so it cannot distinguish request outcomes, competing bundle payloads, or revalidation of conflict and readiness. The final model check reports 268 schedules and no mutations (`--no-mutation`); call 10 records four public Python tests passing. No custom implementation observation or crash/growth test is present in the frozen submission.

The strict Python monitor events in both skill runs are emitted by test code from actual returned results and `read_heads`, not fabricated standalone P announcements, but represent selected sequential observations; their separate concurrent/crash tests use normal assertions rather than model exploration. In `skill-01`, `observe.p` defines a stage-specific `PublishHistory` with a fixed sequence of `eCheck` outcomes and heads, separate from the copied `model.p` monitor. In `skill-02`, `observed.p` defines a separate `ObservedSafety` monitor over `eObserved(id, result, head)`, distinct from its design model monitor; converting heads to integers preserves the actual values in its bounded 0/1/2 scenario. These saved P tests validate selected scenarios but do not reuse the design-model monitors or establish general model-to-implementation refinement. None bridges all implementation operations and storage steps into a comprehensive P model. Successful model checks establish bounded properties of those abstractions, not correctness of the Python implementations or the entire contract.

## Comparison limits

In these three runs, skill exposure coincided with model-before-code, guide use and additional actual implementation tests; skill-02 also modeled competing IDs and skill-01 measured a substantial 64-branch case. Baseline nevertheless produced a similar persistent CAS architecture and a real retry/race abstraction, and skill-01's model was copied unchanged from a generic example. Skill-02's less scalable whole-snapshot layout shows that added model/observation evidence did not guarantee a better growth design. These are conditional, task-specific observations from two skill runs and one baseline, not a reliable estimate of a population effect or proof that skill caused the differences.
