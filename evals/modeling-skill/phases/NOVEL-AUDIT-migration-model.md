# Migration model v1 source audit

- **Skill run 01 has a material backfill fidelity bug.** It has separate `Backfill` and `PublicClient` actors, distinct prepare/apply operations, and each service handler runs atomically ([submission/model.p:38](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:38), [submission/model.p:47](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:47)). But apply copies staged logical rows directly to `shadow` for a, b, and c ([submission/model.p:51](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:51)). Live writes encode correctly, while inspected backfill rows simply expose the copied value ([submission/model.p:68](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:68), [submission/model.p:119](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:119)). The monitor repeats that representation: it copies its logical row into shadow on apply and compares inspection against that row ([submission/monitor.p:34](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/monitor.p:34), [submission/monitor.p:103](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/monitor.p:103)). Thus a clean initial backfill can report ready while `inspect_new("a")` exposes 10 instead of encoded 101. Its `read` also returns the shadow payload unchanged after cutover ([submission/model.p:103](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:103)); whether public reads should decode is ambiguous in the task wording, but inspection encoding is explicit. Its readiness/cutover check is limited to a/b/c ([submission/model.p:84](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:84)), and the monitor rejects other keys ([submission/monitor.p:54](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/monitor.p:54)). The key bound is undocumented, and the required `DESIGN.md` is absent. These are model/source issues, separate from execution budget: the transcript's `snappea check ... --timeout 90s` ended with exit 124 ([tool-transcript.jsonl:15](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/tool-transcript.jsonl:15)); that run is incomplete evidence, not a failed correctness assertion.

- **Skill run 02 is the strongest bounded model and monitor.** `MigrationService` owns authoritative, encoded shadow, and staged maps; snapshot preparation encodes live snapshot values and preserves tombstones ([submission/model.p:62](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/model.p:62)). Apply performs a revision-guarded merge in one service handler ([submission/model.p:90](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/model.p:90)); prepare, live writes, deletes, and apply are separate public service calls, so the scheduler can interleave the live actor between them. The monitor independently rebuilds snapshots and shadow state from public events, then checks readiness, cutover, reads, and inspection ([submission/monitor.p:46](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/monitor.p:46), [submission/monitor.p:73](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/monitor.p:73), [submission/monitor.p:91](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/monitor.p:91), [submission/monitor.p:125](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/monitor.p:125)). It uses the `Row` type declared in `model.p`, which is a compile/package coupling rather than evidence that its oracle reads service state. The fixed actors cover a pre-ready cutover rejection, two prepares, superseded and unknown apply tokens, repeated current-token apply, live write/delete interference, cutover, reads, and inspection. The declared finite key bound is a/b/c ([submission/DESIGN.md:9](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/DESIGN.md:9)); the service and monitor enumerate that bound, so behavior for other strings is outside this model. Tool output records 5,597 completed schedules for the concurrent lifecycle; the default command still exits on coverage-gate incompleteness, which the design reports separately ([tool-transcript.jsonl:29](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/tool-transcript.jsonl:29), [submission/DESIGN.md:11](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/DESIGN.md:11)).

- **Baseline has broad map-based state and meaningful order exploration.** Its service snapshots the whole authoritative map, converts live staged values on apply, guards merges by revision, and updates both maps atomically for live writes/deletes ([submission/model.p:31](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:31), [submission/model.p:37](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:37), [submission/model.p:48](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:48)). The monitor reconstructs staged and shadow rows from the public event history and checks arbitrary observed keys rather than a/b/c only ([submission/monitor.p:21](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/monitor.p:21), [submission/monitor.p:28](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/monitor.p:28), [submission/monitor.p:65](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/monitor.p:65)). Separate live and backfill actors issue calls to a shared service, allowing alternative orderings around prepare/apply; the second scenario supplies an ordered successful lifecycle ([submission/model.p:84](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:84), [submission/model.p:92](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:92), [submission/model.p:134](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:134)). The first scenario did not finish search: the final transcript shows 112,542 schedules at the 10-second limit, while the ordered case completed 257; the DESIGN accurately reports this limit ([tool-transcript.jsonl:42](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/tool-transcript.jsonl:42), [submission/DESIGN.md:11](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/DESIGN.md:11)). The baseline's fixed workload is broader than a single trace because the checker explores cross-actor message orderings, but it remains bounded to the finite requests and values the actors issue.

- **Atomic apply and monitor boundaries are aligned in all three models.** Each apply is one synchronous service handler, with writes/deletes schedulable between prepare and apply but not midway through an apply, as required by the task ([public/TASK.md:9](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/public/TASK.md:9), [submission/model.p:47](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:47), [submission/model.p:92](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/model.p:92), [submission/model.p:37](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:37)). The main domain difference is that skill-01/02 constrain history to three named keys, while baseline uses maps for the generated keys. Skill-02 discloses its bound; skill-01 does not.

- **Contract clarification opportunity:** the task explicitly says `inspect_new` exposes encoded shadow values and that reads use the active path, but does not explicitly state whether `read` must decode the new representation back to the logical integer. Skill-02 and baseline decode after cutover; skill-01 returns its shadow payload directly ([skill-02 model.p:149](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-02/submission/model.p:149), [baseline model.p:68](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-base-01/submission/model.p:68), [skill-01 model.p:103](/workspace/snappea-skill/evals/modeling-skill/phases/runs/migration-model-skill-01/submission/model.p:103)). Clarify this public boundary so that difference can be judged as correctness rather than interpretation.
