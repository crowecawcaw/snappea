# Frozen skill-v4 focused audit

Scope: read the two frozen submissions, prompts/metadata, manifests, and tool transcripts. No grading data or private files were read. Both manifests match their frozen files. Transcript call numbers below are one-based.

## The model-first instruction

Both agents read the updated skill entry containing the explicit instruction to write and check a meaningful P model **before** writing implementation (v4-01 call 1; v4-02 call 2; the instruction is visible in those transcript outputs). Neither followed that chronology. Run 01 wrote `solution.py` at call 5 and ran public tests at call 8 before creating its P model at call 16. Run 02 wrote `solution.py` at call 6, edited it at call 8, then created the model at call 10. Their first successful Snappea checks came later (v4-01 call 22; v4-02 call 22). Thus this cohort did not demonstrate a meaningful pre-code check; the new instruction was visible, but did not change the code-first workflow.

The checks themselves are small deterministic histories rather than concurrency explorations. Run 01 has one `Scenario` driving one `Store` through sequential requests; its successful check covered two schedules. Its modeled operation changes one branch at a time, so it does not test a single bundle's multi-branch atomic visibility. Run 02 has one `BundleDriver` issuing a fixed sequence to one `BundleStore`; its check also covered two schedules. It tests stale-base rejection and replay, but does not schedule separate clients between a modeled read and CAS. Both models are useful for request-result and no-reapply properties, but neither is a substantive check of the proposed multi-client concurrency boundary before implementation.

## Saved observations and evidence

Both final submissions include a saved, passing observation test. Run 01 imports `check_events`; run 02 uses `emit` within `check_spec`. The test wrappers call the actual `Service`, use actual returned outcomes, and obtain head values through public `read_heads`; they do not read hidden store fields. The result and head observations are therefore real public behavior, though their scenarios are serial.

- **v4-01:** `test_observation.py` checks a successful request, a different request ID on an already-published bundle, replay of the original ID after another bundle commits, and a stale-base conflict. Its P monitor tracks request results and modeled heads against emitted result/head-change observations. The observer does not cover a bundle that updates two branches in one call: A, B, and C each have a single-branch update. Separate saved tests inject a crash after the publish pointer CAS and check that a restarted instance returns the committed result and head; another checks a 20 KB payload. The public plus observation suite passed at call 28 (7 tests). This is useful implementation evidence, but the P check has only two schedules and the two-branch contract property remains untested in one operation.
- **v4-02:** `test_observation.py` reads both heads before and after each actual publish, emits the actual result and whether those public heads changed, then checks the P monitor. Its sequence covers A success, B conflict on the same two parents, replay of A's result after B's attempt, and a fresh request on already-published A. The monitor checks both modeled heads advance together and retries do not change the recorded result. The helper normalizes every head string other than the initial value to `1`; a wrong noninitial value could therefore pass its modeled state assertion. An exact mapping or direct final-head assertion would make the observation more discriminating. This is still a credible public-boundary test of the listed sequence. Public plus observation tests passed at calls 23 and 25 (5 tests).

The observer artifacts are stronger than v3 in run 02 because the same two-branch successful operation is observed before and after; v4-01 adds explicit post-CAS crash recovery. In both cases, P model checks and Python observations are separate evidence: the P models have only two schedules, while the saved API tests execute serial calls. Run 02's checker reports full statements, branches, and handlers, but only 18/20 conditions; it detected 17/29 mutants. Run 01 reports full modeled statements, branches, handlers, and conditions, but only 9/20 mutants detected. Neither report has suppressions. These model mutation counts are not Python implementation mutation tests.

## Overall finding

The explicit wording alone did not make agents model first: both read it, implemented, and only then produced a P artifact. Both saved observation tests now run against real public calls and are useful bounded checks, with clear provenance for actual return values and reads. The main gap is that the model-first step was not operationalized as a checkpoint or required artifact before implementation; the two final models are serial two-schedule histories, and the multi-client root-CAS race remains outside both checked models. Run 02 additionally needs exact head-value observation rather than mapping any noninitial value to the same modeled value.
