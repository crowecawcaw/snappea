# Frozen skill treatment audit

Scope: read only the three frozen `submission/` directories, their `tool-transcript.jsonl` and run prompts/metadata, plus the public modeling-skill rubric. No grading data, grader logs, hidden/private files, or other audit results were read. Transcript call references below are one-based `call` values in each run's `tool-transcript.jsonl`. This is a qualitative audit, not a correctness score or substitute for hidden grading.

## Cross-run findings

All three agents opened `/opt/p-modeling/SKILL.md` (treatment-01/02/03 call 1), and all read at least the modeling guide and a runnable/example model. Treatment-01 read the modeling, recovery, implementation, scenarios-and-oracles, and pattern reference material, plus durable-retry and versioned-publication examples (calls 3, 4, 11). Treatment-02 read modeling and implementation guides and versioned-publication material, then reservation examples (calls 3, 8); there is no transcript evidence it read recovery or scenarios-and-oracles. Treatment-03 read modeling, recovery, pattern reference, and versioned-publication materials (calls 2–3); there is no transcript evidence it read implementation or scenarios-and-oracles. This suggests the entry point and runnable examples are discoverable, while agents select the guides unevenly.

Every model used a P `Store` handler that checks a request and updates its abstract state in one non-yielding transition. That is a sensible model for an already-identified atomic primitive, and each DESIGN explains a limited publication focus. It does not expose the implementation's separate `read`, immutable record/blob writes, and root/pointer `cas` operations as independently schedulable steps. Thus the models can explore contenders at the abstract commit point, but cannot establish that the Python code's actual CAS/retry/staging boundaries implement that point, nor cover a crash after staging and before pointer CAS. Treatment-01 comes closest to the source boundary by focusing explicitly on pointer-CAS behavior; it still models that CAS as one abstract state transition.

None of the frozen submissions includes a saved runnable test harness that observes actual Python implementation calls/results and checks a P monitor. All three have Python implementations and P models, but their evidence is inline shell heredocs in the transcript. These checks are useful probes, not a reproducible source-to-model observation path. No agent modeled source-emitted events, and none demonstrated a deliberately defective implementation being rejected by a saved observer. The implementation/model relationship is explained structurally in DESIGN files, rather than checked by captured implementation events.

The best independent-oracle pattern appears in treatment-01 and treatment-02: each has a monitor with state distinct from the model Store and checks successful publication history, while treatment-02 also checks that the event's reported head matches its monitor's head. Treatment-03's monitor tracks both parent heads and detects stale-parent commits, but only sees successful commit announcements; its result handler accepts either `published` or `conflict` without independently checking that the result matches the history. In all cases, some model event fields are authored by the same Store transition being monitored, so the monitor is independent in state, not in observation provenance.

Model checking and inline probes received real use. Coverage and mutation reports were available and generally not hidden behind assertion-only validity flags. However, none of the runs followed the surviving mutants with a targeted new invariant/scenario in the final frozen model. Treatment-02 did respond to an early failed assertion and coverage gaps by revising the model/scenario before reaching full coverage; treatment-03 expanded the scenario to cover the all-parents branch and improved mutation detection. Coverage completion is useful feedback, but it did not close the fidelity and observation gaps above.

## Run-specific evidence

### skill-treatment-01

- **Model:** `submission/CommitPointer.p` models two publishers with expected head 0, one competing publication and a same-ID retry. The monitor checks that each announced applied request extends the monitor's current head exactly once (request uniqueness, expected head, and changed head). The Store memoizes both success and conflict. This gives a useful independent history check for pointer serialization and request replay. The model has one head and fixed request data; it omits bundle readiness/revision/CI, multi-branch publication, crashed staging, and the implementation's actual CAS call sequence. `DESIGN.md` explicitly calls it a focused model and lists these omissions.
- **Skill use:** entry point at call 1; modeling/recovery/pattern guide and runtime/tests at call 3; durable-retry and versioned-publication examples at call 4; implementation and scenarios-and-oracles guides at call 11.
- **Checks:** Snappea call 9 reports complete statement/branch/handler/condition coverage (32/32, 8/8, 2/2, 8/8), 11 detected of 25 mutants, zero suppressed. The transcript reports no added P model after this report. DESIGN reports 80 schedules, while the raw report's schedule count is not exposed at its top level; the mutation report includes 80-schedule complete searches for many mutants and one 1,000-schedule incomplete mutant search. The model is therefore useful but leaves substantial surviving behavior unchallenged.
- **Python probes:** public tests passed (call 7). Inline checks report crash recovery at selected writes and large-record handling (call 13), plus concurrent same-ID retry checks (call 14). These directly exercise the implementation, but the scripts are not retained as submission files; there is no modeled event observation. DESIGN says the crash checks cover staged-node and post-pointer-CAS positions, but these checks do not test a formal monitor.
- **Assessment:** strongest evidence of broad skill access and an explicit, honest boundary description. The model is a meaningful small design aid for pointer-level commit/retry semantics, but it only validates an abstracted protocol. Mutation feedback is reported rather than used to refine the frozen model.

### skill-treatment-02

- **Model:** `submission/AtomicBundle.p` gives two competing requests a single shared head; its monitor checks successful commits use the current parent, request retries preserve recorded outcomes, and the published event's head equals monitor state. It is a good compact check of idempotent result memoization and a single-head publication CAS. The task requires multiple heads to change atomically: the model does not represent two or more heads, readiness/revision/evidence, crash points, or separate root CAS and log staging. The one-head Store transition makes memo update and head update atomic by construction, so it cannot find a defect that splits those effects in the Python code.
- **Skill use:** entry at call 1; versioned-publication example and modeling/implementation guides at call 3; reservation model/tests at call 8. No transcript evidence of recovery or scenarios-and-oracles guide use.
- **Checks:** the first runnable check encountered syntax/lint/model coverage problems (calls 9–12). The agent then added a retrying client/scenario (calls 13–14). Final call 14 reports 1,770 complete schedules, statement/branch/condition/handler coverage 57/57, 20/20, 24/24, 2/2, and 23/45 mutants detected with no suppressions. This is the clearest example of using coverage feedback to improve a model. Twenty-two mutants still survive, and the final model was not visibly revised to target those survivors.
- **Python probes:** public tests passed (calls 7, 16). Inline checks exercise 64 branches, submit retry after revision, crash positions through completion, restart, and competing publishers (calls 16–17; DESIGN summarizes them). These are valuable implementation checks, but only the public test file is part of the frozen submission; the custom checks are not saved or linked to a P observation monitor.
- **Assessment:** most complete retry/result history model and broadest check report, though its single-head abstraction misses the key bundle-wide atomicity obligation. Coverage was actively used; mutation results were documented but not used for follow-up.

### skill-treatment-03

- **Model:** `submission/bundle_model.p` models two requests sharing two branch heads; one request's parent map is stale on one branch. The monitor rejects a successful commit unless both expected heads match and then advances both heads. This is a concrete negative case for checking every parent and provides the strongest multi-branch fidelity among the three P models. Its Store handler still checks and changes both heads in one non-yielding action. The conflict result is only checked for membership in an allowed string set, no result/request memo or retry is modeled, and the monitor sees successful commit announcements rather than independently observed implementation outcomes. There are no crash or root-CAS staging states.
- **Skill use:** entry at call 1; modeling/recovery/pattern references and versioned-publication example at calls 2–3. No transcript evidence of implementation or scenarios-and-oracles guide use.
- **Checks:** initial P check call 9 covered 23/23 statements, 2/2 branches, 3/3 handlers, but only 3/4 conditions and detected 4/14 mutants. After changing the second request's expected head to exercise the missing all-parents mismatch (call 10), coverage reached 4/4 conditions and mutation detection 7/14. Call 16 reran after moving the commit announcement to follow both head assignments; its coverage/mutation result remained 23/23, 4/4, 7/14. Seven mutants remain undetected, including removal of either initial-head assignment and of a head update. The DESIGN says the model checks that both heads advance together, but the monitor only sees successful `eCommit`; the model's own one-transition action supplies that event after its assignments.
- **Python probes:** public tests passed (call 13). Inline checks exercise a two-branch publication and lost-response submit/publish retry (call 15); there is no saved harness or event observer in the submission. The probe's transcript output confirms the custom path ran, not that P checked its actual result.
- **Assessment:** strongest concrete stale-parent negative control and visible improvement from coverage/mutation feedback. It still abstracts over storage-call boundaries and leaves several important mutations alive without follow-up tests.

## Tuning recommendations for the skill

1. Make source-boundary extraction the required first modeling step: name each actual durable read/write/CAS boundary, identify which calls yield, and justify every P atomic transition against those primitives. When the design has staged immutable data plus a pointer, show the staged-but-uncommitted state and the pointer-CAS visibility point, even if a smaller second model abstracts to that point.
2. Ask for at least one contract-derived negative control per important guarantee: stale one-of-many parents, a conflict/retry, lost response after durable commit, and crash before versus after the visibility CAS. Have the monitor derive expected outcomes from its own history and request inputs, not from a claimed `valid` flag or a model-authored outcome alone.
3. Treat mutation survivors as a question list. Require a short statement of which survivors are abstraction limits, which are missing scenarios/invariants, and one targeted scenario for each survivor that could violate the contract. Full structural coverage alone did not make these models informative enough.
4. Add a portable, saved Python observation example to the skill's expected deliverable: invoke the submitted implementation with selected inputs, capture actual inputs/results or explicit emitted events with provenance, feed those observations to a monitor with separate state, and demonstrate one intentionally defective implementation is rejected. Keep it runnable from the frozen submission directory so reviewers can repeat it.
5. Keep the novice path and honest limits. Treatment-01/02/03 all found and read the entry point, and runnable examples helped agents author P quickly. Better prompts/checklists should make model scope and evidence quality clear without encouraging a giant model of every operation.
