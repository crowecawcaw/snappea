# Frozen skill-v3 treatment audit

Scope: read only the frozen submissions, their tool transcripts, run prompts/metadata and manifests, plus the public modeling-skill audit rubric. While runs were still freezing, read-only `work/` copies were inspected and then checked against frozen artifacts. No grading data, grader logs, hidden/private files, or other audit results were read. All three submission manifests match the frozen files. Transcript call references are one-based. This audit distinguishes a saved file from evidence that the saved test ran against real implementation observations.

## Cross-run result

All three frozen submissions now include a saved Python test that imports Snappea's `check_events` helper and passes event dictionaries to a P monitor. Unlike v2, these are real service-level observations: the tests invoke `Service` methods and record the returned results; runs 01 and 02 also read public branch heads after each publish. No test claims to observe private storage internals. Each observed input is a test call's actual request/bundle data, and each observed result comes from the awaited `Service` call. Run 03 records only publish request IDs/results for the P monitor and asserts final public heads directly in Python.

The observation files were run and passed. Run 01's `test_model_observation.py` passed alone at call 25 and again with all four public tests at call 28. Run 02 initially had a test-discovery failure (call 20), fixed the test class and passed it at call 21; it then passed public plus observation tests after its later solution changes (call 27). Run 03 passed public and observation tests plus the P check at call 20, then passed the expanded four-test observation suite and public tests after later solution edits (call 31). The last final checks also passed Snappea lint for run 03. These are runnable, repeatable artifacts; they are stronger evidence than a P model or hand-written trace alone.

All three authored `solution.py` before their main P model (run 01 call 6 before 9; run 02 call 7 before 10; run 03 call 7 before 14). They therefore used the model primarily to validate a chosen implementation design, rather than to settle the abstraction before coding. Runs 01 and 02 read the implementation guide and relevant examples before their code/model work (run 01 calls 2–4, 8; run 02 calls 3–6, 9). Run 03 read the modeling/implementation guides early (call 3), then inspected helper signatures and example test code before writing its P model (calls 10–13), but after its Python implementation (call 7). All three used `announce` inside P models; that is model instrumentation, not Python observation. Their Python tests use `check_events` with wrapper-created dictionaries, not a Python `emit` call. This is appropriate for the public-boundary observations described, while leaving internal storage-call histories outside the evidence.

The P models use a non-yielding Store transition to represent the actual root CAS visibility point. That abstraction is explained and generally matched to each design's shared-root CAS. Runs 02 and 03 model a read/conditional-write interaction and retries explicitly; run 01's P model treats the whole publication decision as one Store transition. None feeds actual Python storage operations to Snappea or checks a real concurrent Python interleaving. The Python observation tests are serial scenarios, paired with P schedules that explore abstract concurrency. This distinction is stated clearly in run 01 and run 03 designs and should remain part of any quality claim.

## Run-specific findings

### skill-v3-01

- **Frozen artifacts and actual helper use:** `solution.py`, `BundleCAS.p`, `DESIGN.md`, and `test_model_observation.py`. The test imports `snappea.check_events`; its wrapper records each call's actual `publish` result and then the actual `read_heads` result for both branches. The input expectations and new heads are taken from the exact update map passed to `Service`. `strict=True` and `unknown_events="error"` make unexpected/missing observations fail the monitor. The final test passed at call 28.
- **Strongest property:** an accepted two-branch publish advances both heads together; same-ID retry returns its first result; a competing bundle from the stale base conflicts. The P oracle maintains its own head pair and request-result memo and compares them with each observation's actual result and public heads. `BundleCAS.p` also includes a new request for an already-published bundle and a competitor whose expected parent matches one branch but not the other, a useful all-targets negative control.
- **Negative controls and limits:** the implementation observer exercises retry and stale-base rejection, but its calls are serial, and its conflict bundle is stale on both branches. The one-parent-matches/one-parent-stale case exists in P schedules, not in the Python observation test. The observer does not exercise a lost response or process crash. The P model represents the root CAS as an atomic transition, so it does not validate the Python content-addressed map writes or the real `read`/`cas` sequence.
- **Model feedback:** initial model checks failed to parse/typecheck (calls 9–11), then scenario construction had syntax/coverage failures (calls 15, 19, 21). The author repaired the case and reached full model coverage (call 23); the one-parent mismatch was added after mutation feedback (call 27). Final check reports 1,097 schedules for the competing case plus two for published replay, 51/51 statements, 14/14 branches, 4/4 handlers, 18/18 conditions, 1/1 transition pair, and 20/30 mutants detected. Suppressions are zero. Several mutant searches stop at their 1,000-schedule budget. The change made after call 26 lowered the detected count from 22 to 20; the final result is the relevant one.
- **Chronology:** implementation was written at call 6, public tests run at 7, P model written at 9, and the observation helper signature inspected at 24. The saved observation test was added and run at 25. This is a substantial improvement over v2, though P remained a later abstraction of the implemented root protocol.

### skill-v3-02

- **Frozen artifacts and actual helper use:** `solution.py`, `BundleModel.p`, `ObservedBundles.p`, `DESIGN.md`, and `test_observation.py`. The test invokes the real service and records each publish return plus a subsequent public head read. It maps contract strings to small P values and maps actual returned head strings to modeled head values. `check_events` checks the resulting ordered trace against `ObservedBundles.p` with strict unknown-event handling. The actual IDs are supplied to the service; the numbered IDs are wrapper labels for the finite P scenario. It does not read or assert private store fields.
- **Strongest property:** a `not_ready` outcome remains memoized by the same request ID after the bundle becomes ready; a fresh request publishes; a later bundle advances the head again; replaying the earlier successful ID returns its recorded result without rolling back the newer head. This is the richest contract-level retry history in the three observers. The P model separately explores two publishers prepared against the same root version, a losing conditional write/re-read, one successful head advance, and same-ID retry.
- **Negative controls and limits:** the observed sequence distinguishes a durable rejected result from reevaluating after readiness changes, and checks that an old result does not undo a later head. The Python observer is serial and single-branch; the competing conditional-write schedules exist only in P. It does not test multi-branch atomicity, actual crash positions, or conflict results through the observation monitor. The P model's single head abstracts away the task's bundle readiness/revision/CI and branch map. P checks model one head and outcomes, while the observation spec checks a fixed contract scenario; they are related by property, not by a captured internal-code trace.
- **Model feedback and saved-test reliability:** the initial P model had state-machine/type/coverage failures (calls 10–16), then reached 383 schedules with complete statement/branch/handler/condition coverage (call 17). Later monitor changes improved the model report to 45/45 statements, 10/10 branches, 8/8 handlers, 10/10 conditions, and 9/41 mutants detected (call 30); no suppressions. Mutation detection remains low relative to generated mutants, and the report has survivors with incomplete 1,000-schedule searches. Test discovery initially ran zero tests (call 20), then a `unittest.TestCase` wrapper fixed it (call 21). It passed after later implementation changes at call 27. The final call 32 reran the four public tests only; the observation test had already passed after the last Python change. The observation P spec did not change after that pass.
- **Chronology:** implementation at call 7; main P model at 10; observation spec/test at 19–21; helper signature inspection at 18. The observation test is a real saved artifact, but the model came after code and the adapter was added after P model refinement.

### skill-v3-03

- **Frozen artifacts and actual helper use:** `solution.py`, `BundleModel.pproj`, `bundle-model.p`, `bundle-contract.p`, `bundle-tests.p`, `bundle-observation.p`, `DESIGN.md`, and `test_observation.py`. The observation test calls the actual `Service.publish`, appends the returned request ID/result to an event list, and checks that list with `check_events` against `RequestResultsAreStable`. It does not put fabricated head/state values into those events. The test separately reads public heads and asserts they remain `schema=s2, service=v1` after replaying an old request and then using a fresh request on an already-published bundle. The helper test and all extra saved API tests passed at call 31.
- **Strongest property:** the actual API test proves, for this scenario, that an old successful publish request keeps its result after another bundle advances the same branch, and that a new request on the already-published old bundle also does not reapply the old `service` head. Its direct final-head assertion checks the practical no-rewind effect. Additional saved tests cover lost submit response/restart, lazy initial heads, and a large chunked update.
- **Negative controls and limits:** the old request replay after a later state change is a strong negative control. The observation monitor itself checks only per-ID result stability; actual head non-reapplication is asserted in Python rather than encoded in its P observer. The test does not exercise a real concurrent Python race or a crash during publish. The P root model is stronger about concurrency: it separates `eRead` and `eCas`, explores a stale version/re-read, successful commit, conflict, and same-ID lost-response replay. But it uses a single branch and assumes approvals/CI are ready, so it cannot establish multi-branch or readiness behavior. The project also includes an `ObservationEmitter` with a hard-coded P trace for `tcObservedRetryContract`; that checks the observation spec itself only. It is not implementation evidence. The passing Python `test_observation.py` is the actual implementation observation.
- **Model feedback:** the final P check at call 24 reports 223 complete schedules for the root-CAS case and one for the synthetic observation-spec case. Combined coverage is 55/55 statements, 18/18 branches, 7/7 handlers, 19/20 conditions, and 3/3 transition pairs. It detected 24/57 model mutants with zero suppressions; some searches reach the 1,000-schedule limit. The one uncovered condition is in the root-CAS model. Snappea lint returned no findings, and the final public/observation suite passed at call 31. The report should not imply every condition was covered.
- **Chronology:** code at call 7; helper inspection at call 13; P root model at call 14; real-observation spec/test at calls 19–20. This is the closest model of the actual read/CAS boundary, but it too was written after the implementation.

## Overall assessment and next tuning

V3 achieved the intended concrete step: each frozen artifact has a saved, runnable implementation-observation test that feeds actual service return values to a P monitor. Runs 01 and 02 additionally feed public head reads to the monitor; run 03 checks those heads directly in Python. The events are wrapper-created, but their important fields come from public inputs and outputs, rather than assertions about hidden store state. Run 03's hard-coded P emitter is only a spec self-test and must not be counted as implementation evidence.

The most useful next skill revision is to keep this observer pattern required and make each test's observed fields traceable to public calls in comments or a tiny event-construction helper. For the model's strongest claim, ask for one implementation observation per relevant public state change and a contract-derived negative case. Keep separate claims for P schedule coverage and Python evidence: the models cover abstract concurrency, while all three Python observers are serial. Have agents review surviving model mutants and incomplete conditions, and avoid presenting full statement/branch coverage as proof of unmodeled multi-branch, crash, or storage-boundary behavior. The scripts are now concrete and reviewable; the next gain comes from improving negative-case depth and making the abstraction-to-source correspondence more explicit.
