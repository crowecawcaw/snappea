# Frozen skill-v2 treatment audit

Scope: read only each run's frozen `submission/`, `tool-transcript.jsonl`, and prompt/metadata, plus the public modeling-skill rubric and the explicitly permitted read-only work copies while runs were still freezing. No grading data, grader logs, hidden/private files, or other audit results were read. Transcript references below use one-based call numbers. This is an artifact/process audit, not a hidden-grade review.

## Main finding

The v2 guidance still did not produce a saved implementation-to-monitor test in any of the three submissions. Frozen deliverables are `solution.py`, `DESIGN.md`, and a P model; no Python test, observation adapter, event log, or helper module is present. Run-01 and run-03 did run custom Python probes from shell heredocs (calls 21/24 and 27 respectively), but those check their own returned values/assertions and are not retained or passed to a P monitor. Run-02 ran only the supplied public tests after its model check (call 18). The final P files emit and observe events internally with P `announce`; none emits events from the Python implementation, calls a Python-to-P observation helper, or uses an observation/trace command. Their Python code and P models are separate implementations of the same claimed behavior.

The observed chronology helps explain the gap without proving the agents' intent: all three started writing `solution.py` before creating the P model (run-01 call 7 before 10; run-02 call 6 before 12; run-03 call 9 before 12). Run-01 and run-02 had read the implementation guide before coding (calls 4 and 2) and reviewed durable-retry/versioned-publication examples (run-01 calls 5–8; run-02 calls 3–10). Run-03 read modeling and examples first, but only opened the implementation guide and a Python observation example after it had written both the implementation and P model (calls 24–25). All prompts requested only `solution.py` and `DESIGN.md`; none explicitly named a saved `model_observation.py` or `test_model_observation.py` artifact. That combination supports a likely explanation: the model remains an after-the-code abstraction/check, and the executable bridge is easy to treat as optional guidance when the required deliverables do not include it. These files alone cannot establish the agents' internal reason.

The three P models all treat a successful root CAS as one non-yielding Store transition. This is a reasonable abstraction for checking the linearization point once established, and each design says so. It means the model does not schedule the actual Python `read`, content-addressed writes, and root `cas` independently, or observe Python outputs at that boundary. Crash/retry probes therefore complement the model but do not show that the model checks those Python paths.

## Run-specific evidence

### skill-v2-01

- **Skill/example access:** entry point call 2; versioned-publication README call 3; implementation and modeling guides call 4; durable-retry P model/tests calls 5–6; versioned-publication model call 8. This is direct evidence the author had relevant guide/example material before writing `solution.py` (call 7), yet the design model came later (call 10).
- **P substance:** `AtomicBundle.p` models one request with a dropped response and same-ID retry competing with a second publisher. A separate monitor tracks both heads, successful effects, saved outcomes, and replies; it asserts both heads change together, only one competing publication wins, and retries preserve the first result. The P Store makes both head assignments and memo update one atomic transition. It covers the multi-branch commit/retry abstraction well, but has no parent values/revisions/readiness, no real `read`/`cas` scheduling, and no staged-data crash state.
- **Check feedback:** final check in call 18 reports 190 complete schedules, 51/51 statements, 10/10 branches, 9/9 handlers, 10/10 conditions, 1/1 transition pair, and 29/37 mutations detected; call 25 repeats the check. Several earlier checks failed while the author adjusted how commit events and client completion were represented (calls 10–17). This is substantial model iteration and mutation feedback, though it does not bridge to Python.
- **Python observation:** public tests passed (call 9). Inline checks report crash retries, concurrent publication, and a payload over 16 KiB (call 21); a later inline probe adds checkpoint replay (call 24). They are useful direct implementation checks, but are absent from the frozen submission and do not feed observed results to `BundleAtomicity`.
- **Assessment:** most developed P history and implementation probes in the set. Its clear stated scope is a strength; source correspondence and repeatability still rest on DESIGN claims.

### skill-v2-02

- **Skill/example access:** entry point call 1; modeling/implementation guides and versioned-publication README call 2; durable-retry README/project/tests calls 3–5 and 10; versioned-publication files calls 7–9. The implementation is written in call 6; the P model is written in call 12.
- **P substance:** `Publication.p` models a not-ready result that is memoized before readiness changes, two ready request IDs competing to publish one two-branch bundle, and repeated IDs. An independent monitor checks outcome stability by request ID, one atomic two-head change, and request/result correspondence. The code assumes a single `RootStore` handler transition co-commits memo and heads. It is a focused useful model for publication idempotency, but not the Python snapshot-tree encoding, CAS/read schedule, or crash positions.
- **Check feedback:** DESIGN reports 114 complete schedules and full statement/branch/condition/handler coverage; the transcript shows early model construction/check and one repair pass (calls 12–13). It notes mutation exploration reached the schedule budget before checking all mutations. There is no transcript evidence of a targeted follow-up for remaining mutants, and no custom Python scenario beyond `python -m unittest -v test_public` (call 18).
- **Python observation:** no saved observer or custom Python probe appears in `submission/`; the final work uses only the supplied public test run as implementation evidence. P `eRequest`, `eOutcome`, and `eCommitted` are generated by the P test itself, not by Python.
- **Assessment:** strongest explicit negative control for a durable rejected outcome across readiness change, but weakest implementation-observation evidence of the set.

### skill-v2-03

- **Skill/example access:** entry point call 1; modeling and versioned-publication README call 2; durable-retry model/test files calls 3–8; reservation and versioned-publication examples calls 10–11. `solution.py` was written at call 9 and `BundleAtomic.p` at call 12. The implementation guide and Python storage example were read only later, at calls 24–25, after the P checks.
- **P substance:** `BundleAtomic.p` models two clients, two branch heads, snapshot reads before or after a publication, one winning update, one conflict, and same-ID retries. Its monitor checks snapshots are both old or both new and keeps request outcomes stable. It is a good compact negative case for one root-pointer publication becoming visible across two branches. The P Store still performs both head updates and request memoization in one handler; neither client passes a conditional expected-head pair, and the model omits staged chunks, crash positions, and the Python root CAS sequence.
- **Check feedback:** the early model missed some branch/handler coverage (calls 14–16). The author strengthened the monitor and scenario (calls 17, 20–22); final DESIGN reports 3,126 schedules and full statement, branch, and handler coverage. The full report at call 22 still has 11/12 conditions covered. The mutation run at call 23 hit its time limit, although Snappea exited 0 and reports no assertion failure. This is clear coverage-driven revision, but the final report is bounded and not a mutation-complete result.
- **Python observation:** public tests passed (call 18). A custom inline check at call 27 reports crash, retry, 64-branch, and 80-bundle checks passed. It is not saved in the submission and does not emit observations into the P monitor. The agent read the implementation guide/example after authoring the P file, suggesting the bridge material was too late in the chosen workflow to change the deliverable.
- **Assessment:** useful read-after-write and two-head scenario, with transparent scope limits. It has the clearest timing evidence that guide/example access did not result in a bridge artifact.

## High-priority advice for the skill and pilot prompt

1. **Turn the bridge into a required file, not a suggestion.** Name and require a saved runnable observation test in the entry-point deliverables (for example, `test_model_observation.py`). The test should run `solution.py`, capture real inputs/results or explicit implementation events with provenance, and check a monitor with separately maintained state. A P-only `announce` is not an observation of Python behavior.
2. **Show the smallest complete bridge before the full design guides.** Put a copyable Python-to-monitor example in the first-session path: instrument one actual storage or service boundary, run a saved scenario, show a real trace being rejected after changing the implementation in a small way, and give the exact command that replays it. Link the helper API at the point where the example uses it. In these runs, agents copied and adapted P project tests but did not call any bridge API.
3. **Put design order in the task and artifact checklist.** Ask for a contract-level model and scenario before implementation, then the implementation, then the saved observation check. The actual prompt said “model ... then implement,” but all three coded first; adding an explicit model checkpoint/artifact makes this sequence visible and reviewable.
4. **Tie model events to concrete storage boundaries.** Have the agent list actual read/write/CAS operations and identify which P transitions stand for them. Keep a small abstract root-CAS model where useful, while asking the observation test or a second model to exercise interference and crashes around writes before/after that CAS.
5. **Keep useful coverage feedback, but give it a next step.** Runs 01 and 03 improved models after coverage feedback; run 03 retained an uncovered condition and a timed-out mutation report. Ask authors to name uncovered conditions/surviving mutants and either add a discriminating scenario or state why the case is outside the abstraction. This should remain secondary to checking concrete code behavior.

The pilots show that entry-point and example access is not enough to make observation testing happen. The next revision should surface the bridge earlier, make it an explicit deliverable, and provide an exact saved test that authors can run against their own implementation.
