# Compare the implementation through events

A model describes allowed behavior; an implementation test asks whether actual behavior violates the same contract. Bridge them with events emitted at meaningful state changes, after the relevant operation commits. Include enough payload to let the monitor distinguish outcomes and identities. Use one partition key for each independent entity whose history the spec should track, such as an account, order, or lock. If two operations share a global invariant, choose a key that keeps them in the same monitor instance.

In Python, application code can call `snappea.emit`; a selected test can record actual calls and check the resulting events with `check_spec`:

```python
from snappea import check_spec
from storage import ReservationStore


def test_competing_reservations():
    with check_spec(
        "Capacity",
        spec_files=["capacity.p"],
        strict=True,
        check_hot=True,
        unknown_events="error",
    ):
        store = ReservationStore(1)  # emits eOpened
        first = store.read()
        second = store.read()
        assert store.reserve_if_unchanged("order-a", 1, first)
        assert not store.reserve_if_unchanged("order-b", 1, second)
```


The helper checks events generated by application calls. Its captured-event form, `check_events(events, "Capacity", spec_files=[...])`, is useful when a test already records events. Hand-written traces test the spec itself; they do not provide evidence about the implementation. The Python package imports as `snappea`; its distribution name is `pysnappea`. The [reservation example](../examples/reservation/README.md) uses this helper with events emitted by the real storage calls.

An event is evidence only for the behavior it records. Python events include the emitting call site (`src`) in failure output, which helps locate the code that made the observation. An `eAccepted` emitted before a database commit cannot establish that the commit happened. An event written after a transaction can still be lost if the process crashes before the emitter flushes it. If you need to check commit order, place the event after commit or capture the committed result through a reliable test boundary. If a test checks events but never invokes the concurrent path, the monitor has not checked that race.

Observation has explicit completeness limits. `strict` requires at least one relevant event for every selected spec, which catches disabled instrumentation or an empty recording. It does not prove that every required operation emitted an event or that no event was dropped. Python is transitioning named-spec strict behavior with a warning; pass `strict=True` explicitly in tests so a spec with no relevant events fails the check. `unknown_events="error"` catches undeclared or misspelled event names; CLI `snappea observe` defaults to ignoring them. If a spec ignores a declared event, it is not checked by that spec. See [Python helper options](https://github.com/crowecawcaw/snappea/blob/main/python/src/snappea/__init__.py) and the [observer strictness docs](https://github.com/crowecawcaw/snappea/blob/main/docs/observe.md#strict-observation) for the distinction.

Instrumentation should not change application outcomes. Production emitters are best-effort: they must not raise or block a request, and bounded queues or sink failures may drop events. Expose the helper’s dropped count if logs are evidence used operationally. In a test, prefer direct recording so invalid behavior fails the test. Stop or join child processes before checking their event folder; otherwise the check can finish before their final events arrive. Keep recording boundaries aligned with one test or one generated history, not a whole suite of unrelated runs.

Finally compare the model’s boundary with the code’s real boundary. If the model calls a read-and-write atomic but the application uses two independent calls, implementation observation may reveal a behavior the model could not express. Update the model or document why the implementation has an equivalent lock, transaction, or conditional write. A passing observation establishes that the recorded history satisfied the monitor; it does not establish correctness for unobserved schedules, missing events, or model assumptions.
