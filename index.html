One spec checks the design and the running code

A spec is a state machine that watches events and checks rules about them. Check the model's events while you design. Then check your application's events from ordinary tests, against the same spec.

You, or an agent, write a model of the design. snappea check runs it thousands of times, each with a different ordering of messages, and the spec flags any run that breaks a rule. None of your service code is involved.

When the checker finds a failing ordering in the model, turn it into a regression test that forces the same ordering on the real code.

The diagram is an illustration, not a live check. Model checks cover the behavior and assumptions you modeled. Application checks cover the events your tests produce; they do not explore every execution of your code.

Built for agents

Most model checkers were designed for a person at a terminal. Snap Pea's commands, guide, error messages and checks were designed for an agent to run, and changes to them are measured with agent evals.

Fewer missed design mistakes in pilot evals

In pilot evals, agents modeled a design. Hidden broken versions of that design were then run against the specs and tests the agents wrote. Agents using snappea missed 22 of 180. Agents using the same checker through the upstream p command line missed 50. That is 56% fewer.

Haiku agents, three to six runs per task. Eval setup and results

The guide is in the binary

snappea guide teaches the workflow: what to model, where to stop, and how to test the implementation against the specs. There is no skill file to write or keep in sync.

One command runs every check

snappea check lints the model, tries message orderings, and reports coverage and mutation results. It picks the search strategies; the caller sets a time budget. It is one binary with no .NET or Java to install, so it runs in a bare CI image or agent sandbox.

JSON results, and errors that name the fix

snappea check --json prints structured results. Every error says what went wrong, where, and what to try next.

A model with untested behavior fails the check

Lint findings, coverage gaps and undetected mutants fail the check, so an agent cannot stop at a model that passes without testing anything.

How it compares

Upstream P

Snap Pea runs the P models you already have, through either of two commands. Both are one binary that reads .p files directly. Upstream P compiles a model to C# and runs it on .NET; Snap Pea needs no .NET, C# or Java toolchain and has no compile step.

snappea-compat: a drop-in for p, about 100 times faster

It takes the same options and prints the same output and replayable schedules, so existing scripts keep working. See compatibility and migration.

snappea: the command line designed for agents

It adds automatic search, lints, coverage and mutation testing. In pilot evals, agents using it missed 56% fewer hidden design mistakes than agents using the p command line. Eval results.

TLA+

TLA+ describes a system as logic formulas over its state. P describes it as state machines that send each other messages, which reads closer to service code.

Verus

Verus proves properties of Rust code itself, which suits low-level work such as data structures and memory safety. P checks the design of a distributed system: message orderings, retries and failures.

Install

The checker is one binary with no runtime dependencies. On Linux or macOS, install it and read the built-in guide:

$ curl -fsSL https://raw.githubusercontent.com/crowecawcaw/snappea/main/scripts/install.sh | sh
$ export PATH="$HOME/.local/bin:$PATH"
$ snappea guide

The installation guide covers Windows, pinned versions, Cargo and PyPI. To check events from application tests, add the helper for Python, Rust, Go or Java.
