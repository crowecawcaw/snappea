Read the model. Find the race.

Two clients each add one to a shared counter. Each reads the current value, then writes back that value plus one. What happens if both read before either writes?

This is P: state machines exchange messages with send and handle them with on. The test starts two clients and checks that the final counter is 2. Run the model to explore message orderings, then try making the increment atomic.

Two increments should leave 2.

Each client runs independently. The checker chooses which message is delivered next.

Read then write leaves a gap for the other client to run. Atomic increment updates the value in a single handler.

The same rules, from design to application tests

A spec is a state machine that observes events and checks rules about them. Check the model's events while designing, then check your application's events from ordinary tests.

You, or an agent, write a model of the design. snappea check runs it thousands of times, each with a different ordering of messages, and the spec flags any run that breaks a rule. None of your service code is involved.

A contract to review

Write down the real atomic operations and what must stay true. For the counter: every completed increment contributes exactly one to the total.

A spec to share

Express that contract independently of the algorithm. Check events from both the P model and real application calls against it.

A regression test to keep

Force both calls to read before either writes. Use the counterexample to test the implementation, rather than hoping a stress test hits it.

When a check fails, review the design, model and implementation together. Turn counterexamples into regression tests that force the troublesome ordering on real code.

Model checks cover the behavior and assumptions you modeled. Application checks validate the events your tests produce; they do not explore every execution of your code or establish full equivalence.

Give your agent a model checker

Ask your agent to model a feature before implementing it. The built-in guide teaches the workflow, modeling boundaries and implementation tests. Structured CLI results and actionable diagnostics help it inspect failures and revise the model. You review the contract, assumptions and specs.

Fast feedback, on every change

One binary, no compile step or runtime toolchain. Automatic exploration combines exhaustive search, coverage-guided random search, deliberate delays and priority scheduling. It adapts the mix as it discovers new behavior, so you can set a CI time budget without choosing a scheduler.

Install

Install the prebuilt checker on Linux or macOS, then read the built-in guide:

$ curl -fsSL https://raw.githubusercontent.com/crowecawcaw/snappea/main/scripts/install.sh | sh
$ export PATH="$HOME/.local/bin:$PATH"
$ snappea guide

See the installation guide for PATH setup, Windows, pinned versions, Cargo and PyPI options. GitHub releases include binaries for Linux, macOS and Windows. Add a helper to check events from your application tests:

$ pip install pysnappea                       # Python
$ cargo add --dev snappea                   # Rust
$ go get github.com/crowecawcaw/snappea     # Go

Java: io.github.crowecawcaw:snappea on Maven Central, plus a natives jar with the checker (Maven and Gradle snippets). Each language has a guide: Python, Rust, Go, Java.
