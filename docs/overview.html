Overview

What P is, and how it differs from the tests you already write.

Two clients each read a shared counter, add one and write it back. Your unit tests pass because they run the calls in one fixed order, but in production both clients can read 0, and one update is lost. P finds that ordering in milliseconds, from a short model of the design, before any service code exists.

A model, a spec and your code

P is a language for writing small, runnable descriptions of a system's design. You use it to check two kinds of thing:

You, or an agent, write a model of the design. snappea check runs it thousands of times, each with a different ordering of messages, and the spec flags any run that breaks a rule. None of your service code is involved.

Is P my code?
No. A model describes your design: the components, the messages they send, and what each does when a message arrives. It's usually a few hundred lines, and it runs only inside the checker.
Does it check my code?
The checker runs the model, not your code. A spec is a rule written in P, like "stock never goes negative". The same spec checks the model at design time and, through events your tests record, your code at test time.
How does a model help?
It finds bugs that depend on timing: races, reordered or lost messages, retries and crashes. Unit tests rarely hit these bugs, and they cost the most to fix once the code is written.

How it differs from a unit test

In a unit test, you pick one scenario and its order of events. In a P test, you describe the setup, and the checker picks the order: which message arrives first and which component runs next. It runs thousands of orderings and stops at the first one that breaks a rule.

Where P fits

↺ bug found: change the design, update the model, check again

Design. Write or update the design doc: components, messages, failure cases.

AI agents are well suited to writing models: they can turn a design doc into machines and specs quickly, and rerun the checker after every change. Your part is to read the specs. They are the short, plain statement of what must always be true, and the part of the model worth reviewing line by line.
